03前提

先講清楚：限制與現況

限制

  • CCR 在 Doris 4.1 沒有可用的 syncer（官方文件也已下架）——沒有現成的官方跨叢集複製
  • 內部物件儲存不可靠——存算分離／冷備（需 S3/HDFS）受限
  • 使用者程式不可控——平台只握有連線端點與選配 library

現況

  • 公司內其他 team 的慣例：Cassandra team、MFG（Oracle）都是 client 自己管 data consistency——平台不代管跨系統一致性
  • raw 寫入 100% 經 Kafka——具備「源頭重放」的先天條件
HA 設計要在這些邊界內做——後面每個方案的取捨都源自這一頁。

要保住的三件事：R1・R2・R3

R1 快速 failover

邊界：不防程式 bug（重放救）、不管 Kafka 自身（前提依賴）。

05第一部 · 同叢集

同叢集 HA：誰來挑活著的 FE？

叢集內掛一台沒事：3 台 FE 自動選主・資料存 3 份——這層 Doris 自己處理

① JDBC URL

client 自己挑

零基礎設施

改所有 client・只認連線錯

② HAProxy

中間人挑

主動健檢・真 SQL

可延伸跨叢集 ★

③ ProxySQL

聰明中間人

懂 MySQL 協議

Doris 相容坑

④ Nginx

被動中間人

熟悉・簡單

要先失敗才剔除

FE 掛的那一刻：②③幾秒剔除無感；①④要有請求先倒楣。

06第一部 · 同叢集

HAProxy 內部：怎麼主動切換

每 2–3 秒主動探測每台 FE（可跑真 SQL） 連續失敗 → 名單內剔除・恢復 → 加回 整座切換＝翻 flag 換名單（一個動作）
可單台起步：proxy 掛＝入口斷、資料無損；之後加第二台＋keepalived，設定原樣搬。

07第二部 · 跨叢集

方案總覽：同一張圖，六條路線（點選切換）

含 CCR ▸ 不含 CCR ▸

A1 全庫 CCR排除

優點

  • 寫入方無感・DDL 自動同步
  • 唯一能秒級複製 curated・跨 zone skew 最小

缺點

  • 4.1 無 syncer——要走＝自己移植＋維護
  • RPO 非零・FE 切主觸發 full sync
  • 無反向同步——failback 全量重建
  • B 座唯讀

A2 curated 限定 CCR排除

優點

  • CCR 成本只花在 curated
  • 使用者 DDL 自動跟隨

缺點

  • 維護前提同 A1（自己移植＋養）
  • 使用者自由操作最易踩不支援清單而中斷同步

B1 raw 雙寫＋curated 使用者自理入圍

優點

  • 平台成本最低・責任邊界乾淨
  • raw RPO≈0・failover 零 ingestion 動作
  • failback 最簡（無反向鏡像/禁寫）
  • 組織先例：Cassandra／MFG(Oracle)・dbt 重跑即重建

缺點

  • curated 跨座一致無平台保證
  • 需要政策公告與使用者溝通
  • 非 dbt、不可重算的表風險自負

B2 raw 雙寫＋curated 平台鏡像條件

優點

  • 對使用者零侵入
  • curated 有平台承諾的 RPO（鏡像週期）

缺點

  • 六難全攬回平台：loss window 壓不到零
  • failback 反向覆蓋・禁寫・凍結全套 runbook
  • 認賠責任談判・表發現與對帳日常維運

B4 無 HA＋Client Library低需求

優點

  • 零基礎設施・平常零維運
  • 路由可更聰明・可灰度

缺點

  • 採用不可控・BI/dbt 裝不了
  • 過渡期 A、B 同時被寫——curated 分歧
  • 決策分裂 or flag 服務又要 HA

08第二部 · 跨叢集

選 B2 前先看：平台代管 curated 的六個難

① 寫入者不可控

只能事後搬運

② loss window 壓不到零

頻率 ↑＝主座壓力 ↑

③ failback 語義複雜

反向覆蓋・禁寫・凍結

④ 認賠責任談判

丟的是使用者的資料

⑤ ETL join 兩 zone

鏡像也對不齊時點

⑥ 好走的路被堵死

CCR：4.1 無 syncer

高成本，買到的仍是非零的遺失窗口。

09第二部 · 跨叢集

看完六條路之後——推薦：B1・兩層路由・雙路資料

10第二部 · 跨叢集

Curated 自理：責任分界

平台負責

raw 兩座一致＋對帳可切換的入口切換通知（選配）鏡像工具模板

使用者負責

curated 跨座一致自行雙寫 or 重跑 ETLdbt：dbt run 即重建

11第二部 · 跨叢集

Library 路（B4）：腦袋放進每個 client

12第二部 · 跨叢集

Library 路：優缺點

優點

零基礎設施路由更聰明可逐批切換（先讓少數 client 試切）

缺點

採用不可控BI/dbt 裝不了切換時各 client 更新時間不一→有人寫 A 有人寫 B，curated 分岔每個 client 自己判斷打哪座→判斷結果可能不一致
定位：VIP 為主・library 選配（判斷讀平台 flag）
適用：HA 需求低＋client 少且可控＋切換極少。

14保留可能性 · CCR

之後的每一年：「Doris 出 4.2 了」會發生什麼

① Diff 介面

29 個 Thrift IDL 逐檔比對新版

② Regenerate

重新生成 56 萬行、修編譯錯
這部分編譯器會抓 ✓

③ 盤 28 個 JSON 結構

沒有規格書——唯一真相是 FE 的 Java 原始碼；欄位改了不會編譯錯，只會靜默出錯

④ 補新 DDL handler

實例：上游做一次＝14 檔・+213 行（含 6 個雙叢集回歸測試）

⑤ 全量回歸 ×2

新舊版本兩種組合各跑 661 個測試

⑥ 順序演練

Syncer → 下游 → 上游，不可跳過

每一輪的成本

  • 小版本 0.5–1 人月／大版本 2–3 人月
  • 每年至少一次；不做＝叢集鎖在舊版

  • 首年 3–5 人月＝資深工程師的半年；之後 0.4–0.6 FTE
  • 技能＝Go＋讀得懂 Doris FE 的 Java——他離職＝bus factor 歸零
