02PART 1 · 光譜與判準

任務自動化不是新東西——LLM 加入後多了一道光譜

「自動化」早就有了：ETL、CI/CD、排程、DAG。LLM 帶來的不是自動化本身，而是讓「不知道確切步驟」的任務也能自動化。

舊自動化
步驟寫死
ETL · CI/CD · Airflow
＋ LLM
自然語言任務
「幫我查 Trino 為什麼變慢」
步驟無法預先列完
→
光譜
Workflow ↔ Agent
固定路徑 ↔ 動態決策

解決的瓶頸

AUTOMATION 的邊界擴張
  • 過去要寫程式才能自動化的任務，現在一句話就能起頭
  • 中間的「不確定性」由模型補上，不用人先窮舉所有分支

仍沒解決

NEW PROBLEMS
  • 模型會出錯、繞路、胡謅——產出不能直接當真
  • 每跑一輪都在燒 token，失敗重試也燒
  • 執行路徑不固定 → 除錯與稽核變難
真正的問題不是「要不要自動化」，而是「自動化到什麼程度」。

03PART 1 · 光譜與判準

不是 workflow 或 agent 二選一——是「誰決定下一步」

Workflow同一個問題：任務自動化Agent

Workflow：控制流在 code

N8N · HOOKS · AIRFLOW · 純 CODE
  • 步驟順序寫死：這步做完換下一步，不因模型心情改變
  • LLM 只是其中一個 function call——被關在固定步驟裡
  • 可測試、可 resume、失敗模式明確（第 3 步掛了就是第 3 步）
  • 工具由 code 呼叫，不是模型挑

Agent：控制流在模型

LANGGRAPH · PYDANTIC AI · CREWAI · ADK
  • 模型看到工具清單，自己挑、自己組合、自己定順序
  • 在你畫的框架裡選：工具集、狀態、停止條件都是你定義
  • 路徑不固定，繞路、重試是常態
  • 底層就是一個 loop，直到它不再呼叫工具
關鍵澄清兩端都可以有 LLM——deterministic 不是「沒有 LLM」，是「LLM 被放在固定步驟裡」。
分界線只有一條：誰決定執行哪個工具——寫死的程式碼，還是模型的推理。

05PART 2 · Harness 心智模型

所有 Agent 框架，底下都是同一個 loop

使用者
一句話任務
→
LLM（帶工具清單）
決定：呼叫工具 or 直接回覆
→
執行工具
search / calc / API……
→
結果回填
塞回 messages 再問一次
↺ 迴圈 —— 直到模型不再呼叫工具（或超過你設的步數上限）→ 輸出答案

核心 loop（約 20 行）

WHILE NOT DONE
  • 模型回傳的可能不是文字，是工具呼叫請求
  • 執行結果以 tool role 回填，模型再看一次
  • 「不再呼叫」或「超過上限」＝結束

框架做的事

LANGGRAPH · PYDANTIC AI · CREWAI · ADK
  • 把這個 loop 包成 API＋工具註冊＋狀態管理
  • 加上可觀測性、checkpoint、暫停恢復
  • 差別在編排方式，不在 loop 本身
看懂這 20 行，就看得懂所有框架——框架是幫你把 loop 的細節藏起來。

06PART 2 · Harness 心智模型

模型吐「意圖」，Harness 執行——分工就這兩句

動畫示意：橙點＝指令進大腦 → 經身體 → 到手執行工具；藍點＝執行結果回填大腦 → 回應使用者。

為什麼這個模型有用

TEXT IN / TEXT OUT
  • 模型是純文字函式——可以任意替換，harness 不動
  • 「給模型工具」＝在 prompt 塞 JSON schema＋在 harness 註冊 function
  • 工具即協議，沒有魔法

所以安全住在哪

NOT IN THE MODEL
  • 所有安全機制都是你的 code：權限、sandbox、參數驗證
  • 模型只能「建議」動作，能不能做是 harness 說了算
  • 你每天用的 AI 助手本身就是一個 harness
tool call 只是一段 JSON——真正執行的是你的程式，別把信任交給模型。

07PART 3 · 落地檢查表（上）

落地檢查表 ①：定義層＋執行層——動手前先想清楚

定義層
工具設計：粒度、description 品質（模型靠 description 選工具）· 副作用聲明：會寫 DB？會花錢？· 狀態 schema：哪些要跨步驟保留
執行層
Loop 上限：max iterations、timeout——沒有上限是燒錢無底洞 · 冪等性：retry 工具＝重複副作用 · 成本：token 預算、快取、model tiering · context 管理：摘要、壓縮、RAG
信任層
最小權限 · prompt injection · HITL 人審
觀測層
trace · evals · 驗證機制
營運層
版本管理 · CI · 升級路徑

最常漏的執行層坑

RETRY = SIDE EFFECT AGAIN
  • agent 對工具 retry＝重複執行副作用（重複刷卡、重複發信）
  • 工具要有冪等設計（idempotency key）或明確禁止重試

例子：alert 處理的 10 步 chain

定義層 × 執行層
  • 定義層：每步的輸入輸出（alert → 診斷 → 修復步驟）、權限範圍、驗證標準
  • 執行層：每步一次 LLM 呼叫，失敗只重跑該步
沒有上限與冪等性的 agent，是 production 的隱形炸彈。

demo 與 production 的分水嶺，是 evals 與驗證機制——不是模型選得多好。

09PART 3 · 落地檢查表

兩個最常漏的坑：冪等性、驗證機制

坑 1：retry 會重複副作用

IDEMPOTENCY
  • agent 掛了重試＝同一個動作再做一次
  • 重複刷卡、重複發信、重複建帳號
  • 解法：idempotency key、先查後寫、副作用工具禁止 retry

坑 2：self-report ≠ truth

VERIFICATION
  • agent 說「完成了」不代表真的完成
  • 對有副作用的動作做獨立驗證：讀回檔案、查 API 確認
  • 子 agent 的報告也要驗——它可能搞錯或自我感覺良好
Agent 回報
「已寄出、已寫入、已完成」
→
獨立驗證
查 API／讀回檔案／檢查 DB row
→
確認或補救
真的成功才往下走
對有副作用的動作，永遠假設它會重複、會說謊——驗證是你的保險。

12PART 4 · 模式與框架

框架都是預組好的 harness——選的是編排方式

LangGraph

圖結構 · CHECKPOINT · INTERRUPT
  • 流程畫成 node + edge；edge 可固定、可由 LLM 選
  • checkpoint 可 resume、interrupt 可人審中斷
  • 適合多步驟、要人介入的複雜流程

Pydantic AI

單 AGENT · TYPE-SAFE · 上手平緩
  • 輸出用 Pydantic 定義，錯型別直接報錯
  • 工具用 @agent.tool 註冊，最少的樣板
  • 適合「一個 agent + 幾個工具」的規模
CrewAI
角色分工：agent 有 role/goal/backstory，任務串成 crew
ADK（Google）
多 agent 編排、session 持久化、Gemini 生態
n8n
視覺化 workflow，LLM 只是其中一個節點
每個框架都給你：loop + 狀態 + 工具註冊 + 可觀測性——差別在怎麼編排、多重的抽象。

實務規則：從最不自主的開始，不夠再升級

① 可預測
純 code / n8n
步驟寫得死 → 最便宜、最好測，不需要框架
② 單一 agent
Pydantic AI 這類輕框架

# pip install langgraph
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):          # 共享狀態
    alert: str
    root_cause: str
    fix: str
    report: str

def detect(state):     # 節點 1：偵測 alert
    return {"alert": check_alerts()}
def diagnose(state):   # 節點 2：診斷根因
    return {"root_cause": llm("分析異常來源", state["alert"])}
def heal(state):      # 節點 3：修復＋報告
    fix = run_fix(state["root_cause"])
    return {"fix": fix,
            "report": llm("寫 issue 報告", fix)}

g = StateGraph(State)
g.add_node("detect", detect)
g.add_node("diagnose", diagnose)
g.add_node("heal", heal)
g.add_edge(START, "detect")
g.add_edge("detect", "diagnose")
g.add_edge("diagnose", "heal")
g.add_edge("heal", END)
app = g.compile()
print(app.invoke({})["report"])
固定 edge 是 workflow，edge 讓 LLM 選就是 agent——一個框架兩種模式都有。

Pydantic AI：單一 agent，輸出型別安全

Agent
model ＋ system_prompt ＋ result_type
@agent.tool_plain

run_sync()
一次 agent loop，回傳 typed result

# pip install pydantic-ai
from pydantic import BaseModel
from pydantic_ai import Agent

class HealReport(BaseModel):   # 輸出型別
    root_cause: str
    actions: list[str]
    verified: bool

agent = Agent(
    "openai:gpt-4o",
    system_prompt="你是維運工程師：收到 alert 先診斷根因、執行修復、驗證，最後寫成 issue 報告。",
    result_type=HealReport,    # 錯型別直接報錯
)

@agent.tool_plain
def run_fix(action: str) -> str:
    return execute_fix(action)  # 註冊給模型選

result = agent.run_sync("Trino 節點 alert")
print(result.output.root_cause)    # 型別安全輸出
print(result.usage())             # token 用量
型別安全是最大賣點——輸出不符 schema 就失敗，錯誤不會默默往下流。

    tools=[query_logs],          # 給這個角色的工具
)
fixer = Agent(
    role="修復員",
    goal="執行修復並產出 issue 報告",
    backstory="擅長安全的自動修復與變更記錄",
)

t1 = Task(description="分析 Trino 節點 alert",
          expected_output="根因分析", agent=diagnoser)
t2 = Task(description="執行修復並驗證",
          expected_output="issue 報告", agent=fixer)

crew = Crew(agents=[diagnoser, fixer],
            tasks=[t1, t2],
            process=Process.sequential)  # 或 hierarchical
result = crew.kickoff()
角色分工寫在 agent 定義裡，任務描述是 agent 之間的合約——分工清楚，責任才清楚。
