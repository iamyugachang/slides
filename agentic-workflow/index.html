02PART 1 · 光譜與判準

LLM 讓自動化能處理事先列不完步驟的任務

ETL、CI/CD、排程早就在自動跑。LLM 新增的是：只給目標，也能邊做邊找下一步。

固定流程
程式先排好步驟
ETL · CI/CD · Airflow
＋ LLM
開放任務
「Trino 為什麼變慢？」
要查什麼不能先列完
→
兩種控制方式
Workflow：程式選
Agent：模型選

多做了什麼

OPEN-ENDED TASKS
  • 不必先寫完所有分支，只要先給目標
  • 模型可依查到的結果改變下一步

新增的代價

NEW PROBLEMS
  • 模型會出錯與繞路，結果必須驗證
  • 每一輪都花 token，重試也會增加成本
  • 路徑不固定，較難除錯與追查
步驟越難預先列出，越需要讓模型選下一步。

07NAV ④ · 目標、進度、工具

先定三件事：何時完成、記住什麼、能做什麼

01 · GOAL
何時算完成
完成條件必須能檢查，模型才能判斷繼續或停止。
例：測試通過且 PR 已建立
02 · STATE
目前進度與證據
保存已做的動作、結果、錯誤與中間產物。
例：alert、根因、人審、修復與驗證結果
03 · TOOLS
可以做的動作
工具說明、參數格式與權限，決定模型能做哪些動作。
例：查詢與部署使用不同權限
這三項決定 Agent 的目標、資訊與行動範圍。

08NAV ④ · 安全限制

安全限制要放在程式裡，不能只靠提示詞

04 · HOOKS
每步前後檢查
工具執行前檢查參數，執行後讀回結果，停止前做最後驗證。
例：送出前先顯示差異，等人確認
05 · POLICY
權限與人工確認
限制可用權限、資料範圍、預算；高風險動作由人確認。
例：查詢可自動執行；部署與刪除必須批准
06 · TRACE + EVAL
記錄過程並測試結果
Trace 記錄每一步；Eval 測試過程與最後結果。
例：檢查答案、工具使用與成本
07 · SANDBOX
隔離與回復
在可回復的環境執行不可信程式；失敗時能還原。
例：worktree、container、測試帳號、checkpoint
每個動作都要有權限、記錄、驗證與回復方式。

09NAV ④ · 常見錯誤

有副作用的動作要防重複；完成宣告要驗證

坑 1：重試可能重複執行

避免重複執行
  • Agent 會重試，同一動作可能執行兩次
  • 使用唯一操作編號；重試前先查狀態
  • 超時不代表失敗，重試前先讀回狀態

坑 2：模型說完成不算證據

獨立驗證
  • 模型可能誤判結果，或只完成一半
  • 重新查 API、資料庫、檔案或測試結果
  • 驗證失敗後再決定補救、還原或停止
提出動作
帶唯一操作編號
→
執行＋讀回
查真實系統狀態
→
更新 state
確認成功／補救／還原
寫入前防重複；完成後重新查一次。

13結論

開放任務先跑通；固定步驟再收回 Workflow

① 路徑已知
直接用程式或 n8n
步驟與分支都知道，直接寫 Workflow
② 路徑未知
先用 Agent 找到可行路徑
讓模型選工具與下一步，先完成目標
③ 找到固定部分
把重複步驟改成 Workflow
降低 token、增加穩定性；只保留必要的自主區段
未知部分交給 Agent；已知部分寫成 Workflow。

17附錄 03/06 · LANGGRAPH 程式碼

LangGraph：兩個案例都把人審寫成節點

案例 1 · Alert 自動修復
detect → diagnose → approve → heal
from langgraph.types import interrupt

class AlertState(TypedDict):
    alert: str
    cause: str
    approved: bool
    result: str

def approve(s):
    answer = interrupt({"cause": s["cause"]})
    return {"approved": answer == "approve"}

g = StateGraph(AlertState)
g.add_node("detect", detect)
g.add_node("diagnose", diagnose)
g.add_node("approve", approve)
g.add_node("heal", heal)
g.add_edge(START, "detect")
g.add_edge("detect", "diagnose")
g.add_edge("diagnose", "approve")
g.add_edge("approve", "heal")
案例 2 · Lakehouse 寫入
parse → route → execute → approve → submit
from langgraph.types import interrupt

class IngestState(TypedDict):
    workspace: str
    intent: str
    yaml: str
    approved: bool
    run_id: str

def approve_yaml(s):
    answer = interrupt({"yaml": s["yaml"]})
    return {"approved": answer == "approve"}

g = StateGraph(IngestState)
g.add_node("parse", parse)
g.add_node("route", route)
g.add_node("execute", execute)
g.add_node("approve", approve_yaml)
g.add_node("submit", submit)
g.add_edge(START, "parse")
g.add_edge("execute", "approve")
g.add_edge("approve", "submit")
interrupt() 保存目前進度並暫停；收到批准後，從同一個節點繼續。

Pydantic AI：用型別檢查 Agent 輸出

Agent
模型＋指示＋輸出欄位
@agent.tool_plain
把修復函式提供給模型
run_sync()

你寫：指示、工具、輸出欄位
框架處理：反覆執行、工具呼叫、格式驗證、用量
# pip install pydantic-ai
from pydantic import BaseModel
from pydantic_ai import Agent

class HealReport(BaseModel):   # 輸出型別
    root_cause: str
    actions: list[str]
    verified: bool

agent = Agent(
    "openai:gpt-4o",
    system_prompt="你是維運工程師：收到 alert 先診斷根因、執行修復、驗證，最後寫成 issue 報告。",
    result_type=HealReport,    # 錯型別直接報錯
)

@agent.tool_plain
def run_fix(action: str) -> str:
    return execute_fix(action)  # 註冊給模型選

result = agent.run_sync("Trino 節點 alert")
print(result.output.root_cause)    # 已檢查格式
輸出欄位或型別不符，就直接失敗，不往下執行。

# pip install crewai
from crewai import Agent, Task, Crew, Process

diagnoser = Agent(
    role="異常診斷員",
    goal="分析 alert 找出根因",
    tools=[query_logs],          # 給這個角色的工具
)
fixer = Agent(
    role="修復員",
    goal="執行修復並產出 issue 報告",
)

t1 = Task(description="分析 Trino 節點 alert",
          expected_output="根因分析", agent=diagnoser)
t2 = Task(description="執行修復並驗證",
          expected_output="issue 報告", agent=fixer)

crew = Crew(agents=[diagnoser, fixer],
            tasks=[t1, t2],
            process=Process.sequential)  # 或 hierarchical
result = crew.kickoff()
每個角色只拿需要的工具，上一個任務的結果交給下一個。
