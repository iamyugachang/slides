02PART 1 · 光譜與判準

任務自動化不是新東西——LLM 加入後多了一道光譜

「自動化」早就有了：ETL、CI/CD、排程、DAG。LLM 帶來的不是自動化本身，而是讓「不知道確切步驟」的任務也能自動化。

舊自動化
步驟寫死
ETL · CI/CD · Airflow
＋ LLM
自然語言任務
「幫我查 Trino 為什麼變慢」
步驟無法預先列完
→
光譜
Workflow ↔ Agent
固定路徑 ↔ 動態決策

解決的瓶頸

AUTOMATION 的邊界擴張
  • 過去要寫程式才能自動化的任務，現在一句話就能起頭
  • 中間的「不確定性」由模型補上，不用人先窮舉所有分支

仍沒解決

NEW PROBLEMS
  • 模型會出錯、繞路、胡謅——產出不能直接當真
  • 每跑一輪都在燒 token，失敗重試也燒
  • 執行路徑不固定 → 除錯與稽核變難
真正的問題不是「要不要自動化」，而是「自動化到什麼程度」。

模型負責 Decision

INTENT · TOOL · BRANCH · RETRY
  • 讀取目前 state 與可用工具
  • 選擇下一個 action，或判斷可以停止
  • CoT 是這次推論內部的思考，不是另一層 workflow

Harness 負責 Runtime

LOOP · STATE · TOOL DISPATCH · LIMITS
  • 註冊工具、保存狀態、執行 tool call
  • 套用權限、timeout、預算、重試與停止條件
  • Workflow 也能使用同一套 runtime；差別仍在 decision owner
不是「有 loop 就是 Agent」——要看每一輪的下一步是不是由模型根據 observation 決定。

模型能做的

PROPOSE

  • 提出「下一步想做什麼」
  • 根據錯誤改走別條路

07NAV ④ · 控制面（上）

Goal、State、Tools：先定義 Agent 的目的、記憶與能力

01 · GOAL
成功與停止條件
把「做完」寫成可驗證條件；模型每輪才能判斷繼續、換路或停止。
例：測試 exit 0＋PR 已建立，而不是「把程式改好」
02 · STATE
進度、證據與決策上下文
跨輪保存 observation、已採取 action、錯誤與中間產物；不是把所有歷史無限塞回 prompt。
例：alert、root cause、approval、fix result、verification
03 · TOOLS
能力與副作用邊界
工具粒度、description、schema、權限與副作用聲明，決定模型實際可採取哪些 action。
例：read-only query 與 deploy 必須拆成不同權限工具
關係Goal 決定何時停；State 決定目前知道什麼；Tools 決定下一步有哪些選項。
沒有這三個，Agent 不是自主——只是沒有目的地、沒有紀錄、卻拿著一串鑰匙亂試。

08NAV ④ · 控制面（下）

Hooks、Policy、Trace/Eval、Sandbox：讓自主不等於失控

04 · HOOKS
每步前後的攔截點
PreToolUse 檢查參數；PostToolUse 讀回結果；Stop 前做最後驗證。Hook 是 runtime 控制點，不是 Agent 類型。
例：submit 前產生 diff，等人確認再 resume
05 · POLICY
誰能做什麼、何時要批准
最小權限、workspace／tenant 範圍、成本預算與高風險 HITL，限制模型可選 action 的集合。
例：查詢自動放行；部署、刪除、權限變更強制批准
06 · TRACE + EVAL
看得到路徑，也驗得了結果
Trace 記錄每輪 decision、tool、token 與 observation；Eval 評估軌跡與最終 outcome。
例：不只看答案正確，也看是否繞路、誤用工具、成本失控
07 · SANDBOX
隔離、回復與故障邊界
把不可信 code、外部內容與副作用限制在可復原環境；失敗時能 rollback，而不是污染 production。
例：worktree／container／staging account／checkpoint
Production 的分水嶺不是模型更聰明，而是每個 action 都有邊界、證據與復原路徑。

09NAV ④ · 控制面實戰

兩個 production 致命坑：重複副作用、相信 self-report

坑 1：Retry 會把副作用再做一次

IDEMPOTENCY
  • Agent 遇錯會重試；同一個 action 可能刷卡、發信、建帳號兩次
  • 解法：idempotency key、先查後寫、明確標記不可 retry
  • Timeout 不代表動作沒成功——重試前要先讀回狀態

坑 2：「完成了」不是成功證據

INDEPENDENT VERIFICATION
  • 模型與子 Agent 可能誤判工具結果，或只完成一半
  • 解法：用另一條讀取路徑查 API／DB／檔案／測試結果
  • 驗證失敗要回到 state，決定補救、回復或停止
提出 action
帶 idempotency key
→
執行＋讀回
不信回傳文字，查真實系統狀態
→
更新 state
確認成功／補救／rollback
每個有副作用的 action，都假設它可能重複；每個完成宣告，都要求獨立證據。

10NAV ③ · 協作拓樸

Chain 管步驟間；Agent 管步驟內；Multi-Agent 管誰和誰協作

PROMPT CHAINING
Code 決定步驟間順序
每步是一個聚焦 prompt；中間結果可檢查、可替換模型、可只重跑失敗步驟。
A → B → CHECK → C
next step owner = code
AGENT INSIDE A STEP
模型決定該步怎麼完成
Chain 的 B 步可以是一個 Agent：它在受限工具集內搜尋、重試、觀察，再把結果交回下一步。
B: decide ↔ act ↔ observe
next action owner = model
MULTI-AGENT TOPOLOGY
定義交棒與協作關係
Supervisor＝中央派工；Handoff＝代理直接交棒；Teams＝固定角色；A2A＝跨系統互通協定。
SUPERVISOR · HANDOFF
TEAMS · A2A
Alert 案例外層用固定 chain：偵測 → 診斷 → 人審 → 修復；「診斷」步驟內可由 Supervisor 派多個專家並行調查，再合成 root cause。
這三種可以混搭；分類時仍回到同一題：這一段的下一步，究竟由 code、模型，還是另一個 Agent 決定？

12PART 4 · 模式與框架

框架都是預組好的 harness——選的是編排方式

LangGraph

圖結構 · CHECKPOINT · INTERRUPT
  • 流程畫成 node + edge；edge 可固定、可由 LLM 選
  • checkpoint 可 resume、interrupt 可人審中斷
  • 適合多步驟、要人介入的複雜流程

Pydantic AI

單 AGENT · TYPE-SAFE · 上手平緩
  • 輸出用 Pydantic 定義，錯型別直接報錯
  • 工具用 @agent.tool 註冊，最少的樣板
  • 適合「一個 agent + 幾個工具」的規模
CrewAI
角色分工：agent 有 role/goal/backstory，任務串成 crew
ADK（Google）
多 agent 編排、session 持久化、Gemini 生態
n8n
視覺化 workflow，LLM 只是其中一個節點
每個框架都給你：loop + 狀態 + 工具註冊 + 可觀測性——差別在怎麼編排、多重的抽象。

13結論

實務規則：從最不自主的開始，不夠再升級

① 可預測
純 code / n8n
步驟寫得死 → 最便宜、最好測，不需要框架
② 單一 agent
Pydantic AI 這類輕框架
一個 agent + 幾個工具自主跑 → 型別安全、樣板最少
③ 多步多 agent
LangGraph / CrewAI / ADK
要人審、要 resume、多角色協作 → 圖結構與編排
混合最常見：code 定骨架（幾個階段、順序），模型定細節（階段內自己決定）。跑久了發現步驟其實有規律，再把 agent 降級回 workflow。
一句話總結：模型負責想，你負責決定它能在什麼框架裡想。 下一步：附錄用同一個「Alert 自動修復」任務，看 LangGraph / Pydantic AI / CrewAI / n8n 的程式與架構。

# pip install langgraph
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):          # 共享狀態
    alert: str
    root_cause: str
    fix: str
    report: str

def detect(state):     # 節點 1：偵測 alert
    return {"alert": check_alerts()}
def diagnose(state):   # 節點 2：診斷根因
    return {"root_cause": llm("分析異常來源", state["alert"])}
def heal(state):      # 節點 3：修復＋報告
    fix = run_fix(state["root_cause"])
    return {"fix": fix,
            "report": llm("寫 issue 報告", fix)}

g = StateGraph(State)
g.add_node("detect", detect)
g.add_node("diagnose", diagnose)
g.add_node("heal", heal)
g.add_edge(START, "detect")
g.add_edge("detect", "diagnose")
g.add_edge("diagnose", "heal")
g.add_edge("heal", END)
app = g.compile()
print(app.invoke({})["report"])
固定 edge 是 workflow，edge 讓 LLM 選就是 agent——一個框架兩種模式都有。

18附錄 04/06 · PYDANTIC AI

Pydantic AI：單一 agent，輸出型別安全

Agent
model ＋ system_prompt ＋ result_type
@agent.tool_plain
run_fix —— 修復動作註冊
run_sync()
一次 agent loop，回傳 typed result
你寫：agent 定義、工具、輸出模型
框架給：整個 loop、工具註冊、輸出驗證、usage 統計
# pip install pydantic-ai
from pydantic import BaseModel
from pydantic_ai import Agent

class HealReport(BaseModel):   # 輸出型別
    root_cause: str
    actions: list[str]
    verified: bool

agent = Agent(
    "openai:gpt-4o",
    system_prompt="你是維運工程師：收到 alert 先診斷根因、執行修復、驗證，最後寫成 issue 報告。",
    result_type=HealReport,    # 錯型別直接報錯
)

@agent.tool_plain
def run_fix(action: str) -> str:
    return execute_fix(action)  # 註冊給模型選

result = agent.run_sync("Trino 節點 alert")
print(result.output.root_cause)    # 型別安全輸出
print(result.usage())             # token 用量
型別安全是最大賣點——輸出不符 schema 就失敗，錯誤不會默默往下流。

CrewAI：角色分工，任務串成 crew

Agent 診斷員
role / goal / backstory / tools
Task ①
分析 alert 找出根因
↓ sequential
Agent 修復員
role / goal / backstory

你寫：agent 角色＋task 描述
框架給：編排順序、任務間產出傳遞、kickoff 執行
# pip install crewai
from crewai import Agent, Task, Crew, Process

diagnoser = Agent(
    role="異常診斷員",
    goal="分析 alert 找出根因",
    backstory="資深維運工程師，熟悉 Airflow/Spark/Trino 生態",
    tools=[query_logs],          # 給這個角色的工具
)
fixer = Agent(
    role="修復員",
    goal="執行修復並產出 issue 報告",
    backstory="擅長安全的自動修復與變更記錄",
)

t1 = Task(description="分析 Trino 節點 alert",
          expected_output="根因分析", agent=diagnoser)
t2 = Task(description="執行修復並驗證",
          expected_output="issue 報告", agent=fixer)

crew = Crew(agents=[diagnoser, fixer],
            tasks=[t1, t2],
            process=Process.sequential)  # 或 hierarchical
result = crew.kickoff()
角色分工寫在 agent 定義裡，任務描述是 agent 之間的合約——分工清楚，責任才清楚。
