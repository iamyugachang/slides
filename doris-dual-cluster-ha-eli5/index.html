1我們在解什麼問題

想像我們開了一間很重要的餐廳（一座 Doris 資料倉儲），公司很多人每天都靠它吃飯（查資料、看報表）。現在的擔心是：如果整間店停電、淹水、瓦斯氣爆——整座掛掉——怎麼辦？

解法方向大家都同意：開第二間分店（第二座獨立的 Doris cluster）。任何一間整間出事，客人改去另一間，生意照做。

真正的難題只有一個：

怎麼讓兩間店隨時都有「一樣的菜」？而且一間店倒了又修好之後，怎麼把落後的菜補回來？

這篇就是在講：我們比了四種做法，為什麼選了「兩個廚房各自煮」。

2先翻譯幾個名詞

Doris 叢集一間餐廳（廚房＋出餐口）。我們要開兩間。
Kafka一條中央訂單輸送帶。所有「今天要進什麼菜」的單子都先上這條帶子，而且帶子會保留最近 N 天的單子，可以回頭重看。我們家所有資料 100% 都走這條帶子進來——這件事後面會變成關鍵優勢。
Spark job備料員：盯著輸送帶，把單子上的菜做出來、放進廚房。
Query / JDBC客人點餐。程式用同一支電話號碼打進來。
RPO出事時最多允許弄丟幾分鐘的菜。越接近 0 越好。
RTO出事後多久能恢復營業（客人切到另一間店要多久）。
Failover / Failback切過去／修好之後補齊、切回來。

3做法一：請一個抄寫員（CCR）不採用

最直覺的做法：A 店正常煮，請一個抄寫員站在 A 店廚房裡，把每道菜的做法即時抄一份、送去 B 店照做。這個抄寫員就是官方的 CCR 工具。

聽起來很好，為什麼不用？三個理由：

  • 抄寫員的公司實質上收掉了。這不是傳言：官方網站在 2026 年 7 月把 CCR 的說明書整批下架，工具的程式碼庫四個多月沒人更新、只剩兩個維護者。要繼續用，等於我們得把抄寫員接回家自己養——兩萬多行程式碼，而且每次 Doris 改版都要自己重新驗證他還抄得對不對，永遠跟版，沒有盡頭。
  • 抄寫永遠慢半拍。正常時慢幾秒到半分鐘；某些狀況（A 店內部換班）會觸發「整本重抄」，慢到以小時計。A 店在「慢半拍」的瞬間倒下，那半拍的菜就是丟了——RPO 永遠不是零。
  • 只會單向抄。A 店修好之後想歸隊？沒有「反著抄回來」這功能，只能整間店從頭重抄一遍，而且官方連標準流程文件都沒有。

結論：不讓抄寫員當正職。但留他一個打工缺——極端狀況下要「整間店重建」時，叫來抄一次就走（詳見第 8 節）。

4做法二：一個備料員同時餵兩家店出局

第二個想法：讓現在這位備料員（同一個 Spark job）每拿到一張單子，就同時把菜送進 A 店和 B 店。

問題出在「同時」這兩個字：

  • 一家卡住，兩家一起卡。B 店出菜口塞住，備料員整個人卡在那裡，連 A 店都跟著斷貨。兩家店的命運被綁在同一個人身上——這跟我們要的「互相獨立」恰好相反。
  • 送一半失敗最麻煩。A 店收到了、B 店沒收到，這張單子已經翻過去了——兩家店從此差一道菜，而且沒有機制把它補齊。
  • 順帶的，這做法還要求所有客人改用一套特殊的點餐方式（改所有 client 程式），侵入性最大。

業界也踩過：京東用類似做法雙寫兩套系統，公開承認「只能最終一致、業務複雜度高」。雙份資料是對的，但位置放錯了——正確位置在下一節。

5做法三：兩家店各派備料員，看同一條輸送帶我們的選擇

換個思路。訂單輸送帶（Kafka）本來就在那裡、本來就保留最近 N 天的所有單子。那就：

A 店派自己的備料員、B 店也派自己的備料員，兩個人各自盯著同一條輸送帶，各自把完整的菜煮進自己的廚房。兩人互不認識、互不等待、各自記各自看到第幾張單。

這樣一來：

  • A 店整間停電？B 店根本不受影響——它的備料員一直都在做完整的菜。進貨這一側什麼都不用切換，弄丟的菜趨近於零（RPO ≈ 0）。要做的只剩把客人引導去 B 店（下面第 7 節）。
  • A 店修好了？它的備料員回來上班，從自己上次記到的那張單子接著往下補，補完就追平了。不用求任何人、不用整間重抄。
  • 沒有任何要「自己養」的黑盒子。多出來的只是第二位備料員（複製現有的 job）、一個總機（proxy）、跟每天對帳的例行工作——全是我們本來就會的常規工程。

還有一件很幸運的事：我們家的資料 100% 只從這條輸送帶進來，沒有任何人會繞過帶子直接塞菜進廚房。「靠輸送帶重放」這招因此完全成立——很多團隊做不到這個方案，正是因為他們有一堆旁門進貨路徑，我們剛好沒有。

6這個選擇的三個代價要先付

天下沒有白吃的 HA。這方案成立有三個前提，講清楚：

① 每道菜都要有「菜名編號」——最重要的一條

備料員有時會重做單子（當機重開後，會從上次記錄的地方重看幾張，這是正常的）。重做時會發生什麼，取決於菜有沒有編號：

表的類型比喻重做一次會怎樣
Unique Key（MoW）每道菜有編號，重做＝換掉原本那盤✅ 沒事，結果一樣
Duplicate自助餐檯，做一盤放一盤❌ 變兩盤，資料重複
Aggregate（SUM）往同一鍋裡加料❌ 加兩次，數字灌水

我們查證過：Spark 寫 Doris 的工具官方自己承認沒辦法保證「絕不重做」（他們 2026 年 7 月才在修這問題，修好的版本還沒發布）。所以解法不是等工具，而是讓所有的菜都有編號——把資料表收斂成 Unique Key 模型。現況有多少表沒編號，就是這個方案最大的改造工程，也是第一個要盤點的事。

② 輸送帶的單子要留得夠久

B 店停業三天後回來，得從帶子上把三天的單子重看一遍。所以帶子保留單子的天數（Kafka retention）必須大於「一間店最久可能停業多久＋補菜要多久」。預設 7 天太短，我們建議拉到 14–30 天，代價是儲存成本。

③ 每天要對帳，而且對帳不是配件

兩個備料員各煮各的，沒有任何機制自動保證兩家菜一樣——萬一其中一人拿到的食譜版本舊了，他會安安靜靜地一直煮錯，不會有警報。唯一的防線是每天對帳：兩家店逐區（partition）數盤子、抽樣核對內容（hash），不一樣就告警。這是方案的一部分，不是可有可無的加分項。

7客人怎麼無感切換

所有客人只記一支總機號碼（VIP），不直接打給任何一間店。總機（HAProxy）平時把電話轉去 A 店；A 店出事，就改轉 B 店——客人的電話簿一個字都不用改。

  • 總機怎麼知道店死了？三層檢查：電話打不打得通（連線）→ 實際點一道菜試試（真實 SQL）→ 廚房還有沒有在出新菜（資料新鮮度）。光看「電話通」是不夠的——店可能電話通但廚房已經停了。
  • 總機自己掛了怎麼辦？總機也有兩台，互為備援（keepalived），一台倒另一台幾秒內接手同一個號碼。
  • 誰決定切換？半自動：系統告警，人確認後按下切換。只有「A 店徹底全滅」這種黑白分明的情況才自動切。判斷權集中在一個地方，避免兩台總機各判各的吵起來。

要注意的一個體感：切到 B 店的瞬間，客人可能吃到比剛才舊幾秒鐘的菜（兩家店的進度本來就差幾秒）。做報表沒差，但這點要先跟使用單位講好。

8誠實說：這方案防什麼、不防什麼

情境結果
一間店整間掛掉（停電、硬體、機房事故）✅ 防——另一間本來就在營業，切總機即可
掛掉的店修好歸隊✅ 防——從輸送帶接著補，補完對帳確認
輸送帶（Kafka）本身掛掉⚠️ 兩家店同時停止進新菜（既有的菜照常賣）。Kafka 從此升格為一級要害，它自己的備援等級要重新體檢
食譜本身寫錯（程式 bug）❌ 不防——兩家店用同一份食譜，錯就一起錯。救法是從輸送帶重做那段期間的菜；未來有條件再加「定期快照」當第二道防線
兩家店同時出事❌ 服務中斷。緩解方式是讓兩家店在實體上離遠一點（不同機櫃/電力）

另外保留一個備案：如果一間店慘到連輸送帶的單子都不夠補（停業超過保留天數），就把第 3 節那位抄寫員（CCR）臨時叫來抄一次，抄完就請他回家——不讓他變成正職依賴。

9接下來要做的事

方案要落地，第一步不是架設備，而是回答一個問題：

我們現在有多少菜是沒有編號的？（多少表不是 Unique Key 模型）

這個盤點（PoC 清單裡的 P01）直接決定方案的 go / no-go 和改造規模。後面接著做的：故意把備料員弄當機驗證「重做不變多」、演練停機 24 小時要補多久（反推輸送帶要留幾天）、把總機的三層檢查做出來實測切換秒數、對帳工具跑滿一週看誤報率。

還有四件事要請業務方拍板：正式的 RPO/RTO 目標、切換瞬間「舊幾秒」能不能接受、兩間店實體上要離多遠、沒編號的菜要花多少力氣補編號。

論點 A：「CCR 不能長期依賴」——官方公開訊號

  • apache/doris-website PR #4018 — 2026-07-29 官方把 CCR 文件從 3.x / 4.x / dev 文件樹整批移除（92 個檔案），無任何說明。
  • selectdb/ccr-syncer — 自己點進去看 commit 歷史：最後提交 2026-04、2026 年僅 5 個 commit、從未發過 GitHub Release。
  • SelectDB Enterprise 文件 — 商業版仍完整保留 CCR 手冊：開源側淡出、商業側承接的直接佐證。

論點 B：CCR 的實務面貌——社群實戰分享

  • 錢大媽：CCR 實現 Doris 讀寫分離 — 最完整的生產案例，同步 3–4 秒；但屬 2024 官方仍維護時期、且用途是讀寫分離而非整座 failover。
  • 跨年夜資料中心宕機：Doris CCR 容災實戰 — 社群分享，附全量 1TB 約 6 分鐘、增量延遲約 33 秒的數據。
  • CCR 跨叢集同步實操 — 完整部署步驟與版本下限、thrift 調參等實際負擔，可感受維運成本。
  • apache/doris #63269 — 上游 FE 切主觸發整庫 full sync；ccr-syncer #654 — 表級同步靜默忽略 DROP TABLE（open bug）。

論點 C：「上游雙寫兩座叢集」業界有人做——也有教訓

  • 京東 ClickHouse 高可用實踐 — 3,000 台規模：「离线通过 Spark 同时向两个集群写入，实时通过 Flink 消费双写」，公開承認只能最終一致、切換分鐘級。
  • 攜程：700 億資料量 ClickHouse 高可用架構 — 刻意不用內建複製，改「数据独立、多写、互不干扰」＋定時 job 核對一致性——與我們方案同構、長期可運維的直接證據。

論點 D：「Spark 寫 Doris 保證不了 exactly-once」——官方自己說的

  • doris-spark-connector PR #364 — 官方原文：「stream load write path is not exactly-once across a client-side retry」；修復至今未發版。
  • issue #205 — 2PC txn 超時被清、commit 失敗不拋例外的無聲丟數案例。
  • 對照組：Flink Connector 如何做到 Exactly-Once（Stream Load 綁 Checkpoint + 2PC）——正好反襯 Spark 側缺的就是這套機制。

論點 E：「Unique Key MoW 撐得起冪等重放」

  • 全新 Unique Key（MoW）設計與實現 — Delete Bitmap 原理與 SSB 實測（部分場景近 30 倍查詢提升）。
  • 工商信息查詢平台實踐 — 生產環境開 MoW：單點查詢 0.45s→0.22s，日均 10 億條、3,000 QPS 規模背書。

論點 F：「HAProxy + keepalived 切 MySQL 協議」是成熟做法

  • Doris 官方 Load Balancing 文件 — 官方自己給了 HAProxy / Nginx / ProxySQL 三種範例。
  • Doris FE 負載均衡實戰 — 直接針對 Doris FE 的 HAProxy + Keepalived + VIP 配置與切換測試。
  • MySQL + HAProxy + Keepalived 高可用 — 「DB 掛觸發漂移」與「HAProxy 掛觸發漂移」兩種模式的完整配置與驗證。

論點 G：「Kafka retention + 重放」是正規的災難恢復手段

  • Kafka 叢集容災策略 — 系統性整理 retention、offset 管理與故障演練。
  • 如何安全地重放 Kafka 訊息 — 依「消費者是否冪等」選擇重放策略——正是我們表模型前提的出處邏輯。

論點 H：「對帳」是雙活架構的標準配套

  • 數據一致性——對帳工程實踐 — 明細對帳定位問題、總數對帳兜底的兩層設計。
  • 金融級對帳系統設計 — 對帳表結構、核對 SQL 與自動補償告警的完整示範。
