鐵律 1

SCHEDULER DOES NOT RUN TASKS
  • 排程器不執行任何任務——它只把 Task Instance 標成 queued，交給 executor。
  • 執行永遠發生在 worker／task executor 那一側。

鐵律 2

DB IS THE ONLY TRUTH
  • 所有元件彼此不直接講話，只對 Metadata DB 讀寫。
  • UI 看到什麼、scheduler 決定什麼，都來自同一份 DB 狀態。

鐵律 3

EXECUTOR 是排程器的設定
  • executor 不是獨立服務，是 scheduler 的「交辦策略」：本機跑？丟佇列？開 pod？
  • 換 executor 不換排程邏輯——同一個 scheduler loop，換交辦方式。
按下 Trigger 之後你按下的不是「開始執行」，是「請 scheduler 建一個 manual run」——建好之後，仍走同一套排程與執行流程（CH6 劇場）。
往後每一章都只回答同一組問題：這一層在哪裡？由誰負責？狀態寫在哪張表？答得出這三題，就沒有看不懂的 Airflow 行為。

06CH1 · 檔案 → 計畫：DAG 檔案只是 Python

第一個底層事實：解析 = 真的 import 你的檔案，top-level code 會執行

「解析」時發生的事

DAG FILE IS EXECUTED AS PYTHON
# 這個檔案每次被 parse 都會真的跑：
print("loading my_dag...")　← 會印在 parse 日誌
cfg = fetch_config_from_api()　← 每次 parse 都打一次 API！
with DAG(dag_id="my_dag", schedule="@daily") as dag:
　 t1 = BashOperator(...)　# 建 operator 也是在 top-level

對你們平台最 relevant 的例子

DYNAMIC DAG = TOP-LEVEL 迴圈
yaml = read_yaml("jobs/order_etl.yaml")
for job in yaml["jobs"]:
　 with DAG(dag_id=job["dag_id"], ...):
　   tasks = build_from_spec(job)
# 一個檔案 → N 個 DAG，全在 import 時展開

你們「YAML → 動態 DAG」的寫法，本質就是把建藍圖的邏輯放在 top-level——每多一個 job，就多一次 parse 負擔。

常見坑在 top-level 連 DB／打 API／讀大檔：這些 code 會隨每一輪解析重複執行（2.x 約每 30 秒～5 分鐘一輪，3.x 由 DAG Processor 持續解析）。想拿 runtime 設定，請用 Variable 或環境變數（且不要在 top-level 讀 Variable——那也會打 DB）。
把 top-level 當作「建藍圖的時間」：它只該描述結構，不該做任何「執行期才需要」的事。解析頻率 × top-level 成本 = 你排程器的隱形稅。

07CH1 · 檔案 → 計畫：解析管線

解析管線：你的 .py 不會離開解析器——進 DB 的是結構副本


（2.x：dag_dir_list_interval） safe mode：只掃疑似含 DAG 的檔 解析子程序 import 每個檔案在隔離 process 執行
（掛住會 timeout 被殺，2.x 約 50 秒） import error → 該檔 DAG 從排程消失 收集 DAG 物件 dagbag 找出所有 DAG 實例
→ 序列化成純結構 JSON code 本身不會被搬進排程邏輯 寫入 Metadata DB serialized_dag（結構）＋dag_code（原文，供 UI 顯示） 3.x：連同 bundle 版本一起記錄 從此 scheduler／API／UI 都讀 DB 裡的「計畫副本」，不再碰你的 .py

為什麼要隔離解析？

  • 某個檔案 import 卡住／寫爛，不能拖垮整個排程器。
  • 2.x 用 dag file processor 池處理；3.x 獨立成 DAG Processor 元件，可單獨擴。
  • 解析失敗的檔案：DAG 停用（deactivated），歷史 run 資料不刪，修好放回去就復活。

「改了 code 多久生效？」的答案

  • 不是秒級：要等下一輪掃描 + 重新解析 + 覆寫 DB。
  • 2.x：掃描週期（預設約 300 秒級）＋同一檔案最短間隔（約 30 秒級）。
  • 3.x：DAG Processor 有自己一輪輪的解析節奏；bundle 更新後也會重新解析。
  • 所以「改了沒反應」先查 parse 日誌，別急著怪 UI。
改 code 的生效時間軸存檔 → 下一輪掃描發現變更 → 重新解析 → 覆寫 serialized 結構 → 之後建出的新 run 才用新計畫——最快也是「分鐘級」，不是秒級。
排程器、UI、API 看到的永遠是DB 裡的序列化副本——這就是 worker 能不在同一台機器、scheduler 能多台並存的前提。

08CH1 · 檔案 → 計畫：序列化 DAG

serialized DAG 長什麼樣：只留「結構與參數」，程式邏輯留在檔案裡

DB 裡的計畫（serialized）

WHAT SCHEDULER ACTUALLY READS
{
　 "dag_id": "order_etl",
　 "schedule": "0 1 * * *",
　 "tasks": [
　   {"task_id": "extract", "operator": "SparkSubmitOperator",
　    "retries": 3, "pool": "spark_pool"},
　   {"task_id": "load_iceberg", ...}
　 ],
　 "edges": [["extract","load_iceberg"]],
　 "timeout": ..., "timetable": ...
}

scheduler 排程時不需要執行你的 code——它讀這份 JSON 就知道：有哪些 task、誰先誰後、重試幾次、用哪個 pool。

那 code 在哪？

CODE STAYS WITH THE FILE / BUNDLE
  • 你的 .py 原始碼：留在 dags folder／bundle 裡，UI 的 Code 分頁是從 dag_code 表讀給你看的。
  • 執行時（CH5 會講）：worker 反而要真的 import 你的檔案——因為 operator 參數、hook 設定都在 code 裡。
  • 3.x DAG 版本化：每個 run 記錄產生它的計畫版本；重跑舊 run 用的是「當時的版本」，不是現在 folder 裡的 code。
一個心智實驗把「排程」想成看菜單點餐（serialized JSON = 菜單），把「執行」想成廚房照食譜做菜（code = 食譜）。點餐的人不需要會做菜——這就是 scheduler 不需要你的 code 的原因；但廚師（worker）需要食譜。
兩份東西要分清楚：計畫（serialized，給排程用）與 code（留在 bundle，給執行用）。混在一起，就會誤解「為什麼 worker 也要同步 DAG 檔案」。

09CH1 · 檔案 → 計畫 3.x DAG 版本化

3.x 的版本化：run 綁定「當時的計畫版本」，舊 run 重跑不會偷換新 code

DAG versioning（3.x）

RUN 記住它出生時的世界
  • 每次解析到 DAG 內容變更，就產生一個新版本（存 code snapshot 與結構）。
  • 每個 DagRun 記錄產生它的 dag_version。
  • 從 UI 重跑一個舊 run → 用舊版本的 code 執行，不是現在 folder 裡的 code。
  • 好處：重跑「上週失敗的 run」結果可預期；壞處：修 bug 後要重跑，記得重 trigger 或開新的 backfill，別重跑舊 run 以為會用到新 code。

2.x 的對照：重跑舊 run = 用「現在」的 code

IMPORT-TIME SNAPSHOT IS NOT A THING
  • 2.x 沒有版本化：重跑一個舊 DagRun，worker 會重新 import 你目前 folder 的 DAG 檔。
  • 所以「上週的 operator 參數」可能已經不是上週的樣子——debug 歷史 run 時這是最常踩的坑。
  • 實務補救：重跑前確認 git 版本、或用 backfill 補新 run 而非重跑舊 run。
Bundles（3.x）bundle 是「code 的運輸單位」：預設是本地 folder，也可以是 git repo／zip。DAG Processor 從 bundle 解析，worker 也從同一 bundle 拿正確版本的檔案——這就是「worker 怎麼跟 scheduler 同步 code」在 3.x 的官方答案。
你們平台的版本化案例YAML／DAG 檔一改，3.x 就產生新 DAG 版本；還掛著的舊 run 與「重跑舊 run」都用舊定義——「改了卻沒生效」有時是版本綁定，不是 bug。
升級到 3.x 後第一個要改的習慣：「重跑舊 run」的語意變了——它現在是「用舊版 code 重跑」，不是「用新版 code 補救」。

10CH1 · 檔案 → 計畫：解析失敗會怎樣

DAG 突然不見？先查解析，不是先查刪除

import error

FILE RAISES / BROKEN SYNTAX
  • 該檔解析失敗 → 檔裡的 DAG 不會被寫進 DB（新 DAG 看不到）。
  • 原本就在的 DAG：scheduler 掃描時「找不到它」→ 標 deactivated（停用），但歷史 run 全保留。
  • 檔案修好放回去 → 自動重新啟用，歷史可見。

解析掛死

IMPORT NEVER RETURNS
  • 檔案 import 卡住（連不上的 DB、無窮迴圈）→ 有 timeout 會殺掉解析子程序（2.x 常見約 50 秒級），不拖垮整個系統。
  • 找出兇手：看 parse 日誌（2.x 在 scheduler 日誌；3.x 在 DAG Processor 日誌），通常會指出是哪個檔。

控制掃描範圍

SAFE MODE / .airflowignore
  • 預設 safe mode：只 import「內容疑似含 dag 關鍵字」的檔案，省下大量無關檔案的 parse 成本。
  • .airflowignore：像 .gitignore 一樣排除檔案／目錄（3.x 預設 glob 語法）。
  • CLI 檢查：airflow dags list-import-errors 直接列出所有壞檔。
# 診斷順序（DAG 不見時）
airflow dags list-import-errors　# 1. 有 import 錯誤嗎？
airflow dags list --output table　　# 2. 還在但 paused？
# 3. 都不在 → 看 parse 日誌有沒有 timeout／檔案有沒有被 .airflowignore 排除
壞掉的 DAG 不會炸系統，它只會「安靜消失」——所以平台要有「某個該存在的 dag_id 消失了」的監控，而不是等 user 發現。

→ 一輪可能要 數分鐘 才跑完

解析成本來自：top-level code（CH1）、import 的套件、動態 DAG 的迴圈展開、檔案數量。你們的 YAML 平台檔案數 = 直接決定這數字。

2.x vs 3.x 的關鍵差異

PARSE 在不在排程的 critical path 上
  • 2.x：解析在 scheduler 程序內跑。解析塞車 → 排程心跳跟著變慢 → 全平台 run 都延遲。解析就是排程的 critical path。
  • 3.x：DAG Processor 獨立元件。解析再慢也不直接拖排程心跳；但「新 code 產生新 run」仍要等解析完成。
  • 兩版都有效的優化：top-level 輕量化、只 import 需要的套件、檔案數適度拆分、避免每檔 import 巨型 library。
設計含義（動態 DAG 平台）「user 建立 job → 多久能看到並排程」的 SLA，不是 executor 決定，是解析吞吐決定。容量規劃請以「檔案數 × 每檔 parse 時間 ÷ 解析併發數」估，並監控 parse 時長趨勢。
改 code 之後的等待，是「等下一輪解析把新計畫寫進 DB」——不是系統壞了。先量 parse 週期，再決定要不要告警。

12CH2 · 時間模型

Airflow 的 schedule 不是「幾點執行」——它在定義「每一批資料屬於哪一段時間」

所以 run 的名字要這樣讀

  • 一個 run 的 logical date = 它處理的資料從幾點開始。
  • 它實際開始執行的時間，通常在區間結束後（cron 排程的慣例）。
  • 2.3 起叫 logical date；2.2 以前叫 execution_date——舊名誤導了整整一代人以為那是執行時間。

誰決定 run 的日期序列？

TIMETABLE
  • timetable = 一個會「產生下一個 logical date」的物件：cron、timedelta、自訂規則都只是它的實作。
  • 它同時告訴 Airflow 每個 run 的資料區間長什麼樣。
  • 搞懂「timetable 產日期、scheduler 照日期建 run」，時間模型就通了。
看到任何 run 日期，先問：這是「資料的期間」還是「執行的時間」？——Airflow 預設的答案是前者，多數誤解來自這裡。

「9/4 的 run」為什麼 9/5 才跑？因為它處理的是 9/4 的資料

15CH2 · 時間模型：catchup 與 backfill

catchup 一次補 N 個 run：補跑沒問題，沒管車流才會出事

預設：不自動補跑

DEFAULT = 只排最新一個 interval

  • scheduler 停機 3 天復活？只補最新一顆，不會把 3 天空窗全部一次倒出來。
  • 開 catchup=True：scheduler 會把 start_date 以來所有缺的 interval 都建成 run。

backfill：你要的「補跑」指令

　 --start-date 2026-08-01 --end-date 2026-08-31

18CH3 · 排程迴圈：多 scheduler 的互斥

為什麼三台 scheduler 不會把任務發三次？DB 列鎖：一次只有一台能進 critical section

鎖的是「資源」，不是「任務」

  • 為什麼鎖 pool 列而不是鎖 task？因為 concurrency 限制是全域資源：要保證「總共只發 N 個」，就必須讓 enqueue 動作本身互斥。
  • 多台 scheduler 各自跑 loop，只有拿到鎖的那台能在該輪發任務；發完釋放，下一台接手。
  • 結果：加 scheduler = 吞吐變大，但任何時刻的併發量仍被同一個上限管住。

2.x 時代的 HA 提醒

  • 2.x 也可以跑多 scheduler，但解析也在 scheduler 裡：每台都在 parse，DB 層有去重機制，可是資源浪費與鎖競爭都更高。
  • 3.x 把解析拆出去後，多 scheduler 才真正「各司其職」地水平擴展。
  • 共用一個 Metadata DB 是前提——scheduler 各自帶自己的 SQLite 這種事永遠不要做。
「不會重複執行」的保證來自 DB 鎖 + 狀態檢查，不是來自「只部署一台」——這是 Airflow 敢讓你水平擴展的底氣。

21CH3 · scheduled 與 queued 的分界

scheduled → queued 中間有四道閘：全過才「交辦」，任一不過就原地等

scheduled 卡住 ≠ 依賴沒滿足

  • scheduled 的定義是「依賴（上游＋trigger rule）已過，該跑了」。
  • 它還停著 = 卡在資源閘：pool 滿、平台併發滿、或該 DAG 的 task 併發滿。
  • UI 上它會一直灰著；點進去看 pool／併發數字才知道在等哪一閘。

queued 卡住 ≠ 資源問題

  • queued = executor 已經收件，在等執行端（worker／pod）來領。
  • 它卡住通常是：celery worker 全掛、broker 不通、K8s 排不到 pod。
  • 所以診斷口訣：卡 scheduled 看資源，卡 queued 看執行端——方向完全不同（CH6 有檢查表）。
default_pool 的 128 個 slot 常被無腦吃滿不宣告 pool = 全部擠進 default_pool。多團隊平台請依「任務類型／團隊／資源重量」建立命名 pool，再配 priority_weight 排優先序。
scheduled 與 queued 的分界 = 「資源閘有沒有過」。先講出這個分界，你就能把一半的「為什麼沒跑」自己診斷掉。

22CH3 · 心跳與殭屍

zombie：狀態還寫 running，但執行它的程序已經死了——由 scheduler 負責收屍

怎麼發生的

RUNNING 但沒有心跳
  • task 在 worker 執行時會定期心跳，把 last heartbeat 時間寫進 DB。
  • worker 被 OOM kill、機器重啟、網路斷、DB 連線斷——心跳就停了。
  • DB 裡那顆 TI 還停在 running：它沒人執行了，但沒人說它死了。

誰來收屍、怎麼收

SCHEDULER 的巡邏工作
  • scheduler 定期掃：running 的 TI 中，心跳逾時（超過 task instance heartbeat timeout）→ 判定 zombie。
  • 處置：標 failed；還有 retry 次數 → 進 up_for_retry 重排（CH5）。
  • 3.x 官方文件明列：worker OOMKilled、liveness 失敗、機器掛點都是典型成因。
心跳是「執行端還活著」的唯一證明。worker 死了不會自己說——所以判死權在 scheduler 手上，而判死需要時間（timeout），這就是「明明掛了卻要等幾分鐘才失敗」的原因。

25CH4 · LocalExecutor 深看

LocalExecutor：scheduler 在「自己這台機器」開程序跑任務

運作方式

SUBPROCESS PER SLOT
  • TI 進 queued 後，executor 在 scheduler 所在主機上 spawn 程序執行（3.x 文件用語：「tasks run locally within the scheduler process」）。
  • 同時跑的數量由 parallelism 控制：它就是「這台機器開幾個執行槽」。
  • 優點：零額外元件、延遲低、好 debug——3.x 的預設選擇。

代價與界線

SHARES RESOURCES WITH SCHEDULER
  • 任務跟排程器搶同一台機器的 CPU／記憶體：一個 Spark driver 就能把排程心跳拖垮。
  • 2.x 的 LocalExecutor 也曾是「小生產」選項，但任務一重就該換 Celery／K8s。
  • 判斷句：「你的任務吃多少資源、跟排程器共宿安不安全」——不安全就別用 Local。
給你們的提醒Spark／重量級 ETL 不適合 LocalExecutor：driver 與 scheduler 共宿 = 一次 OOM 拖垮整台排程。評估 executor 時先問「任務的資源天花板」，再問「要不要排程器陪葬」。
什麼時候該升級 executor訊號：任務開始長時間佔用 CPU／記憶體、需要獨立依賴、scheduler 主機開始 OOM——任何「資源重」的跡象出現，就往 Celery／K8s 移動。
Local = 簡單但共宿。它的「低延遲」是用「與排程器同生共死」換來的——任務愈重，愈該往佇列／container 走。

26CH4 · CeleryExecutor 深看

CeleryExecutor：scheduler 把任務丟進佇列，worker 自己來領——兩邊從此脫鉤

要記得的三件事

  • worker 也是 Airflow 程式：它要能拿到 DAG code（2.x：同步 dags folder；3.x：從 bundle 取正確版本）才能建 operator。
  • worker 上的 concurrency（每台同時跑幾個 task）與 scheduler 的 queued 量是兩套數字，瓶頸在小的那個。
  • 「task 卡 queued」= broker 有訊息但沒有 worker 領，或 worker concurrency 已滿。

掛掉怎麼辦

  • worker 死：正在跑的 TI 心跳斷 → 走 zombie 流程（CH3），自動 retry 或失敗。
  • 佇列訊息本身有 ack 機制，但 Airflow 的可靠度最終靠「DB 狀態＋zombie 收拾」，不靠佇列保證。
  • 重啟 worker 後：卡 queued 的任務會被領走繼續跑（前提 TI 沒被判死）。
Celery 的分工哲學：scheduler 只負責「送訊息」，worker 只負責「領訊息跑」——中間隔著一個 broker，兩邊的生死、擴展互不影響。這是中大型 Airflow 最常見的架構。

27CH4 · KubernetesExecutor 深看

KubernetesExecutor：每個 task 一個 pod——用「開機成本」換「絕對隔離」

為什麼值得

  • 隔離最徹底：每個 task 有自己的 container、依賴、系統套件——兩個 task 打架不會互相污染（noisy neighbor 問題消失）。
  • 擴展交給叢集：任務爆量 = pod 變多，不用養常駐 worker。
  • 執行環境跟著任務走：某個 task 需要特殊 JDK／GPU driver，用它的 image 就好。

代價

  • 延遲高：每顆 task 都要等 pod 排程＋image 啟動——秒級到分鐘級。
  • 短 task 海（幾百顆 10 秒級）會讓 overhead 吃掉大半時間，通常不合算。
  • 要管 k8s 叢集容量與 pod 配額；「卡 queued」在這裡多一個原因：叢集排不出 pod。
executor 光譜的兩端：Local 省事但共宿，K8s 隔離但每個 task 都要付開機成本。中間的 Celery 是多數「任務多但環境一致」團隊的甜蜜點；3.x 還能混用。

28CH4 · 資源池與死結

Pool：給「會搶同一批資源的任務」限量——限量沒設計好就會死結

Pool 語意

SLOT = 可同時執行的額度
  • task 宣告 pool="spark_pool" → 只有 pool 有空 slot 才會被 enqueue（CH3 閘門）。
  • 用途：限制某類任務的併發——例如 Spark 任務總共只能 4 個同時跑，避免打爆叢集。
  • 沒指定就吃 default_pool（2.x 預設 128 slot）。
  • slot 在「queued→running」期間被佔用；deferrable task 在 deferred 期間不佔 worker slot（這是它省資源的關鍵，CH5 詳述）。

經典死結（真會發生）

互相等對方釋放 slot
  • 情境：pool A 的 task1 等 pool B 的 task2 完成；但 task2 也卡著等 pool A 的 slot——兩個 pool 都滿，誰也動不了。
  • 另一種：sensor／長等待任務佔住 slot 不放，把 pool 塞滿，後面真正要跑的排不進來。
  • 防呆：pool 大小 ≥ 該階段想跑的併發；等待型任務（sensor）別跟重任務共用 pool，或改用 deferrable。
診斷線索一大片 task 全部卡 scheduled 且都指著同一個 pool → 檢查 pool 使用率與「誰在裡面等誰」。解除方法：調大 pool、清掉卡住的 sensor、或把等待型任務移出 pool。
Pool 是「併發承諾」：你承諾某類任務最多 N 個同時跑，就得保證 N 個 slot 不會被「等別人」的任務佔死。限量要配「誰在等誰」的設計一起看。

30CH5 · Task 執行契約

一顆 task 的執行契約：獨立程序、獨立環境、只靠參數與外部系統溝通

執行時，實際發生什麼（2.x）

AIRFLOW TASKS RUN …
# worker 收到任務後，本質上是跑：
airflow tasks run <dag_id> <task_id> <run_id>
# 在 worker 機器上、獨立於 scheduler 的 process
  • worker 先 import 你的 DAG 檔重建 operator（參數都在 code 裡），再呼叫 operator.execute(context)。
  • context 帶上 run 資訊：logical date、params、ti 等——你的 task 就是「一個被呼叫的 Python 函式」。

3.x 的變化（對你幾乎無感）

TASK SDK 時代
  • 3.x 任務用 Task SDK 執行與回報狀態：經 API server／state store，不必直連 Metadata DB。
  • 對 DAG 作者：還是寫 operator、還是 execute()；「任務是獨立程序」的契約不變。
  • 真正有感的是 infra：worker／task executor 可以更自由地分散部署。
為什麼要「獨立程序」① 掛掉只死一顆 task（zombie 機制可重試）。② 資源可以隔離（K8s pod）。③ 可以 kill 而不傷 scheduler。④ 重試 = 重新再開一個程序跑一次——Airflow 不幫你記「跑到一半的狀態」，任務要自己設計成可重跑。
把 task 想成「每次從零開始的獨立程式」：它不知道上一顆 task 的記憶體，只知道 XCom、外部系統與參數。所有跨 task 的狀態，都必須經過「能重跑也安全」的通道。

31CH5 · 從 queued 到 running 的完整路徑

queued → running 的六站：每一站換一個「主人」


section 標記＋交辦 ② executor 收件 依類型：本機 / 佇列
/ k8s API ③ 執行端接手 worker 領取（celery）
/ pod 啟動（k8s） ④ 載入 code import DAG 檔、重建
operator（2.x 程序） ⑤ running＋心跳 execute() 開跑，
心跳定期寫 DB ⑥ 完成回寫 success / failed 寫回
DB，run 繼續下一步 2.x 細節：worker 內 LocalTaskJob → 另 spawn「airflow tasks run」子程序執行；3.x 把執行側抽象成 TaskExecutor／task SDK，六站的語意相同

這一頁記什麼

  • 每一站都有「主人」：①scheduler ②executor ③worker/pod ④執行程序 ⑤執行程序 ⑥執行程序＋scheduler 收尾。
  • 卡在哪一站，就看該站主人還活不活躍——診斷 = 定位站別（CH6 檢查表直接對應）。

為什麼 worker 也要有 DAG code

  • ④的意義：operator 的參數在 import 時才成形（bash_command、Spark 設定都是 Python 物件）。
  • 所以 2.x worker 要同步 dags folder；3.x 由 bundle 提供「正確版本」的檔（CH1）。
  • 執行端 import 失敗 → task 在 worker 端就壞——不是 scheduler 的錯。
站在除錯角度重看六站卡 queued → 檢查②③站（executor 收件、執行端接手）；顯示 running 但不動 → 查⑤站的心跳與 zombie 判定。六站就是你的診斷地圖。
「task 從 queued 變 running」不是一步，是六站接力。下次看 log 從 queued 到 running 之間發生什麼，就是在看③④兩站的主人表演。

32CH5 · 失敗與重試

重試 = 整顆重新執行：Airflow 的重試不是 resume，是 re-run

重試參數（default_args 常見組合）

  • retries=N：最多重試幾次（UI 的 try number 從 1 起算）。
  • retry_delay：兩次嘗試間隔多久；retry_exponential_backoff=True 會指數退避。
  • 每次嘗試都是全新程序、全新執行：寫入一半的資料不會自動清——task 要自己冪等。

誰在什麼時候做什麼

  • 「失敗」由執行程序判定（exception／非零 exit code），狀態與 on_failure_callback 都在執行端處理。
  • 「何時重試」由 scheduler 看 delay 是否到期——所以 up_for_retry 會「等一陣子」才動。
  • 3.x 有 Resumable Tasks 方向（可中斷續跑），但多數 operator 的語意仍是「整顆重跑」。
調 retry 的務實建議暫時性失敗（連線、叢集滿）→ retries=2–3＋exponential backoff 很夠；程式 bug 重試不會好——配 on_failure_callback 發告警，比無限重試更早被發現。
設計任務時先問：「這顆 task 重跑兩次會不會出事？」——Airflow 的重試保證的是「會再試」，不是「不會重複」。冪等是資料工程師自己的責任。

33CH5 · 執行環境在哪裡

task 執行的環境是 worker 的環境——不是 scheduler 的，更不是你的 laptop

執行端需要「重現」哪些事

  • Python 套件：operator import 的 library 要在 worker 上裝好（2.x 最常見的「scheduler 機有、worker 機沒有」悲劇）。
  • 系統工具／binary：bash operator 呼叫的 CLI、JDK、Spark client……
  • DAG code 本身（CH5 ④站）；Connections／Variables 在執行當下才由 hook 解析——不是 import 時。
  • 權限：worker 的 service account／OS user 能碰到的資源，才是 task 能碰到的。

三個版本時代的解法

從「同步 folder」到「bundle」到「per-task image」
  • 2.x：worker 與 scheduler 共用同一份 dags folder（git-sync／volume）＋同一份 requirements——環境一致性靠部署紀律。
  • 3.x：bundle 提供正確版本的 code；環境一致性仍靠 image／依賴管理。
  • 3.x K8s 路線：每顆 task 可以指定不同 image——環境跟著任務走，最徹底。
最貴的誤解「我在 scheduler 機器上 pip install 成功了，為什麼 task 還壞？」——因為 task 不跑在 scheduler 上。任何執行期依賴，都要以「執行端環境」為準驗證；要嘛統一部署，要嘛用 container 把環境釘死。
把「執行端環境」當成一台獨立的機器來管理：它的套件、權限、code 版本都獨立於 scheduler。環境漂移造成的 task 失敗，code review 永遠看不出來。

34CH5 · Sensor 為什麼貴、deferrable 為什麼省

「等條件」的任務別佔著 worker：deferrable task 把等待外包給 Triggerer


self.defer(trigger=…) 自願讓出 slot deferred TI 暫存、trigger 交給
Triggerer（asyncio） 不佔 worker slot、不佔執行資源 註冊 trigger Triggerer（事件迴圈） 一個 process 同時等幾百上千個 trigger 時間到／檔案出現／API 完成 → 發事件 事件 → scheduler 把 TI 重新 queued → worker 再跑一小段驗證→ success 對照：普通 sensor（poke 模式） 整段等待期間都佔著一顆 worker slot——sleep／poll 燒機器 100 顆 sensor 等 1 小時 = 100 個 slot 被「等待」佔走

省多少？算給你看

100 顆 sensor、各等 1 小時
poke 模式：佔 100 個 worker slot 一整小時
deferrable：只佔 1 個 triggerer（容量約數千）
＋偶爾喚醒的短暫 slot

「等待」的資源成本從「一台 worker 機器」降到「一個 asyncio 事件」。

使用要點

  • operator 要支援（sensor 的 mode="reschedule"、或 deferrable=True／自訂 Trigger 類）。
  • deferred 期間不吃 worker slot；trigger 條件滿足由 Triggerer 通知 scheduler 重新排。
  • 平台要跑 triggerer 元件（可多台水平擴展）；沒部署 triggerer 就沒有 deferrable。
  • 3.x 的 HITL（awaiting_input）是另一條路：不吃 worker、也不用 triggerer，由 scheduler 管。
凡是「等外部條件」的任務（等檔案、等 API、等時間窗），都該想辦法不佔 worker slot——deferrable 是 Airflow 對「等待型任務吃掉執行容量」的標準答案。

35CH5 · 跨 task 傳資料

XCom 是「便利貼」，不是「貨櫃」：跨 task 傳資料要選對通道

XCom 怎麼運作

PUSH / PULL，存在 DB
  • task A 執行中 push 值 → 存在 DB 的 xcom 表（key + value + task 出處）；task B 用 ti.xcom_pull 取回。
  • TaskFlow：return value 自動 push，函式參數自動 pull——語法糖包著同一套 XCom。
  • 換 backend 可存別處；2.9+ 有 object storage XCom backend（大檔改存遠端）。

經典誤用與正解

  • ❌ 把 Spark DataFrame／大 list 塞進 XCom：序列化成本＋DB 膨脹＋每顆下游 task 都整包搬一次。
  • ❌ mapped task 每顆都 pull 大 XCom：N 顆 × 大物件 = 爆炸。
  • ✅ 正確姿勢：task 寫結果到外部系統（Iceberg 表／S3 路徑），XCom 只傳「路徑／版本／row count」這種小 meta。
  • 原則：XCom 傳「指標與指路」，資料本體走資料系統。
對照你們的 Spark 世界Spark job 的產出 = 寫 Iceberg 表；下游 XCom 只該拿「table / snapshot_id / count」。把「資料」留在資料層，把「描述」放在 XCom——管線才會快且可追。
傳資料前問三題多大？（KB 級才考慮 XCom）／誰要？（一個下游還是 N 個）／重跑安全嗎？（先清再寫）——答案指向「外部系統＋meta 傳遞」。
XCom 的命名已經說明一切：com = communication（溝通），不是 storage（儲存）。跨 task 的大資料，永遠走資料系統；XCom 只當便利貼。

36CH5 · 動態展開與分組

mapping 是「一份定義、N 顆執行」；TaskGroup 只是收納盒，不是子管線

Dynamic Task Mapping

@task
def process(item): ...

process.expand(items=["a","b","c"])
# 排程時展開成 3 顆 mapped TI（map_index 0..2）
  • 展開發生在 排程階段（scheduler 看到 input 後），不是 import 時——input 可以來自上游 XCom。
  • 每顆 mapped TI 獨立狀態、獨立重試：第 2 顆失敗不影響第 1、3 顆（3.x 的 retry policy 也 per-TI）。
  • 與「動態 DAG」不同：動態 DAG 在 import 時決定有幾個 DAG；mapping 決定一顆 task 有幾個實例。

TaskGroup：純 UI 語意

FOLDING FOR HUMANS
  • TaskGroup 只是把一群 task 在 UI 上摺疊／分組，執行時全部攤平在同一個 DAG graph 裡。
  • 沒有獨立狀態、沒有自己的 retry、不是子 DAG／subprocess——別用「它是不是一組」來猜行為。
  • 真需要「一組一起重跑／一起跳過」的語意？那是 task 層級的 trigger rule 與 retry 設計，不是 TaskGroup。
命名即語意mapped TI 在 UI 顯示為 task_id [0] / [1] / …；若看到某顆 task 有幾百個 map_index，先問「input 多大」——展開量 = 排程器＋DB 的瞬間負擔（有 max_map_length 之類上限保護）。
mapping 把「重複結構」變成「平行執行」；TaskGroup 把「畫面」變整齊。一個是執行語意，一個是排版工具——混用就會誤判行為。

42CH6 · 三個「假性卡住」劇本

三個經典劇本：系統沒壞，但設計讓它永遠跑不完

劇本 1：重試無窮迴圈

RETRIES 設很大 + 每次很快失敗
  • 重試會「等 delay 再試」，但若失敗原因固定（code bug），就是慢速空轉。
  • run 拖到 dagrun_timeout 才被判 failed——中間看起來像卡住。
  • 修法：retries 給合理值；先在本機重現失敗再上線；失敗要告警不是無限重試。

劇本 2：等待型任務堵住資源

SENSOR 佔 SLOT / POOL 被等滿
  • poke 模式 sensor、或一堆 sensor 共用 pool → slot 被「等待」佔走，真任務排不進。
  • 修法：sensor 用 deferrable／reschedule（CH5）；等待型任務與重任務分 pool；pool 大小對齊真實併發。

劇本 3：backlog 與正式 run 搶資源

CATCHUP / BACKFILL 海量湧入
  • 一次補 60 天 → run 排隊與「今天的正式 run」搶同一批 slot，今天該跑的反而延後。
  • 修法：backfill 分段小批、避開高鋒期、或臨時調低它的優先權（priority）。
  • 口訣：補跑是重放，要當正式流量管理（CH2）。
共同特徵三個劇本都不是「單一故障」，而是「某個設計把時間或資源吃掉」。診斷時若沒看到 crash、沒看到錯誤 log，就往「資源被誰佔走、時間被誰拖住」想。
防呆三原則等待型任務不佔正式 slot（deferrable）／pool 大小對齊真實併發／重試設上限——三個劇本都是違反這三條的結果。
假性卡住的三個元兇：無限重試、等待佔資源、補跑搶流量。記住它們，很多「平台卡住」其實是「平台照設計空轉」。

46CH7 · 不管幾版都成立的三條鐵律

收束成全書三句話：版本會換，這三條不會換

① 想與做分離

SCHEDULE ≠ EXECUTE

排程器只決定「誰該跑、何時該跑」，執行永遠發生在 executor／worker 側。看到任何「排程器在執行任務」的說法——先懷疑，那是錯的。

② DB 是唯一真相

EVERYTHING TALKS THROUGH THE DB

所有元件不直接互 call，狀態只寫 Metadata DB。HA、多 scheduler、換 executor 全都靠這個前提。狀態對不上 = 先查 DB 再看 code。

③ 執行端環境獨立

TASKS RUN SOMEWHERE ELSE

task 跑在 worker／pod 的環境：套件、權限、code 版本都獨立於 scheduler。「在我機器／scheduler 機器上好的」都不算數。

90 分密碼：闔上這份簡報，能把 CH6 的「15 分鐘劇場」從 run 建立講到 success、並說出每一站的主人——你就真的懂了。
如果只記得兩張圖§04 全系統角色圖（誰在哪）＋§38 劇場表（誰在何時做什麼）——其餘所有細節都是這兩張的 zoom-in。
帶新人把 §38 劇場講一遍，就是最好的 Airflow onboarding——30 分鐘講完底層。
如果只能帶走一行：Airflow = 一台以 DB 為唯一真相、把「決定」與「執行」徹底分離的狀態機——其餘都是這一句的展開。
