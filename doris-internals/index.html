解解決的瓶頸

OLAP 最貴的三件事：掃描量（列存＋索引）、平行度（MPP＋分桶）、寫讀互卡（LSM 順寫＋版本快照）。Doris 用一套系統把三者一次解決。

限仍沒解決

複雜度沒有消失，而是轉移到建表與查詢設計：key 順序、分桶鍵、寫入頻率，都會變成執行期的快或慢。這份 deck 就是讓你把「帳」算回來。

例例子

同一張事實表，WHERE user_id = ? 可以差到千倍——只差在排序鍵有沒有把 user_id 放前面。看懂 03–10 頁後，你就能自己解釋這種差距。

TAKEAWAY閱讀路線：骨架 (03–05) → 資料怎麼切與放 (06–07) → 磁碟上的長相與加速 (08–11) → 寫入路徑 (12–16) → 查詢引擎 (17–21) → 副本與維運 (22–23) → 收尾回顧 (24) → 名詞速查 (25)。
01 · 骨架03

Doris 只有兩種程式：FE 管「想」，BE 管「做」

一顆大腦 + 一群手腳
FE · Frontend（大腦）
對外講 MySQL 協定（預設 9030）——你以為在連 MySQL，其實是連 Doris
收 SQL：解析 → 綁定 → 最佳化，產出「分片執行藍圖」
管 全部元資料：庫表 schema、tablet 分佈、副本狀態
協調寫入 transaction、排程修復 / 平衡
⇄
BE · Backend（手腳 × N）
真正儲存資料：列存檔、索引、compaction 都在這裡
執行查詢：掃描 tablet、join、聚合、排序（向量化 + pipeline）
接收寫入資料流並落地成檔案（HTTP 8030）
每秒向 FE 心跳回報：活著嗎？哪些 tablet 落後？
BE 越多 → 儲存與算力越分散（水平擴充）；FE 通常 1–5 台即可

解解決的瓶頸

把「誰來規劃」與「誰來執行／存資料」分開：規劃集中一處（好做全域最佳化與一致性），執行與資料打散到所有機器（拿平行度）。

限仍沒解決

FE 是單點協調者：所有 SQL 都要經過它解析與規劃，併發再高也會在 FE 排隊——所以 Doris 的做法是「FE 只規劃不碰資料」＋可以加多台 FE 分攤。

例例子

你 mysql -h fe_host -P 9030 下查詢，Doris 傳回的「Query OK, 10 rows」其實經歷了：FE 規劃 → 派給 8 台 BE 平行算 → coordinator 彙整。EXPLAIN 給你的就是 FE 那張藍圖。

TAKEAWAY查詢慢或寫入卡關時，先分清楚：是 FE 層（規劃／元資料／協調）的問題，還是 BE 層（掃描／執行／寫檔）的問題——兩邊的看診方式完全不同。

FE 的元資料是「要同步的帳本」：多台 FE 靠 BDBJE 扮演同一顆大腦

解解決的瓶頸

元資料是叢集的單一事實來源：誰都不能亂改。讓多台 FE 共用同一份「帳本日誌」（Berkeley DB Java Edition 複製），leader 掛了 follower 能接手，資料庫不腦死。

限仍沒解決

帳本要多數派確認才安全——2 台 FE 掛 1 台就無法選舉（50% 不是多數）。所以最少要 3 台 FE（或 1+1 observer）；元資料量其實很小，瓶頸不在容量而在「同步延遲」。

例例子

你 CREATE TABLE 之所以要等一拍，不是磁碟慢——是這筆 DDL 正在寫入帳本並等 Follower 確認。改欄位、加 partition 全都走同一條路，所以「DDL 突然變慢」常是 BDBJE 同步出問題。

TAKEAWAYFE 叢集＝一本會自我修復的分散式帳本：資料的「位置與結構」永遠一致；而真正的大資料本體，一筆都不放在 FE。

解解決的瓶頸

查詢最佳化需要全域視野（統計資訊、所有 tablet 分佈、並行 join 的成本），集中在一顆大腦做，比每個 worker 各自亂猜便宜得多——這是 MPP 資料庫的共同設計。

限仍沒解決

CBO 靠統計資訊吃飯：沒有 ANALYZE / 統計過期時它會選錯 join 順序或誤判要不要 shuffle。資料工程師能做的：定期更新統計、必要時用 /*+ hint */ 或調 session 變數。

例例子

EXPLAIN SELECT ... 看到 Fragment 0 / Fragment 1…：Fragment 0 通常是彙總端（coordinator 所在），其餘是分散到 BE 的掃描與 join 段——「查詢有幾個 Fragment」就是你這條 SQL 的平行架構。

TAKEAWAYSQL 不是被「執行」的，是被編譯成一張分工藍圖再派工的——所以同樣的 SQL，tablet 分佈不同、統計不同，跑法可以完全不一樣。

partition = 剪枝單位：WHERE dt 命中哪幾區就只掃那幾區；過期資料整區 DROP，比 DELETE 快幾個量級
bucket = hash(key) % 固定數：把資料打散成可平行、可分散的片段；同一 partition 內 bucket 數固定（可 AUTO 自動選）
每個 bucket = 1 個 tablet：最小複製單位（3 副本）＋最小平衡單位（可在 BE 間搬移）
bucket 數 = 平行度上限：查詢掃一個 partition 最多開 bucket 數個掃描任務

解解決的瓶頸

一次掃全表太貴。四層切法讓系統能「只碰需要的、其餘平行掃」：partition 砍掉時間範圍，bucket 把剩下的切成可分散的平行任務，tablet 讓副本與搬移有最小單位。

限仍沒解決

切太細有代價：tablet 數量暴增會拖垮元資料與排程；切太粗則單 tablet 過大、平行度不足、compaction 變慢。bucket 數與資料量要一起長——這就是 AUTO bucket 存在的理由。

例例子

DISTRIBUTED BY HASH(user_id) BUCKETS 16：同 key 的資料永遠進同一個 bucket → 之後「兩張都按 user_id 分桶」的表 join 可以不用搬資料（見 20 頁 colocate）。選錯分桶鍵 = 這張表永遠無緣本地 join。

TAKEAWAY建表時的三個決定——partition 鍵、分桶鍵、bucket 數——分別決定了剪枝、join 本地化與平行度的天花板，而且事後都很難改。

tablet 是一本「版本化小日誌」：每次寫入追加一筆 rowset，查詢時合併著讀

單一 tablet 內部：rowset 依版本排列，visible 以上的才給查詢讀

visible version = 3：查詢只看到 v1–v3；v4 還在寫，任何查詢都看不見（見 14 頁）
compaction 會把 v1–v3 併成一個大 rowset（見 16 頁），但「版本語意」不變
rowset = 一次寫入的資料批次（含 1~N 個檔案），帶著自己的版本區間 [v-x, v-y]
同 key 可能散在不同 rowset：Aggregate 要跨 rowset 聚合、Unique 要去重——所以查詢要「多路合併」
寫入 = 順序 append 新 rowset，不碰舊檔：這就是 LSM 精神，寫入快的根源
rowset 越多 → 合併路數越多：compaction score 越高，查詢越慢（見 16 頁）

解解決的瓶頸

把「隨機更新」變成「順序追加」：新資料永遠寫新檔，不跟舊檔競爭鎖與磁碟位置——這是 Doris 能撐高吞吐寫入、又不卡查詢的根本。

限仍沒解決

追加的債要還：檔案只增不減，查詢合併路數變多、重複 key 佔空間。解法是背景 compaction 重新整理——但它本身吃 CPU / IO，尖峰寫入時可能排隊。

例例子

每 5 分鐘一個 Stream Load，一天下來一個 tablet 內有近 300 個小 rowset。若查詢變慢，SHOW TABLET ... 看 compaction score——數字越高，代表「查詢時要合併越多路」，該讓 compaction 追上。

TAKEAWAYDoris 的 tablet = LSM 風格的小日誌：寫入永遠順序追加（快），讀取要跨 rowset 合併（所以需要索引與 compaction 保持它快）。

每欄獨立編碼 + 壓縮（例：LZ4 / ZSTD）；同欄資料放一起，壓縮率與掃描效率都高
只讀需要的欄：查 3 欄就只載那 3 欄的 page——寬表也能當窄表讀
page 是 I/O 與解壓單位：欄內再切頁，配合 zonemap 可以只解「有機會命中的那幾頁」
append-only 排序寫入：同一 segment 內照排序鍵寫，所以能建「前綴索引」（下一頁）
列存的代價：要「一整列」的 OLTP 點查／逐列更新不是它的場——Doris 靠索引與主鍵模型補，不靠列存

解解決的瓶頸

分析查詢常只取 5% 的欄、掃 90% 的列。列存讓磁碟 I/O 從「讀整列」變成「讀需要的欄」，配合同欄連續存放，壓縮率也比列式高——這是 OLAP 快的第一層。

限仍沒解決

列存對「整列進出」的操作不友善：主鍵更新、逐列 delete 都要額外機制（delete bitmap、delete rowset）來補，這些機制最後都靠 compaction 清乾淨。

例例子

SELECT 100 欄 vs SELECT 3 欄的差異在 OLAP 是「要載多少磁碟資料」的問題：前者可能差 10 倍 I/O。寬表別怕——怕的是 SELECT * 成習慣。

TAKEAWAY「列存」= 把磁碟 I/O 從「以列為單位」改成「以欄為單位」——所以少 SELECT *、欄位越少越省，這不是習慣問題，是實打實的 IOPS 問題。
03 · 磁碟上的長相09

第一個加速器：排序鍵 + 前綴索引——你的 key 順序就是查詢的跳躍表

segment 內資料照排序鍵排 → 每 N 列一個 Data Block → 每 block 記一筆「前綴」索引項（≤36 bytes）
排序鍵 user_id, age, message（示意，鍵值遞增）
行 1: user_id=100 · age=20 · …
行 2: user_id=100 · age=25 · …
行 3: user_id=100 · age=30 · …
┈ block 邊界 ┈
行 N: user_id=100 · age=45 · …
同 key 連續相鄰 → 找 user_id=100 AND age≥20 只需跳進一個 block 連續掃
前綴索引項 = block 第一行的排序列前 36 bytes，全表只此一組、全量常駐記憶體
命中條件：WHERE 要從最左排序列開始連續命中（user_id → user_id+age → …）
跳過 user_id 直接 WHERE age=25 → 用不上（要等值才可能走倒排/其他索引）
VARCHAR 會提前截斷：遇到 VARCHAR 就停（即便未滿 36B），後面的排序列進不了前綴索引
定位到 block 後，再靠頁層級索引（ordinal index）跳到正確 page

解解決的瓶頸

沒有索引時，找一段範圍要掃整個 segment。排序鍵讓資料「物理上按查詢條件排好」，前綴索引在記憶體裡二分定位 block——等值與範圍查詢都從「掃全檔」變成「跳進一小段」。

限仍沒解決

一張表只有一組前綴索引（排序鍵唯一），而且必須「最左連續命中」。常用過濾條件不在排序鍵前綴上 → 這組加速器直接失靈——只能靠倒排索引或物化視圖補第二組。

例例子

官方例子：排序鍵 user_id + age + message，前綴共 32B（沒截斷）；WHERE user_id=… AND age=20 命中；只下 WHERE age=20 就落空。看 Profile 的 RowsKeyRangeFiltered 驗證。

TAKEAWAY建表把 key 排前面不是語法習慣——排序鍵 = 唯一一組自動前綴索引，最常過濾的欄放最左、VARCHAR 別擋路，這是你第一個免費的查詢加速器。
03 · 磁碟上的長相10

其餘三兄弟：Zonemap、BloomFilter、倒排索引——前綴沒命中時誰來救

每種「過濾型條件」該找誰（加速矩陣）
你的 WHERE主角運作方式Profile 驗證指標
範圍 / 大於小於 / 前綴等值Zonemap（每頁 min/max）先比頁的 min/max，整頁不可能命中就整頁跳過，不解壓RowsZoneMapFiltered
非前綴欄的等值 / INBloomFilter（可建在指定欄）先問「這頁／這 segment 有沒有可能含這值」——說沒有就一定沒有，省掉逐列比對RowsBloomFilterFiltered
非前綴等值 / 全文 / LIKE倒排索引（可建多組）欄值建倒排清單：值 → 文件／行號；等值、範圍、字串搜尋都行RowsInvertedIndexFiltered

解解決的瓶頸

OLAP 掃描最怕「整頁載進來才知道沒用」。三兄弟都是過濾下推：在解壓與讀頁之前先用便宜的中繼資料（min/max、bitmap、倒排表）把不可能命中的資料塊扔掉。

限仍沒解決

都是「機率性省事」：選擇性太低（命中 50% 資料）時 zonemap/bloom 幾乎不省；BloomFilter 有誤判可能（說有其實沒有 → 多掃一點，不會錯結果）；每個索引都吃寫入成本與空間，建太多寫入會痛。

例例子

明細表常按 event_time 範圍查 → zonemap 自動跳頁；偶爾按 invoice_no 等值查但它在排序鍵後面 → 對它建 BloomFilter（或倒排）；要 LIKE '%關鍵字%' 才需要倒排索引。

TAKEAWAY加速矩陣一句話：前綴索引管排序鍵前綴，zonemap 免費管範圍，BloomFilter 管「不存在」，倒排管「非前綴的等值與搜尋」——先確認條件落在誰的射程，再決定要不要加索引。
03 · 磁碟上的長相11

資料模型不是「選爽的」：Dup / Agg / Unique 決定了去重與更新發生在哪一層

同 key 重複寫入時，三種模型的行為（都是「排序鍵 = key 欄」）
Duplicate
重複就保留，不去重；明細／日誌用
讀寫都最便宜：沒合併負擔；排序鍵只當索引用
Aggregate
同 key 用聚合函式合併（SUM/MAX/MIN/REPLACE…）
跨 rowset 讀取時也要邊合併邊讀；預聚合結果可能不是你要的維度 → 通常要建「明細 + 匯總」兩張
Unique（主鍵模型）
同 key 以「最新」為準；維度／狀態表用
Merge-on-Write（3.x 預設）：寫入當下查主鍵索引，舊版本直接在 delete bitmap 標刪除 → 讀取不用現場去重

解解決的瓶頸

把「去重與更新」這件 OLAP 最麻煩的事，用「資料模型」在儲存層制度化：Aggregate 讓部分聚合沉到檔案層，Unique MOW 讓「讀到的就是最新」不用查詢時現場比對千百個版本。

限仍沒解決

MOW 把讀的麻煩轉成寫的麻煩：每行要查主鍵索引、要寫 delete bitmap → 寫放大、記憶體吃緊（大主鍵表要靠索引落到磁碟）；Aggregate 的 REPLACE 等函式選錯，合併出來的數字會錯。

例例子

訂單明細（只 append）→ Duplicate；每日各店匯總 → Aggregate(SUM)；會員／庫存狀態（會被 update）→ Unique。把「明細」放 Unique 表＝用主鍵索引換一張永遠不更新的表，白白付寫放大。

TAKEAWAY選模型＝選「誰來付去重的錢」：Duplicate 最便宜但重複留著；Aggregate 把聚合沉進儲存；Unique MOW 用寫放大換讀取純淨——高頻更新、大主鍵、高寫入三者不可能全都要。
04 · 寫入路徑12

一次 Stream Load 的完整旅程：先寫記憶體、再落不可見檔、最後 publish 一次讓全部可見

以「curl 送 CSV 給 stream load」為例
① 你送 HTTP PUT

③ 資料進 BE
每個 bucket 對應一個 tablet writer，收進各自 memtable（記憶體）

解解決的瓶頸

寫入被設計成「記憶體累積 → 順序寫大檔 → 一次生效」：不在磁碟上做隨機小寫入，所以能撐高吞吐；且 ④ 之前全部 BE 平行進行，瓶頸只在最慢那台。

限仍沒解決

寫入是「全有或全無」：任一 tablet 的任一副本失敗就整體失敗；且 ⑥ publish 是全域協調點——tablet 數極多時 publish 本身要花時間。小批次灌太頻繁 → 開銷被 transaction 吃光（解法：group commit，見 13 頁）。

例例子

1 秒 1 筆的小 stream load 會把效能打趴——每筆都是一次完整 transaction（FE 協調、多副本確認、publish）。Doris 把這攤事設計給「一次一大包」，不是給「逐筆」用的。

TAKEAWAY寫入路徑的關鍵字是「批次 + 一次生效」：memtable 吸收、順序落盤、publish 統一開閘。資料工程師的任務是餵大包、別餵碎屑。
04 · 寫入路徑13

所有寫入口殊途同歸：差別只在「誰把資料搬到 BE」，之後走同一條引擎

五種常見寫入 → 同一條 transaction + tablet writer + publish 管線
入口誰搬資料 / 特性何時用
Stream Loadclient 直接 HTTP 餵 BE，同步等結果，靠 label 冪等重試離線批次／程式內送檔，最大宗
Routine Load常駐任務：FE 派 task 給 BE，BE 直接當 Kafka consumer，自動提交 offsetKafka → Doris 近即時管道

解解決的瓶頸

不管資料從哪來，「進 Doris 之後的品質保證」只有一套：transaction、多副本、publish 可見性全部一致。入口多但心智模型只有一個，維運與除錯成本因此很低。

限仍沒解決

每個入口有自己的「搬運工」要顧：Routine Load 的 task 掛了要自動重啟（offset 落在哪）、CDC 端到端 exactly-once 需要來源端配合、小批次進 routine load 一樣會製造大量小 rowset。

例例子

大量小批次（每 30 秒幾百列）→ 開啟 group commit：多個小 load 的資料在 BE 合併成一批才 publish，transaction 數量與小 rowset 都大幅下降——把小寫入「攢成大包」是官方推薦姿勢。

TAKEAWAY選入口只看一件事：你的資料源與時效性適合哪個搬運工。進了管線之後，label / transaction / publish 的規則對所有入口一視同仁。
04 · 寫入路徑14

為什麼「load 還沒結束就查不到」？——因為查詢永遠讀一個已發布的版本快照

讀寫隔離：寫入方在「publish 線」之後，查詢方在線之前（快照隔離）
寫入方： memtable 累積中→ rowset 已落盤（不可見）→ ★ publish→ 查詢可見
publish 前後各一秒啟動的兩條查詢：前者看不到、後者看得到——沒有「看到一半」的中間態
讀者拿到的是「當下最大已 publish 版本」的快照，rowset 只增不減 → 讀取永遠一致
publish 是 FE 的全域動作：一個 label 的 rowset 要在所有 tablet 一起生效，不會這張 tablet 有、那張沒有
失敗的 load：未 publish 的 rowset 變成 garbage，由背景清理回收
代價：publish 需要「所有副本都準備好」→ 最慢副本拖住整批；而查詢會 hold 舊版本直到跑完（版本不會立刻被 compaction 吃掉）

解解決的瓶頸

OLAP 同時有「高頻寫」與「長查詢」，最怕彼此看到一半。版本發布制讓寫入像「換頁」：一次換一整頁，讀者要嘛看舊頁要嘛看新頁，永遠一致——連 MVCC 的鎖都省了。

限仍沒解決

版本機制讓「剛剛寫入立刻讀到」有天然延遲（要等 publish），也讓「極高頻小批次」的代價很高；另外長查詢會釘住舊版本，擋住後續 compaction 的清理範圍。

例例子

Stream Load 回傳 OK 的瞬間查詢就讀得到——因為 OK 代表 publish 完成。若看到「PUBLISH_TIMEOUT」類錯誤，表示 tablet 太多或副本太慢，不是資料壞掉，重試同 label 即可。

TAKEAWAY「寫完立刻查不到」不是 latency bug，是交易設計：publish 前全世界看不見，publish 後全世界同時看見——這就是 Doris 不用鎖也能讀寫並行的秘密。
04 · 寫入路徑15

DELETE / UPDATE 的真實成本：Doris 不原地改，只「記一筆不要了」——清償在 compaction

delete 的一生：標記 → 查詢過濾 → compaction 才物理消失
你下 DELETE
WHERE 範圍（不是逐列改檔）
→
產生「delete 標記」
Duplicate/Agg：只記刪除謂詞的 rowset；Unique MOW：在 delete bitmap 標掉那些 key 的舊版本
→
之後每次查詢
掃描時套用標記：該濾的照濾（MOW 甚至讀取時直接跳過被標的行）
→
Compaction 清償
合併 rowset 時才把被刪資料真正從檔案移除、空間還給磁碟
UPDATE = 標記舊的 + 寫入新的（Unique 表兩步都做）

解解決的瓶頸

維持 LSM「永不原地改檔」的承諾：刪除也走 append（記標記），寫入路徑不會因為刪改而變慢或鎖表。對「維度值會變」的資料，這比整表重寫便宜太多。

限仍沒解決

被刪資料在 compaction 前仍然佔空間、且查詢要過濾它；delete 標記若分散成幾萬個小片段，還會拖慢掃描與壓縮。習慣性「每分鐘 DELETE 幾列」會讓 tablet 永遠清不乾淨。

例例子

「刪除上個月某渠道資料」→ 直接 DROP PARTITION 或整 partition 重寫，秒級完成；「逐筆刪幾筆」→ DELETE + 讓 compaction 追上；「每秒刪一堆」→ 這是 OLTP 行為，Doris 會一直背著墓碑。

TAKEAWAY在 Doris 裡 DELETE 是「標記死亡、緩慢安葬」：物理刪除要等 compaction。能用 partition 級別解決的刪除，就別用列級 DELETE 解決。
04 · 寫入路徑16

Compaction：Doris 的「資源回收 + 合併同類項」——查詢變慢先看它的 Score

兩個階段分工：Cumulative 收拾小檔，Base 偶爾跟大檔大合併（每 10 輪 1 次）
v1-3 base v4 v5 v6 v7 → 9 成時間
▼ cumulative：把小 rowset 併成中等檔（也順帶清 delete）
v1-3 base v4-7 已併 → 累積到夠大
▼ base：把 boundary 之前的全部併成單一大檔（每 10 輪 1 次）
v1-7 一個大 rowset（乾淨、有序、去重後）
Compaction Score = 查詢時要合併的路數；越高查詢越慢，compaction 優先處理高分 tablet
選擇策略：cumulative 併小檔（最大檔 ≤ 總量一半）、base 需與 base 檔比例 ≥ 0.3 才划算——避免寫放大爆表
資源有限：每個磁碟每輪挑 score 最高的 tablet 做；單次併檔數量有上限（cumulative ≤1000、base ≤20）
Vertical compaction 按「列組」合併降記憶體；別把 compaction 整個關掉「拼查詢」——那是透支

解解決的瓶頸

把「追加出來的碎片」重新疊整齊：路數變少 → 查詢合併成本下降；順帶物理清除 delete 標記、Aggregate 預聚合、Unique 去重——檔案數量與空間都回到健康狀態。

限仍沒解決

compaction 吃 CPU / IO / 記憶體，跟查詢搶資源；高頻小寫入會讓它永遠追不上（score 居高不下）；且 merge 期間要hold 住版本，太長會拖住後續寫入的清理。

例例子

某張表一天幾百個小 load，查詢每況愈下：SHOW TABLET … 看到 compaction score 破百。解法不是加機器——是餵大包 / 開 group commit，讓 rowset 數量長回正常。

TAKEAWAYCompaction 是 LSM 的「還債機制」：寫入越快越碎、債越多。健康的 Doris 是「寫入節奏 × compaction 能力」的平衡——score 是這份健康的儀表板。

05 · 查詢引擎19

3.0 起唯一的執行引擎：Pipeline——執行緒由 CPU 決定，不是由併發查詢數決定

火山模型（1 查詢 N 執行緒）→ Pipeline（固定執行緒池，跑「可讓位」的任務）
舊火山模型的痛：每個 fragment instance 一條 OS 執行緒 → 100 個併發 × 每查詢幾十條 = 幾千條執行緒互相卡 IO
Pipeline 做法：fragment 拆成 DAG 狀的 pipeline（源頭 Source → 終點 Sink），每條 pipeline 開 N 個 PipelineTask，丟進固定大小執行緒池（照 CPU 數）
讓位不阻塞：任務卡 IO 或時間片到（預設約 100ms）就 yield，執行緒立刻接下一件——執行緒永不空等
join / 聚合 / 排序會拆成「Sink 先建 hash table → Source 再 probe」兩段，用 Dependency 通知「準備好了」
傾斜救星：Local Shuffle
掃描端某 bucket 特別大時，BE 內部先本地重打散再餵給下游，把 (7, 1, 1) 變成 (3, 3, 3)——不經網路就撫平長尾
別混淆：向量化是「另一層」
向量化決定「一個 operator 對一坨列做什麼」（4096 列 block、欄式迴圈）；pipeline 決定「這些批次怎麼排上核心」——兩者正交、一起運作
主要旋鈕
parallel_pipeline_task_num（預設 0 = 半數核心）——通常不用動

解解決的瓶頸

同時解三個洞：執行緒爆炸（改由 CPU 預算決定）、核心閒置（傾斜與阻塞不再綁死一條執行緒）、調參靠猜（不用再逐 instance 設併發）。3.0 起火山模型已刪除，pipeline 是唯一引擎。

限仍沒解決

pipeline 不是加速器，是「別浪費核心」的排程器：單查詢變快有限，真正的加速仍靠少掃、少交換、少傾斜；且超輕量點查（單 key 幾千 QPS）不值得走完整規劃 → Doris 另有「高併發點查」短路徑。

例例子

網路上舊文章教你開 enable_pipeline_engine——那是 2.x 的實驗開關，3.0+ 已是 no-op。看到舊調優文章先看版本，這類知識半衰期很短。

TAKEAWAYPipeline = 把查詢切成「可讓位的小任務」跑在固定執行緒池上：併發再高，執行緒數都鎖在 CPU 預算內——這是 Doris 扛高併發 OLAP 的引擎底氣。
05 · 查詢引擎20

JOIN 的四種資料流：分桶鍵對齊就能「本地 join」——最貴的 shuffle 是可以被設計掉的

orders ⋈ users（都按 user_id 分桶 16）→ 四種做法 vs 網路代價
Join 型態怎麼搬資料什麼時候會出現
Colocate Join完全不搬：兩表同分桶鍵、同 bucket 數、且 tablet 被排在同一台 → 各自本地 join 完再合建表就約定好分桶＋colocate 屬性——最省、最快
Bucket Shuffle只搬一邊：orders 已按 user_id 分桶，把另一邊 hash 後對齊餵過去一張表的分桶鍵剛好等於 join 鍵
Shuffle Join兩邊都按 join 鍵 hash 重排到各 BEjoin 鍵 ≠ 任一分桶鍵（預設命運）
Broadcast Join小表整張複製到每個掃描端一方很小（預設幾百 MB 內）——網路傳小表比傳大表划算

解解決的瓶頸

網路 shuffle 是 MPP 最貴的動作。Doris 用「分桶鍵設計」讓 join 盡可能變成資料本地運算；小表則直接廣播——「少搬資料」是 join 調優的第一定律。

限仍沒解決

colocate 條件嚴格（分桶鍵、bucket 數、副本數都要一致），且改分桶就要重建；join 鍵跟分桶鍵天生不合的查詢只能 shuffle——此時資料傾斜會讓單台 hash table 爆記憶體。

例例子

EXPLAIN 看 join op 欄位寫的是 colocate / bucket / shuffle / broadcast——若出現 shuffle 且兩表可改分桶，這是「建表期欠的債，查詢期每天還」的訊號。另外 build 端（右表）產生的 Runtime Filter 會下推去 scan 端提早濾 probe 資料。

TAKEAWAY建表分桶鍵不只是「怎麼存」——它是join 的戶籍制度：兩張常 join 的表，分桶鍵與 bucket 數一致，就等於預約了零搬運的 colocate join。

Profile 只能告訴你「現在怎麼跑的」，不會告訴你「該怎麼改」——要不要換排序鍵、要不要加索引、分桶要不要重做，仍要對照 06–11 頁的原理自己下判斷。

例例子

掃描讀了 5,000 萬列、最後只回 500 列 → 過濾沒在底層做掉：檢查 WHERE 條件有沒有命中排序鍵前綴／索引，或條件根本沒下推。反之若 ① 就只讀 500 列 → 索引與剪枝運作正常，問題在 ③④。

TAKEAWAY慢查詢的標準動作：開 profile → 依 ① 掃描 ② 過濾 ③ 交換 ④ 運算 逐層對數字——90% 的「為什麼慢」在四層內就有答案，剩下 10% 才是系統層問題。
06 · 副本、一致與維運22

副本是「活的保險」：FE 盯版本、落後就補、壞了就重建、太擠就搬家

FE 對每個 tablet 的每份 replica 都記得「它在哪台、版本到哪」

① 寫入照常走 A、B（多數派）

另有 balance：磁碟／節點使用不均時，FE 把 tablet 從滿的搬到空的（也吃 IO，可設限速）
寫入要「多數副本確認」（3 副本至少 2 份成功）→ 掛 1 台 BE 不丟資料、不停寫
查詢由 FE 只派給健康且版本足夠的 replica——不會讀到落後副本的舊資料
副本落後 → clone 補資料（背景、有限速）；壞節點超過時限 → 別的機器重建副本
代價：clone 與 balance 都吃網路與磁碟 IO；一次滾動重啟太多 BE，會瞬間製造大量 clone 任務互相搶頻寬

解解決的瓶頸

單機硬碟會壞、機器會掛，OLAP 不能停擺。多副本 + FE 的「版本帳本」讓故障變成背景事件：少數副本落後不影響讀寫，壞了自動重建——資料庫自己會療傷。

限仍沒解決

副本數是乘法成本：3 副本 = 3 倍儲存 + 3 倍寫入壓力（每筆要寫多份）；「極端耐用」（跨機房、跨叢集災難）單靠副本做不到——那是你們另一份 Doris HA deck 的主題（CCR／雙寫）。

例例子

半夜一台 BE 掛了，早上你發現叢集「有點慢」：很可能是它那幾百個 tablet 正在別的機器 clone 補副本。所以滾動升級要一台一台來，給 clone 時間消化，別一次重啟半個叢集。

TAKEAWAY副本機制 = 用「版本」做健康檢查：FE 不需要知道硬碟死活，只要看到 replica 版本落後或心跳消失，就自動進入「補齊／重建」流程——維運的標準動作是「一台一台來，讓保險自己生效」。
06 · 副本、一致與維運23

改表結構也有「貴與便宜」：加欄位很便宜，動排序鍵／分桶很貴

Schema Change 兩條路：light（只改元資料）vs 重寫（搬全部資料）
你的 ALTER底層發生的事成本與注意
ADD / DROP 欄位
（light schema change）		只更新 FE 的 schema 版本 → 新資料直接帶新欄位；舊 segment 讀取時「補預設值／忽略」秒級、不搬資料；日常加欄位放心做
改排序鍵／分桶／欄位型別等產生重寫任務：按新結構把資料重新排序、重新分桶、寫成新 tablet，完成後原子切換要搬全部資料（吃 IO／空間／時間）；會跟 compaction、查詢搶資源，選離峰做
改 bucket 數（分桶）資料要按新 hash 全部重新分配重寫等級——所以 bucket 數與分桶鍵「建表就要想清楚」
另兩個「結構性加速」記一下：同步物化視圖＝用另一組列順序多存一份 → 等於多一組前綴索引（Duplicate 表常用）；AUTO bucket＝沒指定 bucket 數時依資料量自動選，降低「建表選錯數」的風險

解解決的瓶頸

資料模型在演化（加欄位、加字典欄是常態）。light schema change 讓「結構演進」不必每次都付出全量重寫的代價——加欄位變成改一行元資料的事。

限仍沒解決

「便宜」只涵蓋特定操作；會改變資料物理排列的修改（排序鍵、分桶、型別）永遠是重寫等級。輕重之分不會隨版本消失，因為資料已經照舊結構排好了——物理排序無法免費重排。

例例子

「加個 user_name 欄」→ ALTER 秒回；「把 user_id 從排序鍵第 2 位移到第 1 位」→ 全表重排，幾 TB 表可能要跑幾小時。前者隨時做，後者等於是「改表的物理設計」，做完記得驗證前綴索引命中。

TAKEAWAY區分兩種 ALTER：「加東西」便宜（light）、「重排東西」昂貴（copy）。排序鍵、分桶鍵與 bucket 數屬於後者——它們是建表期就要下對的決定。

25 頁濃縮成一座工廠
① 接單與設計（FE）
SQL 被編譯成藍圖（fragment），元資料是 BDBJE 同步的帳本；所有寫入由 FE 開 transaction 協調
② 進料（寫入）
memtable 吸收 → 順序落成 rowset → publish 一次開閘；刪改只記標記，物理清理交給 compaction
③ 倉儲（儲存）
tablet = 最小單位，3 副本分散放；segment 一欄欄排，排序鍵＋前綴索引＋zonemap/bloom/倒排負責跳過不該讀的
④ 出貨（查詢）
fragment 派到各 BE，pipeline 在固定執行緒池平行跑、向量化批次運算；colocate 讓 join 不出貨（零搬運）
⑤ 定期盤點（compaction）
score 高的 tablet 優先：小檔併大檔、清墓碑、去重預聚合——讓查詢永遠只面對少數幾路
⑥ 保險（副本修復）
FE 用版本盯每個 replica：落後就 clone 補、壞了就重建、不均就搬家——機器故障是背景事件

解看懂底層 = 預測行為

現在你能解釋：為什麼少 SELECT * 快、為什麼 key 順序重要、為什麼小批次寫入會害了 compaction、為什麼 join 慢可能是建表欠債——每個「為什麼」都能對回某一頁。

限仍沒解決

這份 deck 沒覆蓋的角落：跨機房 HA／CCR（另有專屬 deck）、存算分離模式（3.0+ 可選，把儲存搬上物件儲存）、湖倉一體查詢外表、以及 Workload Group 資源隔離——需要時再看官方文件。

例例子

把知識轉成三個「檢查動作」：新表上線前看 EXPLAIN（join 是不是 colocate、掃描有沒有剪枝）；慢查詢開 profile 對四層漏斗；每週瞄一眼compaction score 與 rowset 數量趨勢。

TAKEAWAYDoris 的效能不是靠單一黑魔法，而是「每層省一點」：列存省 I/O、索引省掃描、pipeline 省執行緒、colocate 省網路、副本省停機。把每一層的省法用對，就是 90 分以上的 Doris 使用者。
