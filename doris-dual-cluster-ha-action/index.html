Doris 雙叢集 HA 行動版

5 分鐘讀完 · 決策在第一行 · 論證出處：技術版 / 白話版 / 證據清單

決策：選方案三。兩座 Doris 各跑一個獨立 Spark Streaming job，消費同一個 Kafka topic；query 用 HAProxy VIP 半自動切換。
第一步：本週先盤點表模型（下面「現在就做」第 1 項）——它決定整個方案 go / no-go。

01為什麼選它（4 點，夠了）

  • 故障時 ingestion 零動作、資料零遺失（RPO ≈ 0）——備援座平時就在寫。
  • 唯一不踩兩顆地雷的方案：CCR 已被官方實質棄養（文件下架、repo 停滯）、MinIO 不可依賴。
  • 我們的寫入 100% 走 Kafka——「源頭重放」剛好完全成立，多數團隊沒這條件。
  • 新增元件全是常規工程（第二套 job、proxy、對帳），沒有要自己養的 fork。

02為什麼不選別的（一句話一個）

方案一句話死因
① Proxy + CCR✗ 要接手 2.2 萬行 Go 的 fork 永久跟版，且 failback 只能整座重抄
② 同 job 雙寫✗ 一座卡住拖垮兩座；半批失敗後兩邊永久分歧
④ Backup 冷備✗ 只支援 S3/HDFS（我們沒有），RPO 小時級不合格

CCR 留一個用途：整座重建時叫來搬一次資料，搬完即拆。

03成立前提（3 個，都要付）

  1. 所有表收斂成 Unique Key（Merge-on-Write）——connector 官方自承給不了 exactly-once，重放去重只能靠表模型。Duplicate / SUM 表重放必髒。
  2. Kafka retention 拉到 14–30 天——它決定一座能離線多久還追得回來。
  3. 對帳跟方案一起上線——雙路寫入沒有任何機制自動保證兩邊一樣，分 partition count + hash 是唯一防線。

04現在就做（5 件，按順序）

  1. 盤點表模型：數清楚多少表不是 Unique Key、缺主鍵的怎麼補。產出一張清單。約 2–3 天
  2. MoW 壓測：拿最大的一張表實測 Unique Key MoW 寫入吞吐 vs 現況。約 1 週
  3. 重放冪等驗證：kill -9 job → 重啟 → 對帳，證明「重做不變多」。約 2 天
  4. 追平演練：停一座 24 小時再重啟，量追平耗時 → 反推 retention 要買幾天。約 3 天（含等待）
  5. HAProxy + keepalived PoC：三層健康檢查 + VIP 漂移，量實際切換秒數。約 1 週
之後再說（先別碰）：對帳工具完整版、DDL migration pipeline、2PC 開關決策、整座重建演練、升級 2.1.8+ 排程。第 1–5 項有結果前，這些都不動。

05要拿去問業務方的（4 題）

  1. 正式 RPO / RTO 要多少？（現在的假設：分鐘級、半自動）
  2. 切換瞬間查到「舊幾秒」的資料，可以嗎？
  3. 兩座機器實體上隔多遠？同機櫃同電力等於白做。
  4. 沒主鍵的表要補主鍵，下游改查詢的量能排進哪個季度？

06做完的樣子（驗收條件）

  • ✓ 拔掉 A 座電源，query 在 5 分鐘內全部落到 B 座，資料零遺失。
  • ✓ A 座重開後自己追平，對帳全綠，人工擇時切回。
  • ✓ 對帳每天跑，兩座差異 = 0 或有告警單。
