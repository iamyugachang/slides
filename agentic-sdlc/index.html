01AGENTIC SDLC · 實戰拆解影片實作筆記

進階 Agentic SDLC：
你 ↔ 一個 orchestrator
由它去調度一隊 agent

把「自己盯每一個任務」換成「只對一個 orchestrator 說話」——拆解 Kun（前 Meta／Microsoft／Atlassian L8 principal engineer）1 小時 40 分的實戰直播：全程只靠一個模型，從空目錄做完一個真的有人在用的 iOS 全端 App。他整場只做三件事——砍範圍、抓錯數字、按授權。

Herder · agent session 管理 FirstMate · 單一 orchestrator Crewmates · 可觀察的 worker Lavish · 互動決策 artifact No Mistakes · 變更驗證閘 Atomic Vault · 機密授權
這 24 頁只回答一個問題：哪些做法你今天就能搬進自己的工作流。（原始影片：youtu.be/kPN564Kol14，Kun 的 agentic engineering workflow 實作篇）

02PART 0 · 全景角色怎麼切

整套系統只有四個角色：你、orchestrator、worker、工具層

① 你 · Captain
只跟一個 agent 說話；下決策、給授權、定義「什麼叫做完」——不碰調度
② FirstMate · orchestrator
唯一的對話窗口：拆工、派工、收狀態、關掉做完的 session、把回報排成 follow-up 佇列——自己不做工
③ Crewmates · worker
每個都在自己 tab 裡跑的普通 agent（Pi agent／Claude Code）：你可以隨時走進去直接 steers，不是黑盒 subagent
④ 工具層
Herder 管 session｜Lavish 做決策 artifact｜No Mistakes 當變更閘門｜Atomic Vault 管機密｜quota widget 看額度
對照傳統 SDLC：你＝PO／Tech Lead 的判斷、FirstMate＝PM＋TL 的調度、Crewmates＝工程師。差別是：三個角色裡有兩個已經換成 agent，只有判斷還在你手上。
學的不是工具，是角色切法：把調度與執行都交出去，你只留決策。

04PART 1 · 八個可複製原則原則 1／8

原則 1：只對一個 agent 說話，其他全都不要看

舊習慣：自己當調度器

  • 同時盯 4 個 tab，自己記哪個 agent 在哪個狀態
  • 自己發現誰做完了、自己收報告、自己關 tab
  • context switch 的成本全部落在你身上

這套做法：把它外包出去

  • 只有一個入口（FirstMate），你只講需求
  • 它派工、收狀態、關掉做完的 session
  • 還在跑的事自動排成 follow-up 佇列，等它有空再讀
他甚至開了 calm mode（FirstMate＋Pi agent 獨有）：terminal 裡只留「你的 prompt」與「FirstMate 的回覆」，所有 tool call 全部隱藏。理由說得很直白：現在的模型很少需要你中途喊停；那是模型比較弱的年代才需要的習慣。
實例
市場研究 scout 一寫完報告，FirstMate 就自己把那個 tab 關掉了——「以前這是我在做的事。」
代價是信任，得到的是一次只裝一件事的腦袋。

05PART 1 · 八個可複製原則原則 2／8

原則 2：orchestrator 的唯一工作是把工作交出去

它自己動手

  • 一次只能做一件事 → 你的事排在後面
  • 它忙起來就沒空接收 worker 的狀態更新
  • 你就失去「隨時可以問」的那個窗口

它只派工（影片的實際行為）

  • 每一次要動工，第一個動作都是「開一個新 crewmate tab」
  • 後端三件事（API／DB schema／VPS）＝三個 tab 同時跑
  • 你要改方向，只講一句，它自己去 redirect 對應的 worker
對比常見 harness 的 subagent：那是黑盒，你很難看它在幹嘛、也很難中途 steers。這裡的 crewmate 就是一個跑在普通 tab 裡的普通 agent——觀測性與可介入性是刻意保留的設計。
實例
他要改基礎設施做法，只對 FirstMate 說「VPS 我想用 OpenTofu 這種 IaC」，FirstMate 回「已把 infrastructure work 改成 OpenTofu」——不用管是哪個 agent 在跑、哪個要重啟。
orchestrator 的價值是排隊系統，不是產能。

06PART 1 · 八個可複製原則原則 3／8

原則 3：永遠問「等待時還能做什麼」

01
市場 scout
有沒有現成 App？最接近的競品？縫隙在哪
→
02
技術 scout
全端怎麼做：資料層、auth、成本；順手建待決策 backlog
→
03
前端 wireframe
趁後端還在調查，先做可點的原型把體驗定下來
→
04
競品靈感回灌
回頭分析市場報告，把別人的好點子併進 PRD
他反覆做同一件事：等後端調查的空檔，就叫前端先做 wireframe；等 wireframe 的空檔，就叫 agent 回去分析市場研究、把競品的好設計撈出來。原則是四個字——不要停：既不讓 orchestrator 閒著，也不讓自己閒著。
實例
競品報告撈回來的概念最後真的進了產品：money buckets（花／存／捐）、教學綁在真實動作上（存錢後解釋餘額、借錢時解釋本金）、彈性的零用金規則。
agent 的等待成本趨近於零，你的等待成本才是瓶頸。

07PART 1 · 八個可複製原則原則 4／8

原則 4：決策要給人看得懂的介面，不是一坨文字

技術研究報告 report.md

  • 351 行文字，「很多有用資訊，但我不想讀這面牆」
  • 很難針對某一段給回饋：你只能再打字描述一次
  • 開放問題、選項、推薦混在同一個平面裡

Lavish 互動決策卡

  • 開放問題攤成卡片：勾選選項、逐元素註解
  • 架構圖直接畫給你看，一眼看出偷偷被加進來的需求
  • 多餘需求當場刪掉，一次送回去重做整份
實例
在架構圖上看到 audit events＋encrypted export 兩個需求 → 判斷「這有點 over-engineering」→ 直接刪除，並附上一句：先把初始範圍保持最小。
技術 scout 甚至自己建了一份 backlog，專門記「還有哪些決策卡在 Captain 身上」。你的回饋不是散句，而是被結構化的決策紀錄。
決策的產出不是文件，是可以被你指著說「這裡不對」的介面。

08PART 1 · 八個可複製原則原則 5／8

原則 5：不需要每個環節都派最強的模型

主線：GPT-5.6 Luna（X-High）

  • 他刻意挑「不是最強」的模型來做整場：你今天能拿到的效率模型就夠用
  • 所有 crewmate 用同一個模型，一路沒換
  • 1 小時 40 分、四次 context 壓縮，全端 App 從零到能上 TestFlight

設計：Claude Design（Opus 過載 → 用 Sonnet）

  • 「Sonnet 不會給很聰明的解法，但這個問題本來也不複雜」
  • 結論：挑模型看的是任務難度與成本，不是自尊
  • 唯一失手：VPS 成本判斷——因為資料是錯的
唯一失手
agent 拿錯誤報價推薦 $25/mo Supabase＋$30/mo VPS。他只回一句「三個使用者不值得付這麼多，$5 上下就夠」並要求去查真實報價 → agent 上網查價、改正建議為 $5.5/mo 的 Hetzner VPS。
注意這裡的機制：模型不會自己知道你的世界長什麼樣。你的產業常識（這個價錢不合理）就是系統裡最貴的那一筆輸入。
模型選擇是成本與延遲問題；但事實錯了，一定要你用常識補一刀。

09PART 1 · 八個可複製原則原則 6／8

原則 6：驗證閘要分級開關，不要一開始全上

01
原型階段
No Mistakes 不開、PR 直接合併：「現在不用等我 approve」
→
02
MVP 階段
每個 code change 都跑本地驗證（No Mistakes），PR 需要被 review 過
→
03
產品階段
更強的 approval flow；此時才有「合併前必須有人簽」的價值
No Mistakes 是他自建的 local validation pipeline：每一筆變更都先跑一次本地驗證，確認「這真的可以 merge」。因為他承認：「我其實沒有很認真在看 code，我只跟 FirstMate 說話」——所以才需要另一組護欄。
判斷準則
如果這個變更，你本來會找人類 reviewer → 把驗證閘打開；如果本來就是自己一個人寫、不需要同事看的 → 就不要開。
guardrail 要跟著風險成長，而不是跟著工具成長。

10PART 1 · 八個可複製原則原則 7／8

原則 7：只接受證據，不接受「做完了」

① 定義 done
在 simulator 用我本人真的 Apple 帳號登入，打到 VPS 上真的 backend，資料雲端同步
② 要證據
FirstMate 說「app 通過 iPhone simulator 驗證」→ 他回：「我需要一些證據。」
③ 追問
「iOS app 真的接上 backend 了嗎？」答案：還沒，只是 mock → 繼續做，直到真的通
④ 收尾
存 $10 → 小孩視角看到 $10 → 登出再登入資料還在 → 才叫完成
測試也不是他自己做的：agent 自己在 simulator 跑起來、自己看到登入錯誤畫面、自己判斷異常、自己去找 bug。人只負責定義什麼叫做完。
實戰 prompt · 除錯 「你自己去做一些 e2e 測試，看能不能找出真正的 bug。除非只有我能做的事，不然不要問我。」 他在影片裡補一句：「這句話我常對 agent 說——它們其實很有能力，只是需要被鼓勵繼續嘗試。」
完成的定義要寫給 agent 看，而且要它自己測給你看。

11PART 1 · 八個可複製原則原則 8／8

原則 8：能力廣開，但碰 production 必須經你授權

Atomic Vault：機密的授權點

  • agent 需要 key 時，你會收到請求，並看到它打算跑什麼指令
  • secret 以環境變數傳入，agent 全程看不到明文
  • 取代 .env 檔：「檔案很容易外流，而且你不知道 agent 已經把它送出去了」

瀏覽器代操：有風險但可容忍的放手

  • 開啟 remote debugging，讓 agent 用你已登入的瀏覽器（Apple Developer 後台）
  • 每個 session 都要你按一次授權
  • 判斷標準：「這些事不會有災難性後果」才放手
他自己的說法：「整體哲學是給 agent 很多權限與能力，但當它要碰 production，就必須由我授權。」——當你把調度都交出去、不再逐一看 tool call 時，這一層就是你唯一強制停下來的機會。
順帶一提
他把 key 名稱講錯（Cloudflare_api_key vs Cloudflare_api_token），發現後只說一句「喔，是我記錯」——對話本身就是修正介面，不用怕講錯。
你沒在看每個 tool call，所以機密與 production 授權點必須是你唯一強制停下來的地方。

12PART 1 · 維運細節讓長 session 不爛掉

三個「可以不用管」與「一定要管」的維運細節

可以不用管：context 壓縮

  • 整場自動壓縮（compaction）四次，每次「看不出差別」——它還記得我們在做什麼
  • 關鍵不是壓縮演算法，是把決策寫進檔案：派出去的任務都留在 backlog／PRD 裡，壓縮掉也能再撈回來
  • 他的結論：壓縮已經變成實作細節，不要主動去整理 context

一定要管：三個數字

  • context 上限鎖在 272K：超過上限的請求會被用更貴的價格計費（「很多人抱怨 quota 燒很快」的原因之一）
  • 額度看板：多個訂閱的剩餘額度放在同一個 widget（Claude／Codex／Kimi／Grok）
  • 成本前置：VPS、SaaS、備份策略都要真實報價，別讓 agent 用猜的
為什麼這頁重要
這一輪跑了 1 小時 40 分、數十個派工、四次壓縮。如果 context 是你要照顧的東西，這個工作流就不可能成立。把它當電費看：偶爾看帳單，不要天天抄表。
能外包給系統的維運就別自己扛；要自己扛的只剩下「錢」跟「授權」。

14PART 2 · 八階段實作階段 2／8

階段 2 Discovery：一次把想法倒完，然後派兩個 scout 並行

實戰 prompt · 需求傾倒（原文約 3000 字） 「這是 Eddie 要我幫他做的 App，用來管零用錢…… 我想要它有教育價值，教他 balance、loan、信用卡怎麼運作、儲蓄的利息…… 今天只做 iOS（他用 iPad），要有 parent mode 跟 child mode…… 幫我做兩件事：先做市場調查，看有沒有現成的 App——有的話我就直接裝給他；另一邊同時看技術面，這個全端要怎麼做。」 關鍵不是講得漂亮，是把限制條件講進去：錢是虛擬的、資料要在雲上跨裝置、家長要能控制、小孩只有讀取。
市場 scout
搜了一圈沒有完全符合的 App，列出最接近的競品與各自的強項 → 建議「自己做，而不是拿替代品」
技術 scout
native SwiftUI、auth 方案、資料層、成本；並主動建了一份待決策 backlog，記「哪些事要等 Captain 拍板」
輸入不必結構化，但一定要包含真正限制條件；scout 會自己長出結構。

15PART 2 · 八階段實作階段 3／8

階段 3 決策收斂：逐項拍板，並砍掉幻想需求

後端 hosting
建議 hosted Supabase Pro $25/mo；自架 VPS 報 $30/mo
3 個使用者不值得付 SaaS → Hetzner VPS $5.5/mo（要求用真實報價重算）
備份與稽核
point-in-time recovery、加密匯出、audit events 全都列進來
只留每日備份 90 天；稽核與匯出先刪——「先把初始範圍保持最小」
環境分層
規劃了 development 與 production 兩套環境
只有一個 production：沒人知道的新服務不需要環境分層
登入方式
Apple 現在、Google 之後、多身份綁定
今天只做 Apple；auth identities 表留著，之後才好綁其他帳號
家長權限
家長能存提、小孩唯讀
加一層 PIN 保護「家長專屬操作」；小孩要用別的裝置就靠配對
你在這一頁的價值是三件事：砍範圍、抓錯數字、決定「不要什麼」（模型預設會 over-engineer）。

16PART 2 · 八階段實作階段 4／8

階段 4 規格：把對話收斂成 repo 裡的一份 PRD

① 對話中的決定
決策卡上的勾選、wireframe 的回饋、市場靈感的取捨
② 落成 PRD
請 agent 寫成 repo 內的 markdown（先放 README）：問題、目標使用者、已定決策、待決問題
③ 進版控＋PR flow
推到 GitHub；從這裡開始所有變更走 PR（此時先 direct merge，MVP 後再收緊）
④ 變成合約
後面每一條 workstream 的 agent 都對照它做事
實戰 prompt · 收斂 「不用再更新這個原型了，只要把我的回饋記下來，然後寫一份 PRD 文件，用 markdown 放在 repo 裡（先當 README 就好）。」＋「把這個 repo 推成我的 GitHub public repo，接下來我們走 PR flow。」 影片細節：他請 orchestrator 去問 worker 要推哪個 GitHub 身份——「多個身份登入時，它會問你，這是好事」。
對話會被壓縮掉，只有進版控的決定能活得比 context window 久。

回饋長什麼樣
「整體不像一個給小孩的 App，要多一點 fun、friendly」｜「這行字根本沒置中」｜「balance 怎麼不見了」｜icon 從幾個選項挑 piggy，並要求直接輸出 iOS 可用的尺寸。
他給設計 agent 的輸入是：repo URL＋「還沒有程式碼，讀 README 理解需求；你可以挑戰任何既定的 UX，用你的判斷做最好的體驗。」——把品味留給 agent，把感受留給自己。
順序錯了（先畫面、後系統），後面每一個新畫面都要重來一次。

18PART 2 · 八階段實作階段 6／8

階段 6 並行實作：後端三條線＋前端一條線同時跑

① backend API
端點與授權邊界：Apple 登入、家庭、錢包、小孩視角、貸款
② DB schema
parent identities／sessions／families／wallets／loans／ledger entries
③ VPS 基礎設施
機器、備份、部署自動化——用 OpenTofu 宣告式 IaC，可審、可 commit、可版控
④ iOS UI
照 design system 建 iPhone＋iPad 版畫面
實戰 prompt · 派工原則 「設計還在跑。同時可不可以開一些工作把 backend 建起來？需要我做什麼（例如 Apple sign-in）再告訴我；只要不是卡在我身上的，就繼續做、盡量平行化。」（Hetzner 的 API token 在 Atomic Vault 裡，你自己拿。） 不在他身上的事被自動圈出來：VPS 開好、Apple 登入研究、DNS 用 Cloudflare token 建子網域——都由 agent 代操完成。
平行化的前提不是「同時開很多 agent」，是先把「卡在人身上的事」單獨列出來。

19PART 2 · 八階段實作階段 7／8

階段 7 驗收除錯：叫 agent 自己去測、自己去修

① agent 自測
自己在 simulator 跑起來、看到登入錯誤、判斷異常
它自己去修；人只看「通不通」
② 修錯時不閒著
bug 修復要時間，orchestrator 同時派另一條線
做 backend 架構 review：只看 API 端點、auth 流程、DB schema——不逐行讀 code
③ 跨 agent 撞牆
前端打到舊的 DNS 位址（後端切換時它不知道）
orchestrator 自己發現、自己派修，只給 Captain 一句 FYI
實戰 prompt · 放手與追問 「你自己去做 e2e 測試，找出真正的 bug。除非只有我能做的事，不然不要問我。」
「我需要一些證據——我們的 iOS app 真的接上 backend 了嗎？」（答案：還沒，只是 mock。） 他也會要求 agent 把「要人在瀏覽器裡做的事」列成逐步清單，再讓它自己用瀏覽器執行。
要驗收架構，叫 agent 講給你聽（review artifact），不要自己啃 code。

20PART 2 · 八階段實作階段 8／8

階段 8 交付：完成 ＝ 真的有人在用

① simulator e2e
真 Apple 帳號登入、真 backend、資料雲端同步
② 存一筆真的資料
家長加 $10 → 小孩視角看到 $10 → 登出再登入，資料還在
③ TestFlight
build 上 TestFlight，裝到真實裝置
④ 隔天開始用
「裝到我兒子的 iPad，明天就可以真的開始用」
這一輪的成果：1 小時 40 分、從空目錄到一個真有人在用的全端 App，全程只用 GPT-5.6 Luna（X-High），設計還只用 Sonnet。他的收尾是：「今天我們用 Luna 從零做完一個真的全端 App——連設計都沒用到最強的模型。」
留給下一輪的
他明講今天不做的事：自動化部署（之後用 Tailscale 把裝置、VPS、GitHub Actions runner 串成同一網段）、Google 登入、UI 打磨——先定義範圍，再定義「之後」。
交付的判準不是 PR 合併，是有人在真實場景用它。

21PART 3 · 落地到你的工作流反模式

五個最容易踩的坑，影片裡他都踩給你看過

✕
盯著 tool call 看
模型夠強時只是分心——這正是 calm mode 存在的原因；弱模型時代才需要「看著它做事」。
✕
讓 orchestrator 自己動手
它一忙，你就排隊，還失去那個隨時能問的窗口。它的工作只有派工。
✕
跳過 PRD 直接開工
決定會散在對話裡，被 context 壓縮帶走；後面的 agent 就沒有人生合約可以對照。
✕
一開始就分環境／做稽核
「GPT-5.6 特別容易 over-engineer」：audit events、加密匯出、dev/prod 分層都被他當場砍掉。先縮小範圍。
✕
把 key 放 .env 檔
你沒在看 tool call，就不會知道它被送到哪裡去——機密要有獨立授權層。
這五個坑的共同點：都是人類習慣被原封不動帶進 agent 工作流。

23PART 3 · 落地到你的工作流起手式（候選）

今天就開始的五個動作：先跑一次完整流程，再談改工具

① 開場立規矩
每個新專案的第一句話：立規矩＋開 repo＋先寫一份 PRD 佔位
成本最低、影響最大——後面幾十個派工都照它走
② 圈出「只有我能做」
派工時同時列出卡在你身上的事，其餘全部放行平行跑
讓 orchestration 有明確的等待邊界
③ 決策改用單頁 HTML
選項＋我的裁決＋理由，取代 300 行報告貼在對話裡
回饋變成「指著某一格說不對」
④ 給高風險 repo 一個 verifier
用腳本斷言結構與規則，每次變更都跑
這就是 No Mistakes 的本質：不靠人盯，靠機器擋
⑤ 機密集中一個授權點
production 操作與 key 取得都走同一道「要我按」的關卡
風險最高、但一旦建立就長期受益
這是候選清單，不是排程；建議照 ①→⑤ 由低風險做到高風險，並且挑一個真的要做的小專案整條跑完。

24收尾帶走三件事

四個角色、八個階段——你的判斷力是唯一不能外包的東西

① 介面：只跟一個 agent 說話
它負責排隊與調度，你負責需求與決策（原則 1–3）
② 可見：決策用卡片與圖，不是牆
開放問題攤開、選項可勾、架構看得懂——才砍得掉多餘需求（原則 4、8）
③ 可信：分級護欄 ＋ 證據式驗收
風險低的先放手，風險高的才上閘門；完成要有可重複的證據（原則 5–7）
整場 1 小時 40 分，他只做了三件事——砍範圍、抓錯數字、按授權。
剩下的，是幾十個 agent 在他設計好的流程裡跑。
下一步不是換工具，是挑一個小專案把這八個階段走完一遍——流程跑順了，再來考慮要不要有自己的 FirstMate。謝謝大家，歡迎討論。
