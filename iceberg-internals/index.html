02Ⅰ 心智模型

先記住一句話：資料檔不動，動的是「指標」

metadata.json v1SNAPSHOT S1
schema v0 · spec v0 · snapshots: [S1]
metadata.json v2SNAPSHOT S2
schema v0 · spec v0 · snapshots: [S1, S2]
metadata.json v3SNAPSHOT S3 · current
schema v1 · spec v0 · snapshots: [S1, S2, S3]
HMS 指標
metadata_location
catalog 只記「現在指到哪一顆」，reader 從這裡開始往下走
1
檔案不可變
data 與 metadata 檔一寫出就不再改寫——全部 append-only。想「改」就是寫新檔。
2
表 = 一顆 metadata 檔
表「現在長什麼樣」由 current metadata 決定，reader 每次從指標往下讀。
3
操作 = 寫新檔 + 換指標
舊指標、舊檔全部留著 → time travel、回滾、並行讀寫都從這裡免費長出來。
對照 Gitcommit 只移動 branch 指標，底下的 objects 永不修改，要回滾就指回舊 commit——Iceberg 把同一招用在資料表上。
後面 23 頁都是這一句的展開：先記住「換指標」，再一層層看它怎麼換得安全、換得快。

03Ⅱ 為什麼要這樣設計

舊世界：Hive 表把「目錄」當真相——一致性、演進、並發全卡在目錄上

Hive 表 · 目錄即一切
schema 在 metastore，partition 是路徑
dw.db/events/ dt=2026-09-01/part-00001.parquet dt=2026-09-01/part-00002.parquet dt=2026-09-02/part-00007.parquet dt=2026-09-03/part-00011.parquet 「資料到哪了？」= list 目錄 「commit 到哪了？」= 檔名搬好了沒 「哪個檔多大/多新？」= 不存在
Iceberg 表 · metadata 即一切
目錄只是擺放位置
dw.db/events/ metadata/00004-<uuid>.metadata.json metadata/snap-<snapshot-id>-1-<uuid>.avro metadata/<uuid>-m0.avro data/event_month=2026-09/<uuid>.parquet 「資料到哪了？」= 讀 metadata 樹 「commit 到哪了？」= 指標換了沒 「哪個檔多大/多新？」= manifest 裡有統計
① 沒有跨目錄的 atomic commit
覆蓋多個 partition = 依序搬目錄/改名，reader 可能看到「09-01 新版 + 09-02 舊版」交錯；搬一半掛掉就停在半套。
Iceberg：換一個指標 = 完整 commit，沒有半套狀態。
② 演進 = 搬資料
schema、partition 規則寫死在目錄與 metastore 約定裡。改 partition 欄位、改欄位名都等於重寫整張表，代價大所以大家不敢改。
Iceberg：schema／partition 是 metadata 內容，換版即可（見 Ⅵ）。
③ 並發靠運氣、查詢靠全掃
兩個 writer 同時寫同目錄 互相覆蓋沒人擋；沒有檔案統計，pruning 只能靠猜與全掃。
Iceberg：樂觀並行 + manifest 內建統計（見 Ⅳ、Ⅴ）。
同一個動作HIVE 世界ICEBERG 世界
一次 commit依序搬多個 partition 目錄——半套狀態隨時可見寫新檔＋一次換指標——沒有中間狀態
改 schema／partition等於重寫資料，或祈禱沒人 renamemetadata 加一版描述——檔案不動
查詢加速list 目錄＋開檔案才知道長怎樣metadata 內建統計，先跳檔再開檔
Iceberg 把「資料長什麼樣」從目錄搬進 metadata——目錄回歸純儲存，一致性與演進交給 metadata 層處理。

05Ⅲ Metadata 解剖 · Table Metadata

metadata.json：一張表的身分證——現在與歷史都住在同一顆檔裡

00004-<uuid>.metadata.json2.4 KB · S3
{ "format-version": 2, "table-uuid": "f1c3…-b0e2…", "location": "s3://…/dw.db/events", "last-sequence-number": 12, "last-column-id": 8, "schemas": [ { "schema-id": 0, "fields": [ {"id":1, "name":"event_id", "type":"long"}, … ] }, { "schema-id": 1, "fields": [ … ] } ], ← 演進保留每一版 "current-schema-id": 1, "partition-specs": [ { "spec-id": 0, "fields": [{ "name":"event_month", "transform":"month", "source-id":2 }] } ], "sort-orders": [ … ], "default-sort-order-id": 0, "properties": { "write.format.default": "parquet" }, "current-snapshot-id": 7234591029384756198, "refs": { "main": { "snapshot-id": 7234591029384756198, "type": "branch" } }, "snapshots": [ … 每顆 snapshot 一行摘要 … ], "snapshot-log": [ … ], "metadata-log": [ … ] ← 時間軸 }
歷史不是備份，是檔案的一部分
schemas[]、partition-specs[] 各留多版，snapshot-log／metadata-log 記時間軸——演進靠「加版本」，不靠「覆蓋」，所以 rename 欄位不用搬資料。
每次 commit 換一整顆新檔
編號遞增（00000-、00001-…）。舊檔留著 = 可以 rollback 回舊 metadata（metadata-log 記著每顆檔的位置）。
它小，所以換指標才快
整顆只有 KB 級。所有引擎的 commit 最後都是「重寫這顆小檔 + 換指標」——表再大，commit 的成本也跟資料量無關。
這顆檔同時是身分證、演化史與 commit 日誌；讀懂它的欄位，就讀懂 Iceberg 一半的詞彙。

06Ⅲ Metadata 解剖 · Snapshot

Snapshot：一次成功 commit 的「出版目錄」——查詢讀的是 snapshot，不是表

          added-file-size: 84.2 MB · total-records: 8,712,901
manifest-listmetadata/snap-7234591029…-1-<uuid>.avro
summary：不開檔先知道這次 commit 多大
operation（append／overwrite／delete…）與檔案數、列數、位元組都寫在 metadata.json 裡——監控、估成本、判斷「commit 了沒」都不用讀 manifest。
refs：main 就是 current
main branch 指到最新 snapshot；branch／tag 讓你把某個好版本釘住（tag 不會被 expire 清掉，見 20 頁）。
time travel 的單位就是 snapshot
Spark／Trino：… FOR VERSION AS OF <id> 或 FOR TIMESTAMP AS OF '2026-09-01 08:00'——引擎把請求換算成「讀哪一顆 snapshot」。
隔離的來源查詢一開場就鎖定一顆 snapshot；之後別人再 commit 幾次，都不會改變進行中查詢看到的資料——這就是 snapshot isolation。
把 snapshot 想成「出版目錄」：目錄定稿後不再改，加印新版只是再出一本。

08Ⅲ Metadata 解剖 · Manifest Entry

Manifest 的每一行 = 一顆資料檔＋足以決定「要不要讀它」的全部統計

<uuid-b>-m1.avro · 其中一筆 entrycontent = 0 · DATA FILE
status1 = ADDED1=ADDED／0=EXISTING／2=DELETED：這顆 manifest 對該檔的立場
snapshot_id7234591029384756198把它加進來（或標 DELETED）的那顆 snapshot
sequence_number V212這顆檔的 data sequence——「何時生效」
content V20 = data0=data 檔／1=position delete／2=equality delete（見 17 頁）
file_paths3://…/events/data/event_month=2026-09/<uuid>.parquet完整路徑＝這顆檔的唯一 identity
partition{ event_month: "2026-09" }這顆檔屬於哪個 partition（不是看目錄！）
record_count / file_size890,121 rows · 33,554,432 bytes規劃 split 與 cost 用
lower_bounds / upper_boundsevent_ts: 09-01T00:00:00Z ~ 09-14T23:59:59Z
user_id: 1001 ~ 99872每欄 min/max——檔案層 pruning 的燃料
null_value_counts…event_ts: 0 · user_id: 12 …value_counts／null／nan、column_sizes、split_offsets 等
一行 = 一顆檔的完整「病歷」
大小、列數、每欄 min/max、null 數——查詢還沒開 Parquet 就知道該不該讀它。這些統計在 commit 寫入時由 writer 從檔案 footer 彙整出來。
DELETED 不是「刪檔」
overwrite／compaction 把舊檔在新 manifest 裡標 2=DELETED，新 snapshot 就不再引用它——檔案本身還躺在 S3，直到 expire 才物理刪除（20 頁）。
manifest 本身也是 Avro 檔
所以 manifest 可以很大、也可以被 rewrite 合併（20 頁）。它的內容不是秘密：任何人都能開一顆 manifest 看表「實際上有哪些檔」。
Entry 是「檔案的索引卡」：Iceberg 一切效能（跳檔、跳 manifest）與一切語意（ADDED／DELETED、content 型別）都寫在這一層。

09Ⅳ Commit · 寫入流程

一次 INSERT 的完整旅程：先寫完所有檔案，最後一動才換指標

1
executor 平行寫資料檔EXECUTOR → S3
每顆 Parquet 直接 PUT 到 data/event_month=2026-09/<uuid>.parquet——此時還沒有任何 metadata 引用它（孤兒候選）。
2
driver 寫 manifestDRIVER → S3
收集 DataFile 清單，寫一顆 metadata/<uuid>-m0.avro：每檔一行＋footer 統計（第 8 頁的 entry）。
3
組 manifest listDRIVER
舊 snapshot 的 manifests ＋ 新 manifest 併成 snap-<id>-1-<uuid>.avro。舊 manifest 直接沿用，不用重寫。
4
寫新 metadata.jsonDRIVER → S3
metadata/0000N-<uuid>.metadata.json：current-snapshot-id 指向新 snapshot。此時S3 上一切就緒，只差指標沒換。
5
CAS 換指標DRIVER → HMS
對 table 拿 lock → 確認 catalog 目前仍指著舊 metadata → 把 metadata_location 更新成新檔（第 11 頁）。
6
成功＝指標已換READER
新 reader 從此刻起看到新資料；手上還握著舊指標的 reader 完全不受影響。
步驟 1–4 失敗
表沒有變——那些檔變成孤兒檔，之後靠 remove_orphan_files 清（20 頁）。寫失敗 ≠ 表髒。
步驟 5 失敗（明確）
收到明確拒絕（如衝突）→ refresh 後重試，或直接失敗退出，表維持原狀（10 頁）。
步驟 5 結果不明（timeout）
指標「可能換了可能沒換」→ CommitStateUnknown，不能亂清檔（12 頁，你們 fault-lab 的主戰場）。
讀者視角
讀者只會看到「換指標前」或「換指標後」兩種完整狀態——沒有中間狀態。
Commit 的祕密是順序：先讓所有檔案就位，最後用一個原子動作「公布」——公布前的一切都只是還沒被引用的檔案。

CommitFailedException 是樂觀並行的正常訊號；writer 會 refresh 重讀後自動重試（預設最多 4 次、指數退避，commit.retry.num-retries）。

B 的 data 檔已存在且不會變；重做的是 manifest list／metadata 的編排——所以重試成本低。
什麼時候會一直撞
表太熱（秒級多 writer）→ 衝突率高。解法是縮小 commit 粒度／合批，不是上 global lock。
多 writer 安全 = 「寫檔互不干擾 ＋ 換指標前先驗證 ＋ 衝突後以新 base 重做」——全程沒有鎖任何一顆資料檔。

11Ⅳ Commit · 原子性從哪來

「換指標」這一下不是 Iceberg core 做的——原子性由 catalog 的 CAS 保證

CATALOG「換指標」的原子機制一句話特性
Hive Metastore你們的環境
Thrift alter_table：先對 table 拿 exclusive lock，lock 內比對目前 metadata_location（舊值符合才更新），由 HMS 的 DB transaction 保證單一更新原子。
兩個 writer 的 CAS 被 lock 序列化；HMS 掛 = 無法 commit（讀可用 cache 撐）。
HadoopCatalogHDFS
以檔案系統的 atomic rename 充當 CAS（v<N>.metadata.json 換檔名）。
只適合有 rename 語意的檔案系統；S3／MinIO 沒有，要用別種。
AWS Glue／S3 Tables＋ DynamoDB lock
條件寫入：version／attribute 檢查不過就拒絕請求。
把「CAS」變成物件儲存上的一次 put-if-absent／條件更新。
REST catalogPolaris · Lakekeeper · 自家
HTTP PUT + Requirement：要求「目前仍是舊 metadata」才接受新檔。
跨引擎、跨語言的開放介面；集中管權限與審計。
Nessie
Git 式 commit：每次更新形成 hash 前鏈，舊值不符就拒絕。
內建 branch／tag 版本控制，把 Iceberg 的「換指標」升級成 Git。
重點Iceberg core 沒有 lock server——誰當 catalog，誰就得提供「單一指標的 CAS」；catalog 只存指標不存資料，換 catalog 不動資料。
Commit 的原子性 = catalog 的 CAS 能力：這是整張表 ACID 的地基，也是維運要盯的第一個環節。

12Ⅳ Commit · 失敗語意

Commit 只有三種結局：成功、確定失敗、「不確定」——第三種最危險

✓ SUCCESSCommitStatus.SUCCESS
收到 HMS 成功 ack，且新 metadata 可讀。資料確定生效。之後的 cleanup 才准動這次 commit 的檔？——不用，已被引用。
現象：job 成功；metadata_location 已前進到 0000N；下次查詢看得到
該做的：正常結束、記錄 snapshot id。
✗ 確定失敗CommitFailedException
明確收到拒絕（如 CAS 衝突）或確認指標沒動。表維持原狀；本次寫的檔沒被任何 metadata 引用 = 孤兒。
現象：例外明確、指標未動；log 常看到 retry 後放棄
該做的：可安全清（或留給 remove_orphan_files）；重試也安全。
? 不確定CommitStateUnknownException
timeout／斷線／499——指標可能已換、可能沒換。job 顯示失敗但資料可能已經 commit。
現象：client timeout < HMS 完成時間；ACK 遺失；重跑可能重複
該做的：不能清任何檔；先查 pointer 與 chain 再決定（重跑可能重複資料！）。
真實事故你們 fault-lab 的兩類 data-integrity 事故都從這裡來：① late-success：client timeout 早於 HMS 完成 → caller 判定失敗 → abort cleanup 刪檔 → 刪到已被 current 引用的 metadata／parquet；② false-success：PUT 回應丟失但物件其實已寫 → commit 指向「以為存在」的 chain。
I2：只有「確定沒被引用」的檔才能清 I3：unknown commit 的產物不可清（當孤兒留著） I4：判 live／dead 以「DELETE 當下是否被 current chain 引用」為準 手動清 table location 底下的「新檔」＝踩雷
看到 timeout／unknown，先當作「可能已成功」處理：查 metadata_location、走一遍 chain，別急著清檔。

15Ⅴ 讀取 · 為什麼快

快的原因：統計在 metadata 主流程裡——一層跳 manifest，一層跳檔案

SELECT count(*) FROM events WHERE event_ts >= TIMESTAMP '2026-09-01'
第一層：manifest list 的 partition 邊界 整顆 manifest 跳過 · 不必開檔
m0 · 2026-08bounds: 08-01 ~ 08-3140 檔✕ 整顆跳過
m1 · 2026-09bounds: 09-01 ~ 09-3012 檔✓ 開
m2 · 2026-10bounds: 10-01 ~ 10-318 檔✕ 整顆跳過
第二層：manifest entry 的 column stats m1 內逐檔比對 min/max
<u1>.parquetevent_ts: 09-01 ~ 09-04890K 列✓ 讀（全在範圍內）
<u2>.parquetevent_ts: 09-01 ~ 09-141.1M 列✓ 讀
<u3>.parquetevent_ts: 06-12 ~ 06-30320K 列✕ bounds 全在 filter 前 → 跳
跟 Hive 的 pruning 差在哪
Hive 只能靠 partition 目錄切，filter 沒打在 partition 欄位就全掃；Iceberg 的 partition 是「隱藏的」——filter 直接打在來源欄位（event_ts）就自動生效，不用知道 partition 欄位存在（18 頁）。
統計 pruning 是 inclusive
min/max 只能說「可能符合」，不能說「保證符合」——所以最後的正確性還是落在 Parquet 的 row-group filter 與真實比對。Iceberg 省的是「開檔數」，不是資料正確性。
統計會失真，要重寫才修
bounds 只會隨新資料「放寬」，不會自動縮小——頻繁 delete 後統計可能過寬，重寫檔案（compaction／rewrite）後才會回到精準。
Pruning 的兩層都在 metadata 上完成：先少開 manifest，再少開檔案——真正讀到的只有「可能命中」的資料。

16Ⅴ 讀取 · 時序真相

snapshot-id 是名字，sequence-number 才是「commit 的全域時鐘」

S1 · seq 8
INSERT 1M 列
（寫入 3 顆檔，seq 8）
S2 · seq 9
DELETE 條件 09-01 前
（新增 delete 檔，seq 9）
S3 · seq 10
INSERT 新資料
（新檔 seq 10）
S4 · seq 11
time travel 回 S2？
seq 11 以後的檔全部看不見
S5 · seq 12
current（last-sequence-number 12）
metadata.json：last-sequence-number（下一號從這裡發） snapshot：sequence-number（commit 當下領的號碼） manifest：sequence-number（這批 entry 的時點） entry：sequence_number（單顆檔的 data seq）
名字 vs 時鐘
snapshot-id 是唯一鍵（長整數，隨機產生，無順序）；sequence-number 是全域遞增的 commit 序號，存在 metadata.json 的 last-sequence-number。v1 只有 id、沒有 clock。
讀舊 snapshot 的規則
讀 seq = k 的 snapshot 時，manifest／檔案的 seq > k 的一律排除——否則會看到「那之後才 commit」的資料或 delete，time travel 就壞了。
delete 只刪「過去」
delete 檔只套用於 seq ≤ 自己的 data 檔：seq 9 的 delete 不會誤刪 seq 10 才寫入的新資料（S3 的新列活著）——並行寫入＋delete 交錯時，clock 是唯一真相。
沒有 sequence，v2 的 row-level delete 在並行下無法證明「刪對版本」——id 回答「哪一版」，sequence 回答「先還是後」。

17Ⅵ 進階語意 · Row-level Delete

DELETE 不改檔案，是「寫一張黑名單」——刪除 = 新增描述刪除的檔

Copy-on-Write寫時複製
受影響的整顆 Parquet 重寫（沒刪到的列也一起複製），新檔取代舊檔。讀的人看到的就是乾淨的檔。
DELETE … → 找出碰得到的檔
→ 重寫成新檔（去掉命中列）→ 換指標
讀最快（沒有黑名單要套）｜寫放大的代價：一次刪 1 列也要重寫整顆檔
Merge-on-Read讀時合併
不動原檔，只新增一顆 delete 檔記錄「哪個檔的哪幾列／哪些值被刪」。讀的人現場套用。
DELETE … → 寫 delete 檔（記錄被刪列）
→ 換指標（讀時過濾）
寫最快（O(刪除量)，不重寫大檔）｜讀變慢：每顆檔都要先套黑名單，黑名單越多越慢
Position Delete Filecontent = 1 · V2
逐列記 (file_path, pos)：哪顆檔、第幾列。精準、檔小；但要知道檔案 layout，重寫後（compaction 併入）才消失。V3 起以 deletion vector 取代。
Equality Delete Filecontent = 2 · V2
只記被刪欄位的值（如 user_id=42）：不知道檔案 layout 也能寫。代價：可能誤殺同值新資料（要靠 seq 守護，16 頁），且比對成本高。
讀取端worker 讀檔時由 DeleteFilter 把該檔相關的 delete 檔套上去；delete 檔累積太多 = 讀越來越慢 → compaction 把 delete 併入資料檔（真正重寫），黑名單就消失。
資料檔永遠不被修改：「刪除」是新增描述刪除的檔 + 讓讀的人過濾；CoW 與 MoR 只是把「重寫成本」放在寫端還是讀端。

partition 不是資料夾，是一條「transform 規則」——規則可以演進，舊檔不用搬

Hive 的 partition
partition 欄位要真的存在於資料裡、寫進目錄路徑；filter 沒打在 partition 欄位 = 全掃。改 partition 策略 = 搬資料＋重建。

partition value 是從來源欄位算出來的（transform），使用者不用加欄位；filter 直接打在來源欄位就自動 pruning。換規則只改 metadata（spec 跟著 snapshot 走），舊檔照常讀。
目錄只是「預設擺放位置」——partition 的真相在 manifest 的 partition 欄位＋spec-id，路徑長怎樣一點都不重要。

欄位 id 才是 identity：所以 rename 欄位不用重寫任何資料

✓

20Ⅶ 維運 · Maintenance

四種 maintenance：全部都是「讓 metadata 不再引用 → 再物理刪除」

Compaction rewrite_data_files
把 N 顆小檔讀出來重寫成幾顆大檔
解決：小檔太多（讀取要開太多檔、planning 慢）。做法：寫大檔 → 新 snapshot 把小檔標 DELETED。之後可再 expire 回收空間。
安全：小檔在舊 snapshot 仍被引用，直到 expire——不會中途消失。
Rewrite manifests rewrite_manifests
把很多小 manifest 合併成少數幾顆
解決：manifest 太多（每次 commit 一顆，append-only 久了會上千）。合併後 planning 開檔次數大減。它不動任何 data file，只重排索引。
安全：metadata-only 操作，可頻繁跑。
Expire snapshots expire_snapshots
刪掉「沒有被保留 snapshot 引用」的檔
唯一會物理刪除舊檔的操作。保留規則：history.expire.min-snapshots-to-keep（預設 1）＋history.expire.max-snapshot-age-ms（預設 5 天）。時間旅行只能回到「還沒被 expire 的 snapshot」。
安全：被任一保留 snapshot 引用的檔絕不刪——先算保留集再刪。
Remove orphan files remove_orphan_files
刪「從來沒被任何 snapshot 引用」的檔
解決：commit 前 crash 留下的孤兒 data／manifest（第 9 頁步驟 1–4）。預設只碰 3 天前就存在的檔——避免砍到還在進行中的 commit。
安全：以「metadata 從未引用」為判準；不是列目錄就刪。
鐵則任何 cleanup 都先算「誰還在引用」，沒被引用才輪得到刪；expire 的保留規則調太小 = 時間旅行資料不見，刪完沒有復原按鈕（object store 沒開 versioning 的話）。
Compaction 讓讀變快、expire 讓空間回來、rewrite manifests 讓 planning 變快、remove orphans 讓目錄乾淨——四者都只是「換一顆新 snapshot 之後，順手刪檔」。

22Ⅶ 維運 · 誤解清單

八個最常見誤解：多半是把資料庫或檔案系統的直覺套到 table format

✗「Iceberg 是儲存／檔案格式」
檔案還是 Parquet／ORC。Iceberg 是 table format：定義 metadata 怎麼描述這些檔。
✗「Iceberg 自己會鎖表」
core 沒有 lock server；原子性來自 catalog 的 CAS（HMS lock／條件寫入…）。
✗「partition 就是資料夾」
partition 是 transform 規則，語意在 manifest 裡；資料夾只是預設擺法。
✗「寫入 Iceberg = DB 等級 ACID」
是單表 atomic ＋ snapshot isolation；沒有跨表 transaction、沒有 FK／約束。
✗「DELETE 完資料就真的刪了」
MoR 只是寫黑名單；物理刪除要等 compaction ＋ expire，在那之前空間照佔。
✗「time travel 可以回到任意時間」
只能回到還沒被 expire 清掉的 snapshot；保留規則由你設。
✗「小檔 Iceberg 會自動合併」
不會。append-only 的結果就是小檔越積越多——compaction 是維運的責任。
✗「v2 表 DELETE 一定很快」
v2 提供 delete 檔機制；快不快取決於 CoW／MoR 策略與 delete 檔累積量。
遇到 Iceberg 行為想不通時，先問一句：「這是 metadata 哪一層的哪個動作造成的？」——答案八成就在這份文件的某一頁。

卡住就翻回對應頁；八題全通 = 可以開始讀 spec 原文，也能 debug 別人的 commit／cleanup 問題。

25Ⅷ 收尾

資料不動，動的是指標。
Iceberg 的一切，都是這句話的展開。

腦中跑完 commit
寫檔 → manifest → manifest list → metadata → CAS 換指標；失敗只有三種結局。
讀懂錯誤與 timeout
unknown 先查 pointer 與 chain，別急著清檔；DELETE 不等於資料消失。
自己推理維運問題
小檔、慢查詢、統計失真、時間旅行不見——都能定位到 metadata 的哪一層。
