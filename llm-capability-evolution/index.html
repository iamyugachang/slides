LLM Capability Evolution

LLM 能力演進：從文字接龍到可驗證成果

模型的底層從未改變——預測下一個 token。改變的，是包在它外面的一層層系統：上下文、工具、執行迴圈與評估。

01THESIS先講結論

LLM 始終是文字接龍。能力的增長，來自外部系統把「猜下一個字」變成「可完成任務的流程」。

能力 ≈ 模型能力 × 上下文工程 × 工具介面 × 執行迴圈 × 評估治理——每一層都在補前一層的洞。

模型能力

會做什麼

推理、程式、長上下文、工具使用的基本盤；決定天花板。

工程封裝

怎麼穩定做到

上下文組織、工具連接、harness、skills；決定達成率。

評估治理

怎麼知道真的變好

eval、軌跡檢核、上線門檻；決定能不能相信。

本 deck 分兩段：先講歷史怎麼走到這裡（2017–2024），再講現在的分層架構（2025–2026）。後者不是線性歷史的延續，而是不同層同時成熟。

032017PART 1 · 模型能力

Transformer：讓「大規模訓練」變成可能

新能力

Self-attention 取代 RNN/CNN

序列中任意兩個位置可直接互相注意，可平行化，長距離依賴不再靠逐步遞迴。

解決的瓶頸

RNN 無法平行、長依賴訓練慢

過去用 RNN 逐字處理，訓練慢且長距離梯度易衰減；Transformer 打開「更大模型 × 更大資料」的路。

仍沒解決

不是通用智慧

不保證事實正確、可控性、安全性或可驗證性——它只是更好的序列模型。

例子

機器翻譯

翻譯一句話時，模型可以同時注意主詞、動詞與遠距修飾語，而不是按順序硬記。

Attention Is All You Need · arXiv:1706.03762

042018–2019PART 1 · 模型能力

Next-token prediction：用「接龍」學到通用語言能力

新能力

生成式預訓練

GPT / GPT-2 以「預測下一個 token」在巨量文字上預訓練，同一模型可遷移到分類、問答、摘要等任務。

解決的瓶頸

每個任務都要重新標註訓練

過去 NLP 是「每個任務一個專用模型」；預訓練讓語言能力先學好，任務再疊上去。

仍沒解決

需要 prompt / fine-tune 才穩定

模型會產出流暢但可能虛構的文字；事實錯誤、偏見、幻覺從這裡就存在。

例子

續寫文章

給一段開頭，模型能接出語法流暢、風格一致的段落——但內容可能是編的。

「Next-token prediction」是訓練目標的技術描述；「LLM 能力演進」是我們現在回頭整理的脈絡，不是單一歷史事件。

052020PART 1 · 模型能力

In-context learning：不用改權重，用範例教新任務

新能力

Few-shot / zero-shot 通用化

GPT-3（175B）在 prompt 裡放任務說明與少量範例，模型即可模仿執行——不必重新訓練。

解決的瓶頸

每個任務 fine-tune 的昂貴流程

從「訓練一個模型」變成「寫一段 prompt」，成本下降幾個數量級。

仍沒解決

對 prompt 極度敏感

措辭、範例順序都會大幅改變結果；推理與事實性不穩，上下文長度有限。

例子

翻譯

放幾組「英文句子 → 法文翻譯」範例，接著輸入新英文句子，模型直接照樣翻譯。

Language Models are Few-Shot Learners · arXiv:2005.14165

062020PART 1 · 模型能力

RAG：把「外部知識」接進生成流程

新能力

檢索 + 生成

先從文件庫檢索相關段落，再讓模型據此生成答案——參數記憶與外部記憶互補。

解決的瓶頸

參數記憶過時、冷門知識查不到、幻覺

知識密集任務（問答、事實查核）不再只靠模型「背過」的資料。

仍沒解決

檢索錯誤 → 答案錯誤

模型仍可能曲解文件、編造引用、忽略證據；不等於可驗證推理。

例子

冷門歷史事件

「某事件發生在哪一年？」系統先查文件庫，再依據檢索到的段落生成答案。

Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks · arXiv:2005.11401

072021–2022PART 1 · 模型能力

Instruction tuning + RLHF：讓模型「照人類的話做事」

新能力

指令遵循 + 人類偏好

FLAN 用多種指令任務 fine-tune；InstructGPT 以 SFT + reward model + PPO（RLHF）把「人類偏好」帶進訓練。

解決的瓶頸

zero-shot 指令遵循不穩、輸出偏離意圖

模型常寫出「合理但不照要求」的回答；對齊讓它更願意遵守「三點摘要、不要閒聊」這類約束。

仍沒解決

RLHF 不是真實性保證

模型仍會迎合使用者、幻覺、拒答不一致；對齊不等於事實正確。

例子

「用三點摘要這篇文章」

InstructGPT 比原始 GPT-3 更可能遵守「三點」「摘要」「不要閒聊」。

FLAN · Finetuned Language Models Are Zero-Shot LearnersInstructGPT · Training language models to follow instructions with human feedback

082022PART 1 · 模型能力

CoT + ReAct：從「直接回答」到「一步步想、一步步做」

新能力

推理軌跡與行動交錯

Chain-of-Thought 要求先產生中間步驟再給結論；ReAct 讓模型交錯產生 reasoning → action → observation。

解決的瓶頸

直接跳結論；純推理無法查資料或操作環境

ReAct 讓模型可以主動呼叫搜尋、查頁面、觀察結果後再決定下一步。

仍沒解決

推理鏈可能是事後合理化

中間步驟不保證真實反映內部推理；工具可能選錯、觀察可能讀錯、行動可能有副作用。

例子

多跳問答

「某演員的配偶出生在哪一年？」模型先推理需要查配偶，執行搜尋 action，讀 observation，再回答。

Chain-of-Thought Prompting Elicits Reasoning · arXiv:2201.11903ReAct: Synergizing Reasoning and Acting · arXiv:2210.03629

092023–2024PART 2 · 工具與執行

Function calling：工具呼叫變成 API 原生能力

新能力

結構化工具輸出

2023-06 OpenAI 讓開發者用 JSON Schema 描述函式，模型輸出結構化參數；2024-08 Structured Outputs 強化 schema 保證（strict）。

解決的瓶頸

靠 prompt 要求輸出 JSON 不穩

格式不穩定、欄位亂掉是早期 tool use 的大痛點；原生 function calling 讓格式變契約。

仍沒解決

執行仍是應用程式的事

模型只「選擇函式 + 產生參數」；真正執行、錯誤處理、權限、prompt injection 防護都要自己寫。

例子

get_current_weather(location, unit)

使用者問天氣，模型輸出函式名稱與 JSON 參數，由你的後端執行後把結果回傳。

102023–2024PART 2 · 工具與執行

Long context：把「更多任務狀態」一次放進上下文

新能力

128K → 200K → 1M

GPT-4 Turbo 128K（2023-11）、Claude 2.1 200K（2023-11）、Gemini 1.5 Pro 1M（2024-02）：整本書、長影片、大型 repo 可一次放入。

解決的瓶頸

長文件 / 長對話 / repo 分析需切片與 RAG

過去要切 chunk、維護向量庫；長上下文讓「先讀完再想」成為可能。

仍沒解決

長 ≠ 好

lost-in-the-middle、成本、延遲；內容選擇與組織仍是工程問題，不是把全部丟進去就好。

例子

數百頁規格書找矛盾

一次放入合約或規格全文，要求模型摘要或找出條款矛盾。

Demo 很多，落地很少：agent 的評測缺口

新能力

Autonomous harness 普及

AutoGPT 等把「目標 → 拆解 → 工具 → 觀察 → 迭代」變成可執行程式，agent 從 prompt demo 走向程式。

可靠性差、容易循環、成本高

122024PART 2 · 工具與執行

Harness 與 ACI：把 agent loop 變成工程

新能力

為 LLM 設計介面（ACI）

SWE-agent 提出 Agent-Computer Interface：為模型設計搜尋、開檔、編輯、跑測試的專屬命令介面；LangGraph 把 stateful / cyclic 流程圖形化。

解決的瓶頸

直接給 shell / editor 容易迷路；線性 chain 無法重試

模型需要「對的介面」而不是「完整的電腦」；迴圈、分支、human-in-the-loop 需要顯式 runtime。

仍沒解決

patch 仍會錯

工具選擇、權限、安全、錯誤恢復仍是應用責任；框架不保證推理正確。

例子

修 repo 的迴圈

讀 issue → 搜尋相關檔案 → 編輯 → 跑測試 → 依錯誤訊息修正 → 輸出 patch。

132024-11-25PART 2 · 工具與執行

MCP：工具與資料的「標準插座」

新能力

開放協議：Model Context Protocol

Anthropic 開源 MCP，統一 AI 應用與工具、資料、工作流的連接方式；2025-06 規格加入 HTTP transport 與授權流程。

解決的瓶頸

M×N 整合問題

每個 app × 每個資料源都要寫客製 integration；MCP 讓「一個 server 接所有 client」。

仍沒解決

協議不保證安全

權限最小化、工具行為安全、prompt injection 防護、企業治理仍要自己設計。

例子

Claude Desktop 接 MCP server

透過 MCP 連到本機檔案、GitHub、Slack 或資料庫，而不是每個 client 各自寫 plugin。

14釐清PART 3 · 分層架構

別把這些當成一條線：MCP → A2A → Harness → Skill 不是取代關係

MCP

Agent ↔ 工具 / 資料

連「外部的東西」：檔案、DB、API、工作流。

A2A

Agent ↔ Agent

跨系統的發現、溝通、任務委派——不是 MCP 的下一代，是旁邊的一層。

Harness

執行與狀態

planning、loop、state、sandbox、checkpoint。2024 前就存在的實務，2025–26 走向 production。

Skill

程序知識封裝

可被 harness 載入、可經 MCP 用工具、可被多 agent 共享——是 packaging layer，不是時間上的下一階段。

真正的基本型態

Loop 不是最終章節

Anthropic 2024-12 定義：agents = “LLMs autonomously using tools in a loop”。Loop 是起點；進步在於讓 loop 可觀測、可評估、可恢復。

正確認知

同時成熟

不是「A 取代 B」，而是每一層在各自的位置上變強、變標準、變可管理。

162025-04-09PART 3 · 分層架構

A2A：agent 與 agent 之間的開放協議

新能力

Agent2Agent（A2A）

Google 發布跨供應商、跨框架的 agent 發現、溝通、委派協議；2025-06-23 捐給 Linux Foundation，AWS、Microsoft、Salesforce、SAP 等加入。

agent 被綁在單一 orchestrator / 產品內

仍沒解決

互通 ≠ 可靠

任務分解品質、長程記憶、權限控管、結果驗證、商業責任歸屬都還要自己設計。

例子

企業 HR agent

HR agent 透過 A2A 查詢另一個負責招募排程的 agent，不必把所有功能塞進同一個 agent。

172025-09-29PART 3 · 分層架構

Context engineering：給「對的上下文」，比給「長上下文」重要

新能力

上下文成為一門工程

Anthropic 定義 agents = “LLMs autonomously using tools in a loop”，並把成敗關鍵指向：每一步給模型什麼。

解決的瓶頸

長上下文 ≠ 好上下文

repo 結構、測試輸出、錯誤回饋、歷史壓縮、失敗原因——組織這些比「塞更多」有效。

仍沒解決

高度依賴任務與環境

沒有萬用配方；錯誤上下文會放大錯誤決策，需要持續量測與調整。

例子

Coding agent 需要什麼

不只 prompt，還有最近修改、失敗原因、任務 checklist、下一步計畫——人類工程師 onboarding 的資訊，模型同樣需要。

192025–2026PART 3 · 分層架構

Long-running harness：從 single-shot 到可跑 25 小時的同事

新能力

跨 context window 的長任務

Effective harnesses（2025-11）；OpenAI Shell + Skills + Compaction（2026-02）把可執行環境、程序知識、伺服器端壓縮變成長跑 agent 的基礎原語；Codex 展示 25 小時任務。

單次 prompt 撐不起真實工作

仍沒解決

長時間累積錯誤

checkpoint、人工 steering、權限隔離、成本控制、測試與 rollback 都要設計；「跑得久」不自動等於「跑得好」。

例子

25-hour Codex run

agent 讀 repo、修改程式、跑測試、保存中間 artifact；人類在 milestone 介入審查，而不是逐行指揮。

202026PART 3 · 分層架構

Evaluation loop：怎麼知道 agent「真的變好」

新能力

Agent evals 成為開發迴圈

Anthropic《Demystifying evals for AI agents》（2026-01）：不只測最終答案，也測軌跡、工具選擇、失敗處理、邊界案例；OpenAI 把 skills 也納入 eval regression。

解決的瓶頸

多步、非決定性、環境依賴的行為難以驗證

只看最終答案不夠；需要把 expected behavior 明確編碼成測試。

仍沒解決

測資污染、覆蓋不足、judge 偏誤

LLM-as-judge 需要校準與抽樣人工審核；eval 設計錯誤會得到「假的可靠性」。

例子

採購 agent

不只檢查有無生成採購單，也檢查是否查過合約、是否遵守金額門檻、缺批准時是否停止。

23迷思PART 3 · 分層架構

五個常見迷思

「A2A 是 MCP 的下一代」

錯。不同層：MCP 連工具與資料，A2A 連 agent 與 agent。

「Skills 是咒語，加了就變強」

錯。沒有清楚說明、範例、測試與正確載入時機，skill 只是文件。

「Loop 是 2026 的新功能」

錯。Loop 是 agent 的基本型態；進步在於可觀測、可評估、可恢復。

「上下文越長越好」

錯。選擇與組織才是重點；長上下文會稀釋注意力、放大成本。

「Eval 只是刷 benchmark」

錯。Eval 是開發迴圈與 release gate；設計不好會得到假的可靠性。

24CONCLUSIONVerified outcomes

結論

從「提示模型」，到「建構能驗證成果的系統」。

模型仍在預測下一個 token；系統讓它反覆抵達已驗證的 outcomes。歷史是堆疊不是取代——每一層都要設計，評估是最後一哩。
