模型決定天花板

再好的工程也補不了模型做不到的事；但只換模型，也補不了上下文與工具的洞。

工程決定達成率

上下文組織、工具介面、執行迴圈——同一模型，達成率可以差好幾倍。

評估決定能不能相信

沒有 eval，你只是在賭；有 eval，你才能談「變好」。例：同一個模型，接上 CRM 工具 + 政策 skill + eval，才能當客服。

核心心智模型：能力 ≈ 模型 × 上下文 × 工具 × 迴圈 × 評估——任何一項是零，結果就是零。換模型的邊際效益遞減之後，組織、介面與驗證才是拉開差距的地方。

032017PART 1 · 模型能力

Transformer：讓「大規模訓練」變成可能

解決的瓶頸

RNN 逐字處理、無法平行、長距離依賴梯度衰減——規模與速度都卡死。self-attention 讓任意兩個位置直接互相注意，且兩兩之間的相關度可以同時計算（平行化），打開「更大模型 × 更大資料」的路。

仍沒解決

它只是更好的序列模型：不保證事實正確、可控性、安全或可驗證。把「文字接龍」變成「會做事的系統」，還需要接下來七年一層層補。

例子

翻譯一句話時，模型同時注意主詞、動詞與遠距修飾語，而不是像 RNN 按順序硬記——長距離依賴不再是瓶頸。

訓練 vs 推論：訓練時餵入大量文字、逐步更新權重去學規律（一次看整個 batch，可平行）；推論時權重凍結，只產生文字。之後的 GPT、BERT 都是建立在 Transformer 之上；後來的擴散模型（diffusion）也用類似的自監督精神——訓練時對圖片逐步加雜訊、再學怎麼還原（denoising），就像 LLM 學「遮住的下一個字」。
當年的時代論述：模型越深、權重越多，表現越好——「大力出奇蹟」的 scaling 路線從這裡確立，一直到現在都還在比參數量。

解決的瓶頸

過去 NLP 是「每個任務一個專用模型」：標註、訓練、部署成本極高。生成式預訓練讓語言能力先從巨量文字學好，任務只需輕量疊加——同一模型可遷移到多種任務。

仍沒解決

模型會產出流暢但可能虛構的文字——事實錯誤、偏見、幻覺從這裡就內建。且要穩定完成特定任務，仍需 prompt 或 fine-tune。

例子

重要澄清：模型不是「直接生字」——是先把上下文變成向量，再在詞彙表上選機率最高的一個。接龍的本質是「在語意空間裡走一步」。

術語：zero-shot＝只給任務說明、沒有範例；few-shot＝給 1～幾個範例。兩者都不改權重。

解決的瓶頸

在 ICL 之前，transfer learning 靠 fine-tuning：每個任務要標註資料、加上任務專用層、再花 GPU 訓練一次。成本對照：光 GPT-3（175B）的訓練，外部粗估約 460 萬美元、355 GPU-年；Meta 的 LLaMA-65B 也要 2,048 顆 A100 跑 21 天。ICL 把「教新任務」變成「寫一段 prompt」——成本下降幾個數量級。

仍沒解決

對 prompt 措辭與範例順序極度敏感；推理、事實性不穩。更根本的：正確性的 bottleneck 在「context 是否涵蓋了正確的資訊」——沒放進去，再會接龍也答不對。

例子

放幾組「英文 → 法文」範例，新句子直接照樣翻譯。整個過程中模型的權重完全沒動。

ICL 證明了「能力可以不靠訓練、只靠輸入」——這是後來所有 prompt / context 工程的種子。

文件庫先全部轉成 embedding
→

（index → 原文）

解決的瓶頸

模型「背過」的知識會過時、查不到冷門細節、還會自信地編。RAG 把檢索器接到生成之前：先找證據，再讓模型看著證據回答，知識密集任務大幅改善。

仍沒解決

檢索錯誤 → 答案錯誤；模型仍可能曲解文件、斷章取義、編造不存在的引用。有檢索 ≠ 可驗證——證據鏈要自己設計。

例子

最早的 coding agent（如 GitHub Copilot）也是類似原理去撈要修改的 lib 程式碼片段；但常常 reference 不到正確的 lib，LLM 就開始幻覺亂掰——同樣的問題出現在各種文件檢索、搜尋任務。

痛點衍生出整族解法：HyDE（先虛構答案再檢索）、Rerank（檢索後重排）、RAG-Fusion、Self-RAG（自己評估要不要檢索）、GraphRAG（知識圖譜結構化）等，都是為了讓「撈到的東西更準」。

RAG 是「外部記憶」的開端：把知識從模型參數裡搬出來，放回文件庫——所有企業知識庫方案都長在這一層。

先別被名字嚇到：Reinforcement learning（強化學習）一直是 ML 的重要技巧——從 DQN 玩遊戲（2013）到 AlphaGo 下圍棋（2016），核心都是「靠回饋讓模型變好」。RLHF 只是把同樣的概念，套在 LLM 外層、用「人類偏好」當回饋信號。FLAN 則先用多種指令任務 fine-tune，讓 zero-shot 指令遵循更穩。

先講「怎麼想」：CoT 之前還有 planning mode（Plan-and-Solve：先擬「拆成子任務的計畫」再照計畫執行），專治整陀塞進去時常見的 missing-step（漏步驟）——同樣一份 SOP，拆成步驟一步步給，就是比整陀丟進去可靠。ReAct 再往前一步：邊想邊做，做完再看、看完再想。

解決的瓶頸

CoT 解決「直接跳結論」：要求先產生中間步驟，多步推理與可解釋性都改善（例：GSM8K 數學題，直接答常錯、要求「一步一步想」大幅進步）。ReAct 更進一步：讓推理與行動交錯——需要資料就去查，看了結果再決定下一步，模型第一次真正「動手」。

仍沒解決

中間步驟可能是事後合理化的產物，不是真實內部推理；工具可能選錯、觀察可能讀錯、行動可能有副作用。會想會做，不代表做得對。

例子

「某演員的配偶出生在哪一年？」模型先推理「需要查配偶」，執行搜尋 action，讀 observation，再收斂答案——這就是 agent loop 的雛形。

日常對照：一份 SOP 整陀丟 vs 拆成步驟一步步給，後者明顯可靠——prompt 結構本身就是工程。

這裡才是 agentic 的分水嶺：既然 LLM 只會推論、文字接龍，那就讓它產出「步驟 + 工具呼叫」，由外面的程式去執行——一個會 parse 關鍵字的 script，就是最簡易的 harness。

解決的瓶頸

早期靠 prompt 要求輸出 JSON、或 parse 關鍵字——格式不穩、欄位亂掉是家常便飯。Function calling 讓格式變契約：模型輸出結構化參數，工程端直接讀欄位。

仍沒解決

模型只負責「選函式 + 生參數」，真正執行、錯誤處理、權限檢查、prompt injection 防護全是應用程式的事——介面標準了，安全邊界沒有。

例子

自然語言驅動的測試工具（如 TestRigor）：用 plain English 描述「登入 → 點購物車 → 結帳」，看起來是用自然語言操作網頁，其實是把情境翻譯成白箱測試 code 去執行。

「讓 LLM 產出可執行的步驟」是 agent 的起點——從 parse 關鍵字到結構化 tool_calls，進步的是工程化程度，不是魔法。

Harness 與 ACI：把 agent loop 變成工程

LLM規劃 + 推理
↑↓命令與結果
ACI 介面搜尋 · 開檔 · 編輯 · 跑測試
為 LLM 設計的受控命令面
↑↓受限的操作
環境檔案系統 · shell · 測試
ACI 的核心思想：不要給模型整台電腦，給它一套精心設計的工具——限制反而是生產力。

解決的瓶頸

直接給模型 shell / editor 很容易迷路——它不知道哪些檔案重要、怎麼安全編輯。SWE-agent 提出 ACI：為 LLM 設計「搜尋、開檔、編輯、跑測試」的專屬命令介面；LangGraph 則把 stateful / cyclic 流程圖形化，重試與分支變成一等公民。

仍沒解決

patch 仍會錯；工具選擇、權限、安全、錯誤恢復仍是應用責任。框架解決「迴圈怎麼跑」，不解決「迴圈跑得好不好」。

例子

修 repo 的標準迴圈：讀 issue → 搜尋相關檔案 → 編輯 → 跑測試 → 依錯誤訊息修正 → 輸出 patch——每一步都經過 ACI 這道受控的門。

Harness 的價值不是「更強的模型」，而是「給模型一間不會弄壞的工作室」——介面設計決定 agent 能做什麼。

132024-11-25PART 2 · 工具與執行

MCP：工具與資料的「標準插座」

解決的瓶頸

每個 app × 每個資料源都要寫客製 integration，是 M×N 的整合地獄。MCP 把中間抽成一個標準協議：寫一次 MCP server，所有支援的 client 都能用——整合成本從 M×N 降到 M+N。

仍沒解決

協議只定義「怎麼連」，不保證「連了安不安全」：權限最小化、工具行為審計、prompt injection 防護、企業治理都要自己在 server 端設計。

例子

23迷思PART 3 · 分層架構

五個常見迷思（其實是六個）

「A2A 是 MCP 的下一代」

錯。兩者解決不同的問題：MCP 連 agent 與工具 / 資料，A2A 連 agent 與 agent。它們是鄰居，不是前後任。

不同層的協議，各司其職

「Skills 是咒語，加了就變強」

錯。沒有清楚的說明、範例、測試與正確載入時機，skill 只是一份文件。包裝 ≠ 能力保證。

品質靠說明 + 測試 + 紀律

「Loop 是 2026 的新功能」

錯。Loop（想 → 做 → 看）是 agent 的基本型態，2022 的 ReAct 就是它。進步在於讓 loop 可觀測、可評估、可恢復。

進步在讓 loop 可信，不是發明 loop

「上下文越長越好」

錯。選擇與組織才是重點；長上下文會稀釋注意力（lost-in-the-middle）、放大成本。對的上下文 > 長上下文。

組織取代長度

「Eval 只是刷 benchmark」

錯。Eval 是開發迴圈與 release gate：改 harness、改 skill、換模型都要回歸。設計不好會得到假的可靠性。

是治理，不是行銷

「多 agent 一定比單一 agent 強」

錯。多 agent 帶來協調成本、重複工作、錯誤傳播與成本膨脹——Anthropic 的 multi-agent 實戰結論是「不是任務越多 agent 越好」。

先證明單一 agent 跑不動，再拆

迷思的共同根源：把「層」當成「路線」、把「包裝」當成「能力」、把「長度」當成「品質」——每一題回到六層架構對照，答案自然浮現。

從「提示模型」，到「建構能驗證成果的系統」。
