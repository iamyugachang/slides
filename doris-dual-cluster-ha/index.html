02前提與約束

兩個 catalog、兩條寫入路——使用者程式不可控

Raw Zone（受控）

  • 寫入 100% Kafka + Spark Structured Streaming，可源頭重放
  • 4.x Unique Key 預設 MoW——重放冪等的底

Curated Zone（開放）

  • User Apps（統稱，含 BI，皆 JDBC）直寫：可查兩 zone、只能寫 curated
  • 不經 Kafka、不必然可從 raw 重算；程式不可控——平台唯二控制面＝連線端點（VIP）／（選配）client library

C-1

CCR 不再維護；4.1 更無對應 syncer

C-2

MinIO 不穩——不碰物件儲存/存算分離

C-3

RPO/RTO 未定——工作假設：30 分內、人工切換

節點級 HA Doris 自理；本研究只解「整座掛掉」。

03評估主軸

四個需求情境 R1–R4——所有方案用它們評優缺點

R1 快速 failover

一座斷掉能切到另一座；≤30 分鐘、接受人工切換——人決策、機器一鍵執行。

R2 斷後不能查到「錯」資料

拆兩類：舊（落後秒/分，可容忍要定數字）vs 錯（重複/半批/矛盾，零容忍靠機制）。特有風險：跨 zone join 時間差。

R3 寫入資料要一致

Spark→raw、Apps→curated 兩路在兩座間一致——落差要可量測、可告警。

R4 恢復之後資料要一致

故障座歸隊：補齊、對帳通過、安全切回。

邊界不涵蓋「程式 bug 寫髒資料」（雙活不防，靠重放）與「Kafka 自身故障」（前提依賴）。
先對齊「要保什麼」——每個方案的優缺點都按 R1–R4 講。

查證 ①：CCR——治理惡化，且 4.1 根本不在支援矩陣

F-1官方 2026-07-29 把 CCR 文件從 3.x/4.x/dev 整批下架（PR #4018）

05關鍵查證

查證 ②：Spark 寫入語義（精確版）——MoW 冪等是必要兜底

官方說法

  • 文件宣稱 2PC 可達 checkpoint 級 exactly-once
  • 但 2PC 歷史上有 txn 超時靜默丟數 bug（#205，已修）與運維坑

兩個保護不到的洞

  • 官方 PR #364 自承 client retry 段非 exactly-once（修復未發版）
  • 跨 restart 的 label 非決定性——重放去重失效，不在 2PC 範圍
結論表模型冪等不是可選項：Unique Key MoW（4.x 預設）承擔重放去重；Duplicate / SUM Aggregate 表重放必髒——存量清查是 PoC 第一項。
connector 的保證有邊界——架構不能把正確性押在邊界內側。

11第二部 · 推薦架構

推薦架構總圖：Hot-Standby 服務 ＋ 雙活資料

定位：ingestion（raw）＝Active-Active；服務面（query＋curated 寫入）＝Active-Standby（VIP 單活）。刻意不做全 AA——雙邊寫 curated 是無仲裁的雙主衝突。可選延伸：唯讀報表分流 B 座。
單活服務、雙路資料——接下來四頁：這套架構如何應對 R1–R4。

12情境檢驗

R1 快速 failover：人只做一件事——翻 flag

B 的 ingestion 本來就在跑（零動作、raw 零遺失）；User Apps 讀寫都經 VIP，自動跟切。30 分鐘預算：告警 2 分 → 值班上線 10 分 → 判讀 5 分 → 一鍵切換 2 分 → 驗證 5 分 ≈ 24 分——前提是演練過。
人工切換成立的條件：監控先把答案算好（p.20）。

13情境檢驗

R2 查詢正確性：「錯」已由機制消除，剩「時間差」要管理

重複＝MoW 冪等消除；半批＝寫入原子性消除。殘留：raw（秒）與 curated（鏡像時點）兩種「舊法」不同——跨 zone join 在切換窗口可能矛盾。手段：縮短鏡像間隔＋切換公告資料時點。
對業務的問法：「切換瞬間 curated 舊 N 分鐘，可以嗎？」——N 是要他們拍板的數字。

14情境檢驗

R3 寫入一致：協議面（raw）＋搬運面（curated）＋驗證面（對帳）

raw：同源重放＋MoW 冪等（協議保證）。curated：常駐鏡像——每 N 分鐘搬變動 partition、記錄各表鏡像時點；loss window ＝ 設計值（頻率＋單輪耗時，與業務議定）＋監控（即時顯示、超標告警）。對帳 job 對兩座逐 partition 比對兜底。
一致性可以是「驗證出來的」——前提是落差可量測、可告警。

15情境檢驗

R4 恢復後一致：raw 續讀、curated 反向鏡像、對帳把關

A 歸隊：raw 從自己 checkpoint 續讀（retention 窗口內天然追平）；curated 反向鏡像 B→A、A 座禁寫由端點層強制（VIP 只指 B，使用者連不到 A）；對帳全綠才擇時切回。超窗重建：Multi-Catalog 全量搬（4.1 唯一路徑）。
每次故障都會經歷 failback——它是流程，不是意外。

17保留可能性

若仍要走 CCR：自維護的三大卡點與五筆帳

① 接手欠帳 repo

issue 關閉率 33%、存量 31；商業版修的 bug 開源看不到——要自己重踩一次

② 升版強耦合

鐵律 Syncer ≥ 下游 ≥ 上游：每次升 Doris 前必須先移植 syncer，不可跳過；4.1 這次無上游可抄

③ 技能門檻

2.2 萬行 Go 核心＋要讀 Doris FE（Java）對照 binlog——雙重稀缺技能

五筆帳E0 移植 4.1（1–2 人月・風險最高）→ E1 接手 2–3 人月 → E2 穩態 0.3–0.5 FTE/年 → E3 每次升級 0.5–3 人月 → E4 常備雙叢集測試環境。首年 3–5 人月＋年化 0.4–0.6 FTE。實作範例（真實 PR 足跡：新增 DDL 14 檔／改邏輯 6 檔／加功能 11 檔）在報告第三部。
4.1 上沒有「凍結版本」的中間態——用 CCR 就是維護 CCR。

18落地前提

三個硬前提：沒滿足前，方案不成立

① 存量表模型清查

  • 4.x 新表預設 MoW ✓
  • 存量 Duplicate / SUM 表重放必髒——MoW 不可事後切換，改造＝重建表

② Kafka retention

  • ≥ 最長離線＋追平＋餘量 → 14–30 天
  • Kafka 升格一級依賴，其 HA 重新體檢

③ 對帳與鏡像先行

  • 雙路無協議兜底——對帳是方案的一部分
  • curated 鏡像頻率＝業務容忍窗口
最大改造項＝存量表模型盤點——PoC 第一項、go/no-go。

19落地設計

Curated 深看：單邊寫＋常駐鏡像＋可量化 loss window

解法主體（CU-2）

  • app 只寫一座（VIP 指誰寫誰）——刻意單邊寫，不可控的使用者無法參與任何雙寫協議
  • 常駐鏡像 job：每 N 分鐘搬變動 partition 到備座、記錄各表鏡像時點
  • failback：反向鏡像 B→A＋端點層禁寫

誠實的代價與出路

  • failover 丟「上次鏡像之後」的 app 寫入——要業務拍板容忍幾分鐘
  • 若答案是「一分鐘都不能丟」→ 唯一值得考慮 p.17 成本的情境
  • 根治＝CU-6（寫入改道 Kafka）——但採用時程不可控，列中期
目標不是消滅 loss window，是把它變小、變可量測、變成業務同意過的數字。
