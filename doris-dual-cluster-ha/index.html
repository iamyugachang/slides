01DATA PLATFORM · HA DESIGN REVIEW

Doris 雙叢集 HA：
方案評估與推薦

兩座獨立 Doris cluster，任一座整座故障時服務可切換——
調查 4 個候選方案、查證 40 項來源，收斂成 1 條推薦路線 + 10 項 PoC。

Doris 2.x · 自建機房 寫入 100% Kafka + Spark Structured Streaming JDBC query 推薦：上游雙路 Ingestion
備援座平時就在寫——故障時 ingestion 零切換、RPO ≈ 0，query 用 proxy 切過去。

02PART 1 · 背景與約束

範圍：叢集層級的 HA——節點級交給 Doris 自己

FE 選主、BE 副本等節點級 HA 由 Doris 內建機制處理，不在本次範圍。本次要解的是「一整座 cluster 掛掉」：query 能切、ingestion 能續、恢復後能歸隊。

C-1 · CCR 停止維護

SelectDB CCR 後續確定不再維護。採 CCR 的方案一律以「fork 原始碼自行維護」計成本——含每次 Doris 升級的 binlog 相容性自行驗證。

C-2 · MinIO 不可依賴

物件儲存只有 MinIO 且不穩定：不採存算分離，任何方案不得把 MinIO 當關鍵依賴。

C-3 · RPO/RTO 未定義

以「分鐘級 RPO、半自動切換」為工作假設；各方案標註不同等級下的適配性。正式定義需業務方拍板。

評估基準兩座資料一致（可容忍落後）· 故障可切換 · failback 流程具體 · DDL/權限/UDF 雙邊一致 · 持續對帳 · JDBC client 低侵入 · 維護成本可控
所有判斷都以這三條約束為前提——違反者直接出局或標註前提成本。

03PART 2 · 關鍵查證

查證 ①：C-1 不只是內部消息——CCR 的公開訊號同樣惡化

F-1Apache Doris 官網 2026-07-29 把 CCR 文件從 3.x / 4.x / dev 文件樹整批下架（doris-website PR #4018，92 個檔案），只剩 2.1 文件保留，且無任何 deprecation 說明。
F-2selectdb/ccr-syncer：最後 commit 2026-04-09（4.5 個月停滯）、2026 年僅 5 個 commit、活躍 maintainer 約 2 人、從未發過 GitHub Release。
F-3SelectDB Enterprise 文件仍完整保留 CCR、持續出 binary——訊號指向「開源側淡出、商業側承接」。Doris 4.x 的替代機制 Binlog/Table Stream 仍是 Preview，未 GA。
F-4版本鐵律：Syncer 2.1.8 / 3.0.4 起不再支援 Doris 2.0——若現行叢集是 2.0.x，CCR 路線連版本門檻都過不了。
對外報告可以直接引用公開證據，不必搬內部消息——CCR 不適合再當長期依賴。

04PART 2 · 關鍵查證

查證 ②：Spark connector 給不了 exactly-once——冪等只能靠表模型

官方自承非 exactly-once

doris-spark-connector PR #364 · 2026-07
  • 「stream load write path is not exactly-once across a client-side retry」——官方原文
  • 修復（retry 重用 label）尚未包含在任何 release（最新 26.0.0 為 2026-04）

Label 非決定性

含 timestamp + JVM 序號
  • job restart 後重放同段 offsets → 全新 label，Doris label 去重完全擋不住
  • 對照：Flink connector 用 checkpoint id 綁 label 才有 exactly-once，Spark 側無等價機制

2PC 的真實定位

sink.enable-2pc · 預設 false
  • 只保 micro-batch 原子可見；epoch 去重僅存 driver 記憶體、跨 restart 不保留
  • 曾有 txn 超時被清、commit 失敗不拋例外的無聲丟數 bug（issue #205）

Label 去重窗口太小

streaming_label_keep_max_second
  • 高頻導入類 label 保留預設僅 12 小時、per-DB 上限 2000 個
  • 不能作為長時間 failback 追資料的冪等依據
結論：冪等必須由表模型承擔——Unique Key（Merge-on-Write）重放天然收斂；Duplicate / SUM Aggregate 重放必髒。

四個候選方案，一頁判定

① Proxy + CCR

主從複製

單寫 A 座、CCR 同步到 B。DDL 自動同步是獨有優點——但 C-1 下要自己養 fork。

不推薦常駐

可當 failback 重建工具

② Client 雙寫

同 job 雙 sink

同一個 Spark job 寫兩座 + client library 決定 query 路由。失敗域耦合、client 全要改。

排除

③ 上游雙路 Ingestion

雙活 · 源頭重放

兩座各跑獨立 Streaming job 消費同一 Kafka topic；query 由 proxy 切換。

推薦主線

④ Backup/Restore 冷備

定期快照

repository 只支援 S3/HDFS（C-2 卡死）；RPO 小時～天級，不符假設。

僅兜底互補

接下來三頁講清楚：①②為什麼出局、③憑什麼贏。

Fork 維護 = 永續跟版

  • 手寫核心 ~2.2 萬行 Go（單檔 job.go 近 5,000 行狀態機）
  • 內嵌 ~1.1 萬行 Doris Thrift IDL——Doris 每次升級都要 regenerate + 適配 + 用完整雙叢集跑 regression
  • 已知靜默 bug：表級任務忽略上游 DROP TABLE（#654）

HA 語意先天不足

  • 非同步複製：RPO 必然非零（正常 lag 秒～33s）；上游 FE 切主會觸發整庫 full sync，期間 RPO 惡化到小時級
  • 無反向同步：failback 只能反向重建全量，官方無 runbook
  • B 座誤寫的資料會在下次 full sync 被原子替換洗掉
判定：不推薦常駐——降級為「超出 Kafka retention 時的一次性重建工具」，用完即拆。

07PART 3 · 方案評估

方案② Client 雙寫：雙寫的位置放錯了

現況只有 Spark 一條寫入路徑，「client 雙寫」實際上 = 同一個 job 內掛兩個 sink。這與方案③的差別是「同 job 雙寫」vs「兩個獨立 job」——逐項比完全面落敗：

失敗域耦合

  • B 座變慢 → 背壓拖垮整條 pipeline，連 A 座一起慢
  • 方案③兩條 pipeline 完全隔離

半批失敗無法收斂

  • A 成功 B 失敗：跳過 → 分歧且 checkpoint 已前進，無法靠源頭重放對齊
  • 整批重試 → 冪等前提照樣要，等於沒省

Query library 侵入全部 client

  • 所有 JDBC 接入方都要改；非 Java client 無解
  • 直接違反「不改連線設定」需求——路由本該收斂到 proxy 層
業界教訓京東：Flink/Spark 雙寫兩座 ClickHouse——公開承認「只能最終一致、業務端複雜度高、切換分鐘級」。攜程也記錄過雙寫一致性做不到。
雙寫值得做的位置在 Kafka 之後的兩條獨立鏈路——那就是方案③。

08PART 4 · 推薦方案

方案③ 上游雙路 Ingestion：三個狀態，一張圖

故障態：A 整座掛

  • Job A 停擺（無妨）；Job B 完全不受影響、持續寫入
  • Ingestion 側零切換動作；query 半自動切到 B（proxy 翻轉）

恢復態：A 修好歸隊

  • 重啟 Job A，從自己的 checkpoint 續讀 Kafka 追平
  • 對帳確認追平 → 低峰期把 query 切回
Spark 的 Kafka source 自管 offset、不依賴 consumer group——兩條鏈路天然互不干擾。

09PART 4 · 推薦方案

憑什麼贏：四個結構性優勢

① Ingestion RPO ≈ 0、零切換

備援座平時就在寫，A 故障不會讓 B 丟任何資料；唯一的「落後」是 B 自身秒級處理延遲。CCR 類主從複製在數學上做不到這件事。

② 唯一同時避開 C-1 與 C-2

不依賴 CCR、不碰物件儲存。四個方案裡只有它不用對任何一條硬性約束付前提成本。

③ 現況正是理想前提

寫入 100% 走 Kafka + Spark、無旁路——「源頭重放」不需要對任何例外路徑打補丁。這個條件很多團隊沒有，我們剛好有。

④ 元件全部自主可控

新增的只有第二套 job、proxy 層、對帳工具——常規工程，沒有外部黑盒、沒有 fork 要養。

京東（雙寫兩座 OLAP）與攜程（多寫 + 一致性巡檢 job）都驗證過同構模式的長期可運維性。

10PART 4 · 推薦方案

代價講清楚：三個硬前提——沒滿足前方案不成立

① 表模型收斂 Unique Key MoW

  • 重放冪等只在 Unique Key（Merge-on-Write）成立——UPSERT 覆蓋、天然收斂
  • Duplicate 表重放 = 重複行；SUM Aggregate = 重複累加
  • 注意：2.0 預設是 Merge-on-Read，要顯式開 MoW；2.1 起才是預設

② Kafka retention 政策

  • retention ≥ 最長離線時間 + 追平耗時 + 餘量
  • 預設 7 天不夠，建議關鍵 topic 拉到 14–30 天
  • Kafka 升格為兩座的共同上游——其 HA 等級要重新審視

③ 對帳先行

  • 雙路寫入沒有複製協議兜底——分 partition 的 count + sum(hash) 對帳是唯一一致性防線
  • 搭配 DDL 統一入口（版本化 migration 對兩座執行 + drift 偵測），涵蓋權限/UDF
最大改造項是表模型盤點與遷移——工作量取決於現況有多少 Duplicate / SUM 表，PoC 第一項就是它。

路徑 A：CCR 一次性搬遷

以活座為源全量搬到重建座，用完即拆、不常駐——C-1 成本壓到最低。前提：Doris 2.1.8+。

路徑 B：Multi-Catalog INSERT INTO SELECT

分 partition 搬，慢但零額外元件（錢大媽採 CCR 前的做法）。fork 不堪用時的保底。

重建完成後把 checkpoint 重置到重建涵蓋的 offset 水位，再啟動增量——縫合點靠 Unique Key 冪等吸收重疊。

14PART 5 · 總結

誠實面對：方案③防什麼、不防什麼

殘餘風險（要管理）

  • Kafka 是共同上游單點：掛了兩座都停寫（query 不受影響）——Kafka 的 replication / min.insync.replicas 升格為一級依賴
  • 靜默漂移：兩條 pipeline 的 code/設定/UDF 版本漂移不會報錯——唯一防線是對帳 + 同 artifact 部署紀律
  • 雙座同時異常：需實體隔離（機櫃/電力/網路）壓低相關性

明確不防（要別的防線）

  • 程式 bug 同毒兩座：兩座跑同一份 code——本方案防機器故障、不防邏輯錯誤；靠 Kafka retention 重放修復＋（未來有 HDFS 時）週級冷備
  • Split-brain：寫入側天然無主從爭議；殘留在 query 決策層——用集中式 flag + VRRP 單活收斂
切換體感切到 B 座瞬間可能讀到落後數秒的資料、與剛才 A 座結果不完全一致——多數分析場景可接受，需業務方明確確認。
「都在寫、但寫得不一樣」是這個架構唯一的深水區——所以對帳不是配件，是方案的一部分。

15PART 6 · 下一步

PoC 清單：P01 是 go / no-go

P01表模型盤點 + MoW 壓測——Duplicate/SUM 表有多少、主鍵可得性、MoW 導入吞吐 vs 現況。直接決定方案成立與改造規模。
P02重放冪等驗證——kill -9 重啟 + 回捲 checkpoint 大範圍重放，對帳驗證零重複零遺漏
P032PC 行為驗證——延遲影響、長 batch 逼近 txn timeout（#205 情境）
P04external-check 腳本——三層探測 + 集中 flag；量測斷電到切換完成的實際 RTO
P05keepalived VIP 演練——nopreempt、VRRP 防火牆、各語言連線池重連行為
P06雙座落後量測——水位心跳表上線，給業務 p50/p99 的「切換回退幾秒」實數
P07追平演練——停 24h 重啟，量測追平耗時 → 反推 Kafka retention 目標值
P08整座重建演練——CCR 一次性搬遷 vs Multi-Catalog 兩條路各走一遍
P09對帳工具 MVP——分 partition count + sum(hash)，跑滿一週看誤報率
P10DDL pipeline——migration 對兩座執行 + 失敗阻斷 + 每日 drift 偵測
P01 → P02 → P07 三項做完，就能對「方案成不成立、retention 要買多少」給出有數字的答案。

16PART 6 · 下一步

帶走四個問題——需要業務方 / 管理層拍板

Q1 · RPO / RTO 正式定義

本評估以「分鐘級 RPO、半自動切換」為假設。若要秒級 RTO 全自動，query 層要追加自動決策——風險升級，建議分階段。

Q2 · 切換時的讀一致性容忍

切換瞬間可能讀到落後數秒的資料——報表/分析通常可接受；交易對帳類查詢需明確確認。

Q3 · 兩座的實體隔離度

同機房同電力？機房級事件下兩座相關性高，方案價值打折；跨機房則要另評 Kafka 位置與網路。

Q4 · 表模型改造的業務影響

Duplicate 補主鍵、SUM 表改明細——涉及下游查詢改寫的範圍與排期。

配套提醒：若現行為 Doris 2.0.x，建議把升級 2.1.8+ 納入本架構配套（CCR 重建工具與 MoW 預設都綁 2.1+）。完整報告（各方案 10 問逐項回答、40 項來源）另附連結。
模型負責算，架構負責活。先做 P01——那是整個方案的 go / no-go。
