02背景與約束

範圍：叢集層級的 HA——與兩個 zone 的現況

Raw Zone（受控）

獨立 catalog
  • 寫入 100% 來自 Kafka + Spark Structured Streaming，無旁路
  • Kafka 是 raw 的唯一事實來源，可源頭重放

Curated Zone（開放）

獨立 catalog
  • 開放使用者自由操作：自建 ETL、ad-hoc 寫入、自建表
  • 寫入路徑不受控——「單一路徑」假設對它不成立，策略須分開評估

C-1

CCR 官方後續不再維護——採用即以 fork 自維護計成本

C-2

MinIO 不穩定——不採存算分離、不依賴物件儲存

C-3

RPO/RTO 未定——以「分鐘級 RPO、半自動切換」為工作假設

節點級 HA（FE 選主、BE 副本）Doris 自理；本次只談「整座掛掉」。

F-2selectdb/ccr-syncer：最後 commit 2026-04-09（4.5 個月停滯）、2026 年僅 5 個 commit、活躍 maintainer 約 2 人、從未發過 GitHub Release。

F-4版本鐵律：Syncer 2.1.8 / 3.0.4 起不再支援 Doris 2.0——若現行叢集是 2.0.x，CCR 路線連版本門檻都過不了。
對外報告可以直接引用公開證據，不必搬內部消息——CCR 不適合再當長期依賴。

04關鍵查證

查證 ②：Spark connector 給不了 exactly-once——冪等只能靠表模型

官方自承非 exactly-once

doris-spark-connector PR #364 · 2026-07
  • 「stream load write path is not exactly-once across a client-side retry」——官方原文
  • 修復（retry 重用 label）尚未包含在任何 release（最新 26.0.0 為 2026-04）

Label 非決定性

含 timestamp + JVM 序號
  • job restart 後重放同段 offsets → 全新 label，Doris label 去重完全擋不住
  • 對照：Flink connector 用 checkpoint id 綁 label 才有 exactly-once，Spark 側無等價機制

2PC 的真實定位

sink.enable-2pc · 預設 false
  • 只保 micro-batch 原子可見；epoch 去重僅存 driver 記憶體、跨 restart 不保留
  • 曾有 txn 超時被清、commit 失敗不拋例外的無聲丟數 bug（issue #205）

Label 去重窗口太小

streaming_label_keep_max_second
  • 高頻導入類 label 保留預設僅 12 小時、per-DB 上限 2000 個
  • 不能作為長時間 failback 追資料的冪等依據
結論：冪等必須由表模型承擔——Unique Key（Merge-on-Write）重放天然收斂；Duplicate / SUM Aggregate 重放必髒。

10第二部 · 深評

深評 S-1（CCR）：技術能跑，但你要養它一輩子

Fork 維護 = 永續跟版

  • 手寫核心 ~2.2 萬行 Go（單檔 job.go 近 5,000 行狀態機）
  • 內嵌 ~1.1 萬行 Doris Thrift IDL——Doris 每次升級都要 regenerate + 適配 + 完整雙叢集 regression
  • 已知靜默 bug：表級任務忽略上游 DROP TABLE（#654）

HA 語意先天不足

  • 非同步複製：RPO 必然非零；FE 切主觸發整庫 full sync，期間 RPO 惡化到小時級
  • 無反向同步：failback 只能反向重建全量，官方無 runbook
  • B 座誤寫的資料會在下次 full sync 被原子替換洗掉
判定：不推薦常駐——降級為「超出 Kafka retention 的一次性重建工具」，用完即拆。

11第二部 · 深評

深評 S-4（雙寫）：雙寫的位置放錯了

raw zone 只有 Spark 一條寫入路徑，「client 雙寫」實際上 = 同一個 job 內掛兩個 sink。與 S-2 的差別是「同 job 雙寫」vs「兩個獨立 job」——逐項比全面落敗：

失敗域耦合

  • B 座變慢 → 背壓拖垮整條 pipeline，連 A 座一起慢
  • S-2 兩條 pipeline 完全隔離

半批失敗無法收斂

  • A 成功 B 失敗：跳過 → 分歧且 checkpoint 已前進，無法靠源頭重放對齊
  • 整批重試 → 冪等前提照樣要，等於沒省

Query library 侵入全部 client

  • 所有 JDBC 接入方都要改；非 Java client 無解
  • 路由本該收斂到 proxy 層
業界教訓京東：Flink/Spark 雙寫兩座 ClickHouse——公開承認「只能最終一致、業務端複雜度高、切換分鐘級」。攜程也記錄過雙寫一致性做不到。
雙寫值得做的位置在 Kafka 之後的兩條獨立鏈路——那就是 S-2。

推薦 S-2（雙路 Ingestion）：三個狀態，一張圖——覆蓋 raw zone

獨立消費進度

故障態：A 整座掛

  • Job A 停擺（無妨）；Job B 完全不受影響、持續寫入
  • Ingestion 側零切換動作；query 半自動切到 B（proxy 翻轉）

恢復態：A 修好歸隊

  • 重啟 Job A，從自己的 checkpoint 續讀 Kafka 追平
  • 對帳確認追平 → 低峰期把 query 切回
Spark 的 Kafka source 自管 offset——兩條鏈路天然互不干擾。curated zone 另有策略（p.15）。

13第二部 · 推薦方案

憑什麼贏：四個結構性優勢

① Ingestion RPO ≈ 0、零切換

備援座平時就在寫，A 故障不會讓 B 丟任何資料；唯一的「落後」是 B 自身秒級處理延遲。CCR 類主從複製在數學上做不到這件事。

② 唯一同時避開 C-1 與 C-2

不依賴 CCR、不碰物件儲存。目錄 9 個方案裡只有它不用對任何一條硬性約束付前提成本。

③ Raw zone 現況正是理想前提

raw 寫入 100% 走 Kafka + Spark、無旁路——「源頭重放」不需要對例外路徑打補丁。這個條件很多團隊沒有，我們的 raw zone 剛好有。

④ 元件全部自主可控

新增的只有第二套 job、proxy 層、對帳與鏡像工具——常規工程，沒有外部黑盒、沒有 fork 要養。

京東（雙寫兩座 OLAP）與攜程（多寫 + 一致性巡檢 job）都驗證過同構模式的長期可運維性。

14第二部 · 推薦方案

代價講清楚：三個硬前提——沒滿足前方案不成立

① 表模型收斂 Unique Key MoW

  • 重放冪等只在 Unique Key（Merge-on-Write）成立——UPSERT 覆蓋、天然收斂
  • Duplicate 表重放 = 重複行；SUM Aggregate = 重複累加
  • 注意：2.0 預設是 Merge-on-Read，要顯式開 MoW；2.1 起才是預設

② Kafka retention 政策

  • retention ≥ 最長離線時間 + 追平耗時 + 餘量
  • 預設 7 天不夠，建議關鍵 topic 拉到 14–30 天
  • Kafka 升格為兩座的共同上游——其 HA 等級要重新審視

③ 對帳先行

  • 雙路寫入沒有複製協議兜底——分 partition 的 count + hash 對帳是唯一一致性防線
  • 搭配 DDL 統一入口（版本化 migration 對兩座執行 + drift 偵測），涵蓋權限/UDF
最大改造項是表模型盤點與遷移——工作量取決於現況有多少 Duplicate / SUM 表，PoC 第一項就是它。

建議組合：CU-2 ＋ CU-4

  • 登記制：重要表登記 → 排程 job 經 Multi-Catalog 鏡像到備座（RPO = 鏡像週期，小時級）＋鏡像後對帳
  • 未登記 = best-effort：災後由使用者以備座的 raw 重算——保障等級變成明確契約
  • 對使用者零侵入、無 CCR 依賴；CU-1 雙跑重算列為 ETL 平台化後的長期方向

三個新增注意點

  • 寫入方向：failover 後使用者只在 B 座寫 curated；A 恢復時先「反向鏡像 B→A 追平＋A 座 curated 禁寫」再切回
  • 對帳分層：raw 全量對帳；curated 只對登記表
  • 切換體感：查 curated 的人切換後看到「上次鏡像時點」——與 raw 的秒級落後不同，要先講清楚
curated 是衍生層：登記的用鏡像保、沒登記的用 raw 重算——保障等級是契約，不是默契。

路徑 A：CCR 一次性搬遷

以活座為源全量搬到重建座，用完即拆、不常駐——C-1 成本壓到最低。前提：Doris 2.1.8+。

路徑 B：Multi-Catalog INSERT INTO SELECT

分 partition 搬，慢但零額外元件（錢大媽採 CCR 前的做法）。fork 不堪用時的保底。

重建後把 checkpoint 重置到重建涵蓋的 offset 水位再啟動增量——縫合點靠 Unique Key 冪等吸收重疊。

長期維運
高：每次升級自行驗證相容
高：耦合排障
中：常規 pipeline
低
結論：S-2 雙路 Ingestion（raw）＋ CU-2/CU-4（curated）；S-1 降級為重建工具，S-4 排除，S-6 兜底。

19第二部 · 總結

誠實面對：防什麼、不防什麼

殘餘風險（要管理）

  • Kafka 是共同上游單點：掛了兩座都停寫（query 不受影響）——其 HA 等級升格為一級依賴
  • 靜默漂移：兩條 pipeline 的 code/設定/UDF 漂移不會報錯——防線是對帳 + 同 artifact 部署紀律
  • Curated 寫入紀律：failover 期間使用者誤寫 A 座 curated → 分歧；需權限鎖或公告紀律（未決）
  • 雙座同時異常：需實體隔離（機櫃/電力/網路）壓低相關性

明確不防（要別的防線）

  • 程式 bug 同毒兩座：raw 兩座跑同一份 code——防機器故障、不防邏輯錯誤；靠 Kafka retention 重放修復＋（未來有 HDFS 時）週級冷備
  • 不可重算的 curated 表：手工修正、外部匯入的表若未登記鏡像，災難即丟失——盤點時要抓出來
  • Split-brain：寫入側天然無主從爭議；殘留在 query 決策層——集中式 flag + VRRP 單活收斂
切換體感raw 落後數秒、curated 落後至上次鏡像——兩種不同的回退幅度，都要先跟使用單位講好。
「都在寫、但寫得不一樣」是唯一深水區——對帳不是配件，是方案的一部分。
