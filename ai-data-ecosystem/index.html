05PART 2 · 逐組對照 01/08

從 Data Operations 到 AI Operations：營運對象從管線擴張到模型、內容與行動

DataOps同一個問題：把系統養到可控、可修、成本可見AI Operations
Data Operations
AIRFLOW · DAG · CI/CD · CAPACITY
觀測單位是 job run、資料延遲、錯誤率與資源成本；失敗後可重跑、補資料、調整容量。
AI Operations
MLOps / LLMOps / AgentOps
觀測單位擴張成 一次推理與行動軌跡；除了延遲與成本，還要持續評估品質與安全。
AI 多出的變因輸出不固定，重試不一定得到同樣結果；營運還要涵蓋 prompt 版本、token 成本與 Agent 動作。
借鏡：既有排程、告警、執行紀錄與成本歸因仍是地基；AI Operations 是把營運邊界從「管線」往「行為」擴張。

06PART 2 · 逐組對照 02/08

先看懂國泰 GAIA 2.0 把 Agent 當資產管，再對回 Data Governance

Data Governance同一個問題：多團隊規模化時，資產與權限不失控AI Governance

GAIA 2.0：國泰銀行的企業級 Agent 管理平台

不是做單一 Agent——是讓多個團隊「開發、部署、申請、維運、下架」Agent 的共通平台能力

  • Gateway：集中權限檢查、路由與執行紀錄——治理中樞

核心做法：Agent 也是「資產」

  • 資產化＋訂閱制：不得私下串接
  • 雙重身份：Agent 系統權限 vs 使用者委派（防權限放大）
  • Provider／Consumer／Governance 分離（SoD）

借鏡：GAIA 把「資產化＋訂閱制」做成了平台能力——我們前半段已有（Workspace＋OPA＋Iceberg），缺口是改版相容性與下架依賴分析。

07PART 2 · 逐組對照 03/08

從資料血緣到決策血緣：追蹤範圍從欄位擴張到上下文與行動

Data Lineage同一個問題：產出從哪來、壞了影響誰AI Lineage

Data Lineage：追「資料的血緣」

OPENLINEAGE · JOB → RUN → DATASET
  • 欄位從哪張表來、job 之間怎麼依賴
  • 用途：衝擊分析、除錯、合規
  • 我們已有：query log 可重建 table 依賴

AI Lineage：追「決策的血緣」

TRACE · PROMPT VN · RETRIEVAL · MODEL · TOOL
  • 這個回答為什麼是這樣：prompt 版本、檢索 chunk 來源、model 版本、tool 結果、policy 檢查
  • 用途：重現決策、責任歸屬、審計
  • GenAI trace conventions 正在把推理與行動軌跡標準化
AI 新增追蹤對象擴張到「上下文與決策」；同樣的底層資料，不同的 prompt／模型／工具組合就是不同答案。
借鏡：依賴圖可以共用——把 AI trace 掛進同一個圖，AI 資產就能享受 Data 資產的衝擊分析。

08PART 2 · 逐組對照 04/08

從資料是否健康到行為是否可靠：Observability 的觀測對象變寬了

Data Observability同一個問題：壞了要第一個知道AI Observability

Data Observability：壞了第一個知道

FRESHNESS · VOLUME · SCHEMA · SLO
  • 資料沒更新、量暴增暴減、schema 漂移
  • 單位：表、job、管線
  • 告警 → 定位 → 修復

AI Observability：行為也要觀測

TRACE · TOKEN COST · QUALITY · SAFETY
  • 延遲、token 成本、內容品質、安全違規
  • 單位：一次推理與行動軌跡
  • GenAI trace conventions 已開始定義跨工具共通欄位
AI 新增「生成內容好不好」本身就是觀測對象；quality score 與 safety 違規要進同一套告警。
借鏡：signal → context → decision → action 的閉環可以共用——平台提供 trace 通道與 feedback 迴路，而不是多一個孤島儀表板。

09PART 2 · 逐組對照 05/08

從規則檢查到結果評估：品質判斷從 pass／fail 走向分布與風險

Data Quality同一個問題：產出可不可信——都要品質閘門AI Evaluation

Data Quality：規則可驗證

SCHEMA CHECK · FRESHNESS · VOLUME
  • pass / fail，規則形式化
  • 可重現、可自動化、壞了就擋（gate）
  • 單位：表、欄位

AI Evaluation：行為分布

GOLDEN SET · LLM JUDGE · HUMAN FEEDBACK
  • accuracy、hallucination rate、task success、guardrail violation
  • 看的是分布與趨勢，不是單次對錯
  • 評估是持續測量，不是一次測試
AI 新增正確性 → 行為可靠性；測試從 pass/fail 變成分布與風險邊界。
借鏡：Data 品質可以從「規則閘門」升級成「行為型 SLA」——不只檢查 schema，還追「資產被用得怎樣、下游結果好不好」。

10PART 2 · 逐組對照 06/08

從 Catalog 到 Registry：資產不只要登錄，還要能被正確選用

Data Catalog同一個問題：資產找得到、選得對、用得上Model Registry

Data Catalog：找資料＋申請使用

HMS · ICEBERG · WORKSPACE · OPA
  • 找得到嗎？有哪些表／欄位、owner 與用途
  • 判斷是否適用嗎？看 SLA、品質、更新頻率與使用範例
  • 申請與使用綁定 Workspace；由我們設定 OPA 控制 schema/table 存取
  • 申請後直接使用嗎？核准後權限應自動落到 Workspace

Registry：找 AI 資產

MLFLOW MODEL REGISTRY · PROMPT REGISTRY
  • 模型、prompt、agent、tool、eval 都要註冊
  • MLflow 已有 alias 指版本、記 lineage
  • 資產是組合：model+prompt+context+tool+policy
AI 新增行為資產也要註冊：policy、eval、trace 不只是 metadata，是資產的一部分。
借鏡：下一步不是再做一個 Catalog，而是補齊「搜尋 → 適用性判斷 → 申請 → 可用」的資產消費體驗。

11PART 2 · 逐組對照 07/08

從查詢入口到動作入口：Gateway 把權限、路由與稽核留在平台層

Query Gateway同一個問題：合規成本留在平台層Agent Gateway

Query Gateway：統一查詢入口

TRINO PROXY · OPA · JWT
  • 集中權限、路由、稽核（query log）
  • 點對點連線 → 樞紐化（hub-and-spoke）
  • 我們已經在做

Agent Gateway：統一動作入口

MCP · GUARDRAILS · 身份委派
  • 動態路由（agent 每次選不同工具）
  • 每 hop 驗證：User → Agent → Sub-Agent → Tool
  • 雙重身份：系統權限 vs 使用者委派，禁止權限放大
AI 新增治理單位從「讀取權限」變成「每個動作的授權」；agent 能做的事超過任務所需（過度自主）是 2025 年十大 AI 風險。
借鏡：我們已有 gateway 心智模型——MCP 時代的「工具目錄」也該走同一道門，而不是讓每個團隊各自對接。

12PART 2 · 逐組對照 08/08

從固定 Pipeline 到動態 Workflow：可沿用的是工程紀律，不是固定路徑

ETL Pipeline同一個問題：把原料加工成可信產出Agent Workflow

ETL Pipeline：加工原料

AIRFLOW DYNAMIC DAG · SPARK JAR
  • Extract → Transform → Validate → Serve
  • 可排程、可重試、可監控、有版本
  • 路徑固定，失敗可重放

Agent Workflow：加工「上下文」

RETRIEVE → REASON → TOOL → VERIFY → ACT
  • prompt 是可版本化的 pipeline component
  • RAG = 把外部資料接進推理的「ELT」
  • 執行路徑不固定，agent 動態選工具
AI 新增context 既是輸入也是狀態——失敗不能簡單重放，要重放「決策過程」。
借鏡：沿用的是流程資產化、版本化、每次執行可追蹤、失敗有 checkpoint；不能硬套固定 DAG，因為 Agent 可能動態決定下一步。

13PART 3 · 萃取 AI 改良設計 ③

AI 生態系被迫把五件事做得更好——這就是可以借回來的東西

不是發想 AI use case；是看 AI 生態系如何重新處理 Data 世界處理不好的五個老問題。

改良 01上線門檻＋持續回歸
golden set、評分、human feedback、CI gate——結果未達門檻就不發布
Data 對應：DQ 會驗證輸入規則，但較少持續追蹤下游結果是否真的可用
改良 02從觀測走到處置
執行軌跡 → 偵測 → 定位 → 建議／核准 → 執行 → 驗證，依風險決定自動化程度
Data 對應：監控訊號很多，但多半停在告警，處置仍靠人串接
改良 03Policy as Code
guardrails、政策即程式碼、每 hop 驗證、高風險動作強制人工覆核
Data 對應：OPA 已有（查詢層）；Agent 導入後才需要補「工作負載＋發起人」身份
改良 04資產生命週期＋Marketplace
publish → subscribe → versioning → deprecation；審批自動化、消費端升級＋回歸
Data 對應：catalog＋snapshot 有；訂閱審批已綁 Workspace＋OPA，缺 Marketplace 體驗與下架依賴分析
改良 05Trace 標準化
把「一次推理與行動」標準化成 spans——跨模型、框架與工具使用共通語意
Data 對應：query log 各自為政，沒有跨系統軌跡標準
這五項不是 AI 的專利，是 AI 生態系被迫先做好的平台功課——每一項都能對回我們自家架構。

Data Quality 主要回答

SCHEMA · FRESHNESS · VOLUME · VALIDITY

  • 結果通常是可重現的 pass／fail
  • 很適合擋 schema、freshness、volume 異常

AI Evaluation 多回答一層

  • 這個版本產出的答案／動作是否真的可用？

  • 線上失敗案例持續回流，避免下一版再犯

改良 02：從觀測走到處置——Auto-healing 是終點之一，不是起點

偵測
監控訊號發現異常
→
定位
找出 job／資產／版本
→
建議
產生可解釋的處置方案
→
人工核准
依風險決定是否需要
→
執行
自動或半自動處置
→
驗證
確認恢復且沒有副作用

低風險：可以自動處置

RETRY · QUARANTINE · FALLBACK · NOTIFY
  • 失敗 job 依條件重跑
  • 隔離壞資料，避免污染下游
  • 切換 fallback 資源或通知 owner

高風險：系統建議，人來核准

DIAGNOSE · EXPLAIN · APPROVE · EXECUTE
  • 改 schema、回滾版本、撤銷權限前先解釋影響
  • 人工核准後才執行，並保留完整稽核紀錄
  • 成熟後只把重複、可逆的處置升級為 Auto-healing
差距監控與執行紀錄已有，常缺的是「定位後如何安全處置、處置後如何確認恢復」。
借回先把告警接成可審核的處置流程，再逐步自動化低風險、可逆的動作。

改良 03：Policy as Code——Agent 場景才新增「工作負載＋發起人」身份

現在的 Data 存取模型

PERSON · M2M · WORKSPACE · OPA
  • 人或 M2M 身份帶 JWT 進 Workspace
  • OPA 依 Workspace、schema、table 判斷是否可讀
  • 這套模型對目前 Query Gateway 已經足夠

Agent 代表人執行工具時

SERVICE ACCOUNT + INITIATING USER
  • Agent 用平台 service account 連接工具
  • 每次動作仍要帶上發起人身份與本次授權範圍
  • 不能因 service account 能讀很多表，就把完整能力放大給使用者
使用者 Alice
本次任務的發起人
→
Agent Runtime
以 service account 連接工具
→
Policy Check
同時檢查 Agent 能力＋Alice 權限
→
Schema / Table / Tool
只允許本次任務所需動作
邊界這不是現有 Data Platform 的既有缺口；只有導入「Agent 代表人操作工具」時才需要。
借回保留 OPA 的 Policy as Code 優勢；未來再把「工作負載身份＋發起人身份＋動作範圍」一起送進政策判斷。

19結論

AI 生態系是 Data 生態系的「未來回顧鏡」

看懂 AI 平台的結構，等於預覽 Data Platform 的下一個十年；把 AI 的治理設計帶回 Lakehouse，則讓我們不用等十年。
① 名詞換了，問題沒換
八組對照，每一組都認得出長輩——先認出長輩，才知道新東西該接在哪
② 新維度要接住
non-determinism、context、agency：真正新的三個維度，定義了「行為控制面」的設計空間
③ 借回五項改良，先補最明確的缺口
上線門檻、觀測到處置、政策即程式碼、資產生命週期、trace 標準——P0 下架依賴分析優先
市場現況 Agentic Lakehouse：資料平台從「給人查」變成「給 Agent 用」——自己發現資料、生成查詢、解讀結果 語意層｜Snowflake Semantic Views · dbt Semantic Layer · WrenAI（開源）
MCP 介面｜Dremio MCP · Databricks MCP Server　治理｜Databricks Unity AI Gateway · Apache Polaris（開源）
路徑不是現在就追 Agentic Lakehouse，而是先把基礎打穩——今天盤點的每個缺口（下架依賴分析、資產消費流程、結果回歸門檻），都是未來敢走這一步的底氣。謝謝大家，歡迎討論。
