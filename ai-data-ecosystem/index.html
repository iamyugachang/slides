01DATA × AI ARCHITECTURE內部技術分享

AI 生態系，其實是 Data 生態系的
「未來回顧鏡」

從 AIOps · AI Governance · AI Lineage 這些新名詞看回去——
它們大多是我們十年前就踩過的坑，只是主角從「資料」換成了「模型與 Agent」。

DataOpsAIOps Data GovernanceAI Governance Data LineageAI Lineage Data CatalogModel / Asset Registry
今天不談「AI 能做什麼」——談 AI 生態系長什麼樣，以及我們的大數據平台怎麼接住它、又從它身上學到什麼。

主題框架：內部研討架構 · 參考 AADay 2026 國泰世華 AgentOps 治理實務

02給三種聽眾的一句話

一場分享，三種收穫：看懂、管住、排程

A｜DATA PLATFORM 工程師
新名詞 = 舊模式
AI 平台的 primitive 你幾乎都做過：catalog、pipeline、gateway、observability。差別只在 non-determinism、context、agency 三個新維度。
B｜治理／資安／平台
治理對象擴張
從「誰能讀什麼資料」→「誰能在什麼情境下做什麼事」。資產生命週期（publish → subscribe → version → deprecate）是現成的管理語言。
C｜技術主管／架構決策
別再追新工具
把資源投在四個 primitive：資產生命週期、控制面（gateway）、依賴圖（lineage）、評估閉環（continuous evaluation）。
今天的主張：與其追著 AI 名詞跑，不如先認出它們在 Data 世界裡的長輩——認識長輩，就知道下一步該補哪裡。

03核心主張

同一組組織壓力，長出同一組平台 primitive

Data 生態系的平台化不是因為技術多酷——是因為「多團隊規模化」遲早失控。AI 生態系正在同一條路上。

組織壓力
來源／團隊變多 · 合規變嚴 · 成本失控 · 信任不足
→所有平台都這樣長出來
平台 primitive
Catalog 有哪些資產 · Pipeline 怎麼加工 · Governance 誰能碰、能碰多久 · Observability 壞了誰知道 · Gateway 所有請求走同一道門
國泰 GAIA 2.0 的案例把這件事講得很清楚：企業導入 AI Agent 的真正瓶頸，從來不是 PoC 做不出來，而是多團隊規模化（scale up）時的失控——點對點串接、權限標準不一、上線維運混亂。
Data 世界已經為這些壓力交過學費；AI 世界正在重交同一筆。差別是：這次我們可以站在已經繳過費的那一邊。

來源：AADay 2026 · 國泰世華 Neo「金融業 AgentOps 與權限治理設計」

05七組同構

新名詞對回舊名詞：七組同構地圖

DataOps↔AIOps
共同問題：把系統顧好、養好——部署、修復、調度
新增：行為軌跡 non-deterministic，每次執行都不一樣
Data Governance↔AI Governance
共同問題：資產誰能用、邊界在哪
新增：prompt injection、權限放大、決策稽核
Data Lineage↔AI Lineage
共同問題：產出從哪來、影響到誰
新增：context、model version、tool call 都要入圖
Data Observability↔AI Observability
共同問題：壞了要第一個知道
新增：生成內容品質、安全違規也要觀測
Data Quality↔AI Evaluation
共同問題：產出可不可信
新增：從規則 pass/fail → 行為分布評估（judge / golden set / human feedback）
Data Catalog↔Model / Asset Registry
共同問題：有哪些資產、誰擁有、品質如何
新增：組合資產——model＋prompt＋context＋tool＋policy＋eval
Query Gateway↔Agent Gateway
共同問題：統一入口＝集中權限／路由／稽核
新增：動態路由、身份委派、決策軌跡稽核
名詞換了，問題沒換。
先認出 pattern，再談差異。

06治理案例 · 國泰世華 GAIA 2.0

資產生命週期：Publish → Subscribe → Versioning → Deprecation

① Publish 上架發布
能力規格＋權限要求註冊進內部 Marketplace，供全行檢索
→
② Subscribe 申請授權
其他 Agent 不得私下串接，一律走平台訂閱與權限審批
→
③ Versioning 版本控管
多版本並存、不強制覆蓋，給呼叫端測試與遷移緩衝
→
④ Deprecation 安全下架
下架前主動分析依賴關係、強制通知、平滑下線
Provider 提供方
開發與維護、版本更新、決定是否同意存取、承擔品質與乘載
Consumer 需求方
Marketplace 搜尋、發起訂閱；新版上線時升級依賴＋回歸測試
Governance 平台方
上架前資安掃描＋合規審核、監控流量與相依性、異常時責任歸屬
這套生命週期不是 Agent 專利——它其實是任何「資產化」的平台都要走的路。下一頁把它套回我們的 Data Asset。

來源：AADay 2026 · 國泰世華 Neo「金融業 AgentOps 與權限治理設計」（GAIA 2.0：Workspace／Marketplace／Gateway 三核心）

07套回 Data Asset

同一條生命週期，我們其實已經走了一半

① Publish
HMS / Iceberg catalog 註冊：owner、SLA、schema、metadata
→
② Subscribe
權限中心申請審批（Ranger 層）——禁止私下連表
→
③ Versioning
Iceberg snapshot / time travel 天生多版本；schema evolution 不強制覆蓋
→
④ Deprecation
下架前 lineage 依賴分析＋通知＋平滑下線——目前缺口
Gateway
Trino = 統一查詢入口＝集中權限／路由／稽核
Marketplace
資料目錄（DataHub / OpenMetadata 等級）＝發現與申請入口
雙重身份
M2M（pipeline service account）vs User Delegation（使用者查詢）
我們已經有「半個 GAIA」：Iceberg 版本管理＋Trino 統一入口＋HMS catalog。缺的是 ②訂閱審批流程、④deprecation 依賴分析、嚴格雙重身份。

08Catalog ≠ Marketplace

Catalog 回答「有什麼」；Marketplace 回答「怎麼安全地用到」

Registry／目錄（我們有）

  • 可搜尋：有哪些表／欄位
  • 有 metadata：owner、schema、SLA
  • 有品質資訊：freshness、行數
  • 但只能「看」——不包含申請與使用流程
→

Marketplace（下一步）

  • 發現＋申請：一鍵發起訂閱
  • 審批流程：依資料機敏度分級核決
  • 自動開權限：審過即生效，不靠人肉
  • SLA 與用量儀表板：好用與否看得見
類比：Catalog = 圖書館目錄；Marketplace = 目錄＋借書證＋流通管理。治理價值在後者。
AI 世界的 Model Registry 也一樣——MLflow 可以註冊模型、Alias 指版本、記 lineage；但「誰可以用、升級要不要審批」是平台層的活。dbt 的 model versions＋deprecation_date 更是 Data 世界自己的 subscribe/version/deprecate。

來源：MLflow Model Registry https://mlflow.org/docs/latest/ml/model-registry/ · dbt Model Versions https://docs.getdbt.com/docs/mesh/govern/model-versions

09Lineage

從「欄位從哪張表來」到「這個回答為什麼是這樣」

Data Lineage（OpenLineage 模型）

  • 單位：Job → Run → Dataset（input / output）
  • 欄位級血緣、schema 演進追蹤
  • 用途：衝擊分析、除錯、合規
  • 我們已有：query log 可重建 table-level 依賴

AI Lineage（= Trace 的擴張）

  • 單位：Request → Prompt → Retrieval → Model → Tool → Response
  • 要記：prompt template vN、檢索 chunk 來源、model version、tool 結果、policy 檢查
  • 用途：重現「為什麼這樣答」、責任歸屬、審計
  • OpenTelemetry GenAI semantic conventions 正在標準化
關鍵差異：Data lineage 追「資料的血緣」；AI lineage 追「決策的血緣」——同樣的底層資料，不同的 prompt／模型／工具組合，就是不同的答案。
對我們來說這是好消息：lineage 基建可共用——把 trace 掛進同一個依賴圖，AI 資產就能享受 Data 資產的衝擊分析。

來源：OpenLineage Object Model https://openlineage.io/docs/spec/object-model/ · OpenTelemetry for Generative AI https://opentelemetry.io/blog/2024/otel-generative-ai/

10Observability × AIOps

AIOps 不是「用 LLM 看 log」——是讓 signal 閉環成 action

Signal
latency / error / token cost / quality score / safety 違規
→
Context
trace＋lineage 關聯：這次請求用了哪些資料、模型、工具
↓
Action
retry／rollback／guardrail 介入／配額調整／通知 owner
←
Decision
根因定位、模型路由、風險分級
↑
OTel 已定義 GenAI semantic conventions：prompt、completion、token 用量、model 版本、tool 呼叫——觀測單位從「資料表」擴張為「一次推理與行動軌跡」。Data observability 的 freshness/volume/schema 對應 AI 的 quality/safety/cost。
平台要提供的不是儀表板，是 trace 通道＋feedback 迴路：壞了能定位到「哪一步」，還能自動或半自動採取行動。

來源：OpenTelemetry for Generative AI https://opentelemetry.io/blog/2024/otel-generative-ai/

11Quality × Evaluation

Data 的品質是「規則可驗證」；AI 的品質是「行為分布要落在可接受風險內」

Data Quality：pass / fail

  • schema check、freshness、volume、row count
  • 規則形式化：可重現、可自動化
  • 壞了就擋（gate）

AI Evaluation：distribution

  • accuracy、hallucination rate、task success、guardrail violation
  • golden set、LLM judge、human feedback
  • 看的是分布與趨勢，不是單次對錯
NIST AI RMF 的 Measure function 說得很清楚：評估不是一次性的測試，是持續的測量與監控（continuous evaluation）——這跟 Data 平台的品質閘門（quality gate）同構，但單位從「表」變成「行為」。
反過來給我們的啟發：Data 品質也可以從「規則閘門」升級成「行為型 SLA」——不只檢查 schema，還追「這個資產被用得怎樣、下游結果好不好」。

來源：NIST AI RMF https://www.nist.gov/itl/ai-risk-management-framework · Google Cloud MLOps continuous evaluation https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning

12Gateway × Identity

治理單位從「讀取權限」變成「每個動作的授權」

User 使用者
→
Agent 主 Agent
→
Sub-Agent 子 Agent
→
MCP / Tool 工具
⚠️ 每個 hop 都要權限卡控＋身份傳遞（Zero Trust per hop）：User → Agent → Sub-Agent → Tool，每一段都驗證，不能在「大門口」檢查一次就放行。

雙重身份（GAIA 2.0）

  • 系統自身權限（M2M）：固定任務、與登入者無關（排程爬蟲）
  • 使用者委派權限：代表當下使用者 → 依使用者權限，禁止權限放大

OWASP：Excessive Agency

  • Agent 能做的事超過任務所需，是 2025 LLM Top 10 風險
  • 意外或被操縱的輸出，也能造成真實損害
  • 解法：最小工具集＋動作級授權＋human-in-the-loop
我們已在做一半：Trino Proxy＋OPA 是集中卡控點（gateway），pipeline SA 是 M2M。缺的是「代表使用者執行」的委派語意——AI 時代這會變成硬需求。

來源：AADay 2026 Neo（雙重身份、Gateway）；OWASP LLM06 Excessive Agency https://genai.owasp.org/llmrisk/llm062025-excessive-agency/

13類比斷點

三個不能硬套的斷點——但正是它們，反過來給我們設計靈感

01

Non-determinism

  • 相同輸入 ≠ 相同輸出
  • 測試從 pass/fail → 分布與 SLO
  • 治理對象：正確性 → 行為可靠性
02

Context

  • lineage 從欄位血緣 → 認知上下文
  • prompt、檢索、記憶、tool 結果都要入圖
  • 要能重現「為什麼這樣答」
03

Agency

  • 從「人查資料、人做決定」→「agent 自己查、自己決定、自己執行」
  • 授權從 read → write / action
  • 責任歸屬：誰對 agent 的行動負責
把 AI 回答當 SQL 結果、把 prompt 當 ETL、把 agent 當 dashboard——這三個誤導會把 AI 治理降級成舊治理的換皮。認出斷點，才能設計真正的控制面。

來源：內部研討架構（自製斷點分析）；風險面參考 OWASP / NIST AI RMF

14收斂架構

未來不是「Data Platform + Model API」，是 Data Plane 之上長出 Behavior Control Plane

AI Control Plane（新增）
prompts · agents · tools · evals · policies · traces · approvals
共用治理基座
Catalog（資料＋模型＋Agent 資產）· Identity（雙重身份）· Policy（OPA 擴張）· Telemetry（trace 統一收）
Data Plane（既有 Lakehouse）
tables · files · features · metadata · ACL · lineage（Iceberg / HMS / MinIO / Trino）
兩個 plane 共用同一套 catalog、identity、policy、telemetry——AI 資產與 Data 資產在同一個治理語言下管理，而不是另起爐灶。
這正是 GAIA 的架構直覺：把合規成本留在平台層，把開發速度還給業務團隊。我們已經有下半層，缺的是上半層的資產模型。

16行動方案

從「管理資料」升級到「管理資料＋行為」：三階段

0–30 天打底
資產註冊模板：owner／SLA／機敏度分級入 catalog metadata
Deprecation 政策：下架 SOP 文件＋審核流程
雙重身份盤點：清點所有 M2M service account 與真實使用者路徑
30–90 天MVP
訂閱審批 MVP：Console 申請 → 分級審批 → 自動開權限（機敏度矩陣）
依賴分析擋下架：query log 重建 table 依賴圖，deprecation 前自動通知
資產健康度指標：freshness／volume／品質閘門，接進現有 telemetry
90+ 天平台化
Marketplace 體驗：搜尋＋訂閱＋SLA 儀表板（DataHub/OpenMetadata 起步）
行為型 SLA：eval-style 品質指標進 SLA 契約
成本歸因＋feedback 閉環：用得好壞看得見，回饋進平台優化
每一步都可獨立驗證、獨立交付——不需要先上 AI 才做；這些是 Data Platform 自己就該補的功課。

17結論

AI 生態系是 Data 生態系的「未來回顧鏡」

看懂 AI 平台的結構，等於預覽 Data Platform 的下一個十年；把 AI 的治理設計帶回 Lakehouse，則讓我們不用等十年。
① 同構 — 老問題，新主角
資產生命週期、控制面、依賴圖、評估閉環：AIOps / AI Governance / AI Lineage 通通認得出來
② 斷點 — 不能硬套，但要接住
Non-determinism、Context、Agency：三個新維度，定義了「行為控制面」的設計空間
③ 行動 — 先補功課，再談新工具
訂閱審批、deprecation 依賴分析、雙重身份：0–30／30–90／90+ 三階段，每一段都獨立交付
我們不是在「追 AI」——我們是在把 Data Platform 升級到「決策與行動」的治理時代。謝謝大家，歡迎討論。
