03先給總地圖

整份教材只講一件事：SQL 如何被拆成可平行的小工作，資料如何流動

三個世界的分工

  • Coordinator：把 SQL 變成計畫與 split——不做資料搬運（第 1–2 章）
  • Worker：執行 task、交換 page——真正的算力所在（第 3 章）
  • Connector：Trino 與外部世界的翻譯層（第 5 章）

三個貫穿全場的關鍵字

  • Split：最小工作單位，決定平行度
  • Task / Driver：怎麼執行一份工作
  • Page：資料在 node 間流動的格式
一句話記住 Trino：把 SQL 拆成可平行的小工作（split／task），資料以 columnar page 在 node 間流動；Coordinator 只負責計畫與調度。

04貫穿範例

一條 SQL 走到底：範例查詢 Q（後面每一章都用它示範）

範例查詢 Q —— 找出 2025 年各國 GMV 前五名
SELECT n.name AS nation, count(*) AS order_cnt, round(sum(o.totalprice), 2) AS gmv
FROM wh.tpch.orders   o
JOIN wh.tpch.customer c ON o.custkey  = c.custkey
JOIN wh.tpch.nation   n ON c.nationkey = n.nationkey
WHERE o.orderdate >= DATE '2025-01-01' AND o.orderdate < DATE '2026-01-01'
GROUP BY n.name
ORDER BY gmv DESC
LIMIT 5
假設資料集WH · 教材假設，非實際 Production 數字
orders：1.5 億列、約 600 GB Parquet、以 orderdate 月份分區（Iceberg，catalog 掛在 HMS，檔案在物件儲存）｜customer：150 萬列｜nation：25 列——一大、一中、一極小三種尺寸
為什麼選它涵蓋面
一次涵蓋完整機制：WHERE → 分區剪枝／pushdown、JOIN（大小表策略不同）、GROUP BY → 兩階段聚合、ORDER BY + LIMIT、以及背後的 split 產生、exchange shuffle、記憶體與容錯
你在 Production 寫的每一條查詢，走的都是同一條路。看懂 Q 在每一章被怎麼處理，就等於看懂所有查詢。

06PART 1 · 定位與架構 ①

三種角色：Coordinator 計畫，Worker 執行，Connector 翻譯

架構關鍵：coordinator 與 worker 都不「擁有」資料；資料在 Connector 後面。要加算力＝加 worker，與資料搬不搬家無關。

07PART 1 · 定位與架構 ②

Coordinator 是「大腦」，Worker 是「肌肉」——資料永遠不經過大腦

Coordinator：計畫與調度

每條查詢都先在這裡「想清楚」
  • Parse → Analyze → Plan → Optimize：把 SQL 變成執行計畫（耗 CPU 的階段都在這）
  • 問 Connector 要 metadata（表結構、分區、統計值），把計畫最佳化
  • 把計畫拆成 stage，產生 split，分派給 worker 並持續收進度
  • 執行結束後把結果串流回 Client；查詢狀態存在 coordinator 記憶體

Worker：真正的執行者

每顆 worker 同時服務很多條查詢
  • 接收分派來的 split，在 task／driver 流水線裡執行（第 3 章）
  • 需要時直接從 Connector 讀資料（S3／MinIO／Kafka……），不經過 coordinator
  • 與其他 worker 之間以 exchange 交換資料（join 的 shuffle 就是這種）
  • 定期回報 task 進度；記憶體、spill 都在 worker 這一層發生
分工的結果要加算力就加 worker（水平擴展）；查詢變多、變複雜時先忙起來的是 coordinator 的 CPU（規劃＋調度＋metadata 呼叫）。
故障語義worker 掛掉 → 它身上的 task 失敗（第 4 章 retry 會接手）；coordinator 掛掉 → 執行中的查詢全部中止——所以 coordinator 只做「輕量決策」，重活全在 worker。
Coordinator 的 CPU 熱點
parse／analyze／最佳化／切 splits／排程＋metadata 呼叫——小查詢大量發生時最先滿載
Worker 的 CPU 熱點
讀檔、過濾、join、聚合、page 交換、spill——真正的大數運算都在這
擴展方向不同
加算力＝水平加 worker；升級 coordinator 只救「想」的瓶頸，救不了執行
看查詢問題先分邊：「計畫階段」慢還是「執行階段」慢——前者多半在 coordinator（第 2 章），後者在 worker／資料（第 3、5 章）。

08PART 1 · 定位與架構 ③

Connector 是翻譯層：引擎不懂資料格式，Connector 懂

三層命名空間：catalog . schema . table
SELECT * FROM wh.tpch.orders   -- wh = catalog（設定檔 wh.properties → Iceberg Connector）
                     -- tpch = schema · orders = table（中繼資料在 HMS）
Catalog設定檔 → Connector 實例
一個 catalog 綁定一個 Connector 與它的目標系統：wh = Iceberg Connector + HMS + 物件儲存；也可以有 hive、kafka、postgresql 等 catalog。SQL 的第一段名字決定「由誰翻譯」
Connector 三大介面第 5 章會展開
① Metadata：這張表存在嗎、有哪些欄位／分區／統計值？② Split：一張表可以被切成哪些獨立小工作？③ Page source：把外部資料讀成 Trino 的 page。引擎只會對著這三個介面寫程式
引擎與 Connector 的默契最佳化不是引擎單方面決定
Connector 會主動宣告自己支援什麼（能不能把 WHERE 推下去、能不能只讀部分欄位）；引擎把能推的都推下去，不能推的才自己處理——推得越多，搬回引擎的資料越少
自家：wh catalog
etc/wh.properties → Iceberg Connector（HMS 4 管中繼資料、Iceberg 1.5.2 表格式）
自家：資料在引擎外
Parquet 檔案在物件儲存（S3／MinIO）；Trino 只負責「讀得懂＋算得快」
自家：入口還有 Gateway
Trino Proxy＋OPA 先做權限／路由——這是查詢進來前的關卡，不是引擎的一部分
寫 SQL 時看到的第一段名字（catalog）不是裝飾——它決定了整條查詢的 metadata 從哪來、split 怎麼切、資料怎麼讀。

12PART 2 · 生命週期 ②

Parse 只是「唸得出來」，Analyze 才真正「看懂」——兩者都要問 Connector

② Parse：文法檢查

ANTLR GRAMMAR · SQL → AST
  • 用 Trino 的 SQL 文法（ANTLR）把文字拆成抽象語法樹（AST）
  • 只檢查「唸不唸得通」：關鍵字、括號、逗點、字面值
  • 範例：SELECT 拼成 SELEC、少一個括號 → 這裡就失敗，不會浪費任何執行資源
  • 還不知道任何表存不存在

③ Analyze：語意解析＋查 metadata

ANALYZER · METADATA LOOKUP
  • 把 AST 的每個名字綁定到真實物件：wh.tpch.orders 存在嗎？欄位與型別是什麼？
  • 型別檢查與隱式轉型：orderdate >= DATE '2025-01-01' 型別合不合法
  • 展開 view、解析函式簽名、權限檢查（若啟用）
  • 「unknown column」「table not found」都在這一階段報錯
Q 的 Analyze：每一段名字都要問 Iceberg Connector
FROM wh.tpch.orders o   → catalog wh（iceberg.properties）→ HMS：表存在？欄位？型別？分區鍵？
o.custkey = c.custkey   → 兩邊都是 bigint？欄位真的存在？
n.name AS nation        → GROUP BY／ORDER BY 用的別名解析
成本含義Analyze 要打 metadata（對 Iceberg 是 HMS／目錄服務）。查詢數量 × 每查詢的表數決定這裡的延遲；大量小查詢時，metadata 服務的延遲會直接出現在「Analysis 時間」。
語法錯、欄位錯、型別錯——全都在真正動工前就被攔下；你看到的報錯訊息，就是這兩個階段的產物。

13PART 2 · 生命週期 ③

④ 邏輯計畫：SQL 被翻譯成一棵「操作樹」——葉子讀表，根吐結果

Q 的邏輯計畫（示意樹：真實節點與順序以 EXPLAIN 為準；CBO 可能重排 join）
Output                                  ← 最後只吐 5 列給 client
└─ Limit(5)
   └─ Sort[gmv DESC]                      ← ORDER BY
      └─ Aggregate[GROUP BY n.name]       ← count／sum 在這裡算（之後會拆兩階段）
         └─ InnerJoin[o.custkey = c.custkey]
            ├─ InnerJoin[c.nationkey = n.nationkey]
            │  ├─ TableScan[wh.tpch.customer]   葉子：讀表
            │  └─ TableScan[wh.tpch.nation]     葉子：讀表
            └─ Filter[orderdate ∈ 2025]         WHERE 條件
               └─ TableScan[wh.tpch.orders]     葉子：讀表（資料量最大的那一片）

這棵樹的意義

  • 每個節點 = 一個「操作」：掃描、過濾、join、聚合、排序、限量
  • 資料方向：葉子（讀表）→ 根（結果），下一層的輸出是上一層的輸入
  • 之後每個節點會變成 operator（第 3 章），葉子的讀表會變成 split 清單（第 5 章）

你怎麼看到它

  • EXPLAIN SELECT …：印出最佳化後的邏輯計畫（樹狀文字）
  • 看 join 順序、filter 掛在哪個 scan 下面、有沒有被推下去——這是你判斷計畫好壞的第一張圖
  • 真實節點名會更細（ScanFilterProject、HashAggregation…），概念一樣
邏輯計畫是「要做什麼」的藍圖；接下來兩步（最佳化、切 stage）決定它「怎麼做、多快做」。

14PART 2 · 生命週期 ④

⑤ 最佳化第一層（RBO）：把操作往下搬、往小搬——最好連引擎都別碰資料

Q 
WHERE o.orderdate >= DATE '2025-01-01' …  → applyFilter 推給 Iceberg → 只讀 2025 年的月分區
查詢只碰 12 個分區，而不是全部歷史
最佳化的核心邏輯只有一句：資料能在越靠近儲存的地方被丟掉，就越省——引擎推、connector 接，推不動的條件才把資料搬回來過濾。

15PART 2 · 生命週期 ⑤

CBO：用「統計值」估成本，決定 join 順序與分布——統計爛，計畫就爛

輸入① 計畫樹
要 join 什麼、filter 在哪
輸入② Table statistics
列數、大小、欄位 distinct 值…
由 connector 提供（Iceberg／Hive 用 ANALYZE 收集）
＋
成本模型
對每個候選計畫估 CPU／記憶體／網路成本
→
輸出：最佳計畫
join 順序（哪張先 join）
join 分布（broadcast 或 partitioned）
官方文件怎麼說（467 optimizer/cost-based-optimizations）
AUTOMATIC（預設）＝ 完整自動 join 列舉，挑成本最低的 join 順序；
若統計值不可用或成本算不出來 → 自動退回 ELIMINATE_CROSS_JOINS（消 cross join，其餘照語法順序）。
ANALYZE
對 Iceberg／Hive 表執行 ANALYZE wh.tpch.orders 才會收集統計值
default: true
Iceberg extended statistics 啟用；collect-on-write 預設也開（寫入時一併收集）
統計過期 → 壞計畫
資料長大後沒重跑 ANALYZE，CBO 用舊數字決策——定期對常用大表 ANALYZE 是最便宜的最佳化
怎麼驗證計畫的選擇EXPLAIN（不帶 ANALYZE）印出最佳化後的樹：看 join 順序、Join 節點的 Distribution、scan 節點有沒有 filterPredicate／dynamicFilters——計畫怪、統計舊，就先 ANALYZE 再重看。
「為什麼 join 順序長這樣？」的答案通常在統計值裡。先檢查統計新不新，再懷疑 CBO。

16PART 2 · 生命週期 ⑥

Join 只有兩種分布：Broadcast（複製小表）或 Partitioned（兩邊都打散）——選錯就是災難

Partitioned join（大表對大表）

兩邊都照 join key 打散 → 每個 worker 只 join 自己那一份
  • 優點：沒有單點記憶體上限，多大都能 join
  • 代價：兩邊都要重新分布（shuffle 網路成本），通常比 broadcast 慢
  • 適用：build 側大到每台 node 放不下

Broadcast join（小表配大表）

把 build 側「複製到每一台 node」→ probe 側就地 join，零 shuffle
  • 優點：快——但 build 表必須能放進每台 node 的記憶體（filter 後）
  • 代價：複製成本＋每 node 記憶體佔用；太多 query 同時 broadcast = 記憶體壓力
  • 適用：build 側很小（維度表）
誰決定join-distribution-type = AUTOMATIC（預設）：CBO 用統計值逐個 join 選擇；並可用 join.max-broadcast-table-size 設上限，官方預設 100MB（超過就別 broadcast，避免壞計畫拖垮整個叢集）。
名詞：build 側／probe 側
Trino join 是 hash join：先拿一邊建 hash table（build），另一邊一行行來查（probe）。build 通常選較小／過濾後較少的那邊
回到範例 Q
nation（25 列）：必 broadcast；orders（1.5 億列）：必 partitioned；customer（150 萬列）：CBO 依估算與 100MB cap 決定要 broadcast 給 orders 還是 partitioned——用 EXPLAIN 看 Join 節點的 Distribution 就知道實際選了哪種
看到慢 join，先問一句：這是一個 broadcast 太大（記憶體／複製），還是 partitioned（shuffle）的 join？——兩種解法完全不同。

17PART 2 · 生命週期 ⑦

Dynamic Filter：把「執行中才知道的 join 條件」變成掃描端的 filter——省下整段沒用的讀取

典型場景：事實表 ⋈「先被 WHERE 過濾」的維度表（Q 的 WHERE 在事實表自己身上，所以 Q 用不到；這是另一種 pattern）
SELECT count(*) FROM wh.tpch.store_sales ss
JOIN wh.tpch.date_dim   d ON ss.sale_date_key = d.date_key
WHERE d.year = 2025 AND d.is_holiday = 'Y'   ← 過濾在維度表（build 側）
dynamic partition pruning） c. partitioned join：coordinator 分發給各 worker 的 probe scan ③ probe 側（store_sales） 照 filter 跳過讀不到的資料： Hive/Parquet 可做 row-group 剪枝； Iceberg split 產生最多等 1s 等 filter （iceberg.dynamic-filtering.wait-timeout）
什麼時候會生效
預設開啟（enable-dynamic-filtering）。支援 inner／right join 的 =／<／<=／>／>=／IS NOT DISTINCT FROM，與 semi join（IN）；build 側過濾後要夠窄才有意義
怎麼確認有沒有效
EXPLAIN 看 join 節點的 dynamicFilterAssignments、scan 節點的 dynamicFilters = {…}；沒看到＝planner 沒產生 DF（條件不支援或統計說不值得）
DF 是「用執行中學到的資訊，回頭省讀取」——效果等同把 join 條件變成分區／檔案剪枝條件。EXPLAIN 沒出現 dynamicFilters，就別期待它幫你。

19PART 3 · 執行引擎 ①

⑥ 計畫切成 stage：每一段「可以平行」的計畫，就是一顆樹枝——Q 會長成這樣

Q 的 stage 樹（示意，真實以 EXPLAIN 為準）

Stage 0（root）Sort＋Limit＋Output
單節點收尾，結果回 coordinator

官方 EXPLAIN (TYPE DISTRIBUTED) 長相（467 文件範例，截錄）

EXPLAIN (TYPE DISTRIBUTED) SELECT regionkey, count(*) FROM nation GROUP BY 1
Fragment 0 [SINGLE]                     ← 單節點 stage（收尾）
  Output[regionkey, _col1]
  └─ RemoteSource[1]                     ← 從 fragment 1 收資料
Fragment 1 [HASH]                        ← 可平行 stage（每 node 一份）
  Aggregate(FINAL)[regionkey]
  └─ LocalExchange[HASH]…                ← 同 node 內重新分配
     └─ RemoteSource[2]
Fragment 2 [SOURCE]                      ← 讀資料的 stage
  Aggregate(PARTIAL)[regionkey]          ← 每 worker 先算自己的部分
  └─ TableScan[nation]
  • [SOURCE]＝讀 connector；[HASH]＝hash 打散執行；[SINGLE]＝單節點
  • stage 之間 = exchange 邊界；資料要跨 node 才需要一個 stage 分界
  • Partial → Final 兩階段聚合：先各自算、再合併——GROUP BY 大表的基本招
看分布計畫先數 stage：stage 越多、exchange 越多＝shuffle 越多；SOURCE stage 的平行度＝splits 數，最下層永遠是並行主戰場。

20PART 3 · 執行引擎 ②

⑦ 執行四階層：Stage 是藍圖，Task 是工人，Driver 是流水線，Operator 是工站

一個 split 對應一個 driver
SOURCE stage 的 task 從 connector 拿 split；driver 從 split 的第一列讀到最後一列，一路過 operator。driver 是「一次讀一份 split 的流水線」
官方定義速記
Stage＝計畫段落（coordinator 腦中）→ Task＝stage 在 worker 上的分身（work horse）→ Driver＝task 內平行流水線（最小平行單位）→ Operator＝吃 page 吐 page 的工站
看到任何「平行度」問題，先定位在階層的哪一層：splits 不夠多（資料切太粗）→ 平行上不去；task 太多（小檔案）→ 管理成本吃掉好處。

21PART 3 · 執行引擎 ③

資料的最小流動單位是 Page：一包「同列數、逐欄分開」的 columnar 資料塊

為什麼 columnar 比較快
① 只把「要用的欄」放進記憶體與網路（Q 的 join 只需 custkey，不必載整列）；② 同型別連續存放 → CPU cache 友善、壓縮率高；③ operator 一次處理一整包，省掉逐列的 method call 開銷
跟 Parquet 的關係
Parquet 本身就是 columnar 檔案格式——connector 讀 Parquet 時，column chunk 直接餵成 Block，格式對齊所以轉換成本低；這也是 lakehouse 引擎的共通語言
Page 是 Trino 的「貨幣」：讀取、計算、傳輸、spill 全部以 page 為單位——所以「少讀欄位、少傳資料」的效益會乘上整條管線。

22PART 3 · 執行引擎 ④

Exchange 是 stage 之間的「水管」：有 backpressure 的水管——慢的 downstream 會回堵上游

output buffer buffer 滿 → 上游暫停（backpressure） HTTP 467 起內部通訊預設 HTTP/1.1 Stage 1：consumer task 用 exchange client 拉 page （RemoteSource operator） 吃得慢 → 對方 buffer 塞住 → 連鎖停等 誰需要 exchange（= shuffle 時機） join 的 partitioned 分布 照 join key hash 分給各 node group by 的兩階段聚合 partial → final 之間打散 同一台 node 內 driver 之間也有「LocalExchange」（EXPLAIN 常見）；跨 node 才是 RemoteExchange（HTTP）

對查詢效能的意義

  • 全 query 的完成時間 ≈ 最慢的那條 exchange 鏈：一台 worker 慢（或 node 資源被別的 query 搶），上游全部等它——「長尾拖垮全場」
  • EXPLAIN ANALYZE 的 Blocked 時間就是在等 exchange／等待的證據

對成本模型的意義

  • exchange 搬的 bytes 是「傳輸成本」：broadcast 複製、partitioned 兩邊 shuffle、skew 造成單一 node 爆量
  • 少搬＝改 join 分布／早點過濾／DF 生效——傳得少比算得快更常是解藥
把 exchange 想成「有 buffer 的水管」：任一節點吃不下，整條管線都會回堵——所以單一慢 worker、傾斜的 key，會以「某個 task 卡住」的形式出現。

排程：Coordinator 照著 split 清單「發工作」，平行度由 splits 數 × 每台 worker 的並行能力決定

Coordinator：split 排程器
問 connector 拿整張表的 split 清單（p30）→ 依 node 狀態分派
（官方：coordinator 追蹤「哪台機器跑哪些 task、哪些 split 在哪些 task 手上」）

25PART 4 · 記憶體與容錯 ①

記憶體是一場「預算戰爭」：user 算的、可回收的、JVM 私藏的——各有額度，超標就殺

JVM heap × 0.3（query.max-memory-per-node）｜全 cluster user ≦ 20GB（query.max-memory）｜含 revocable 的總量 ≦ user × 2（query.max-total-memory）

超標會發生什麼

  • 單 node 或全 cluster 超限 → 該 query 被 kill，錯誤訊息例如 “Query exceeded per-node total memory limit …”
  • 低記憶體時由 low-memory-killer 動手：預設 policy 殺「卡在已滿 node 上、又無法推進」的 query／task（total-reservation-on-blocked-nodes）

一個關鍵例外（常被誤解）

  • 官方文件註明：per-node／total memory 上限不適用於 retry-policy=TASK 的查詢（25 頁那三個額度都是）
  • 原因：TASK retry 把「單點記憶體爆掉」當成可重試的故障，用重跑取代預先設限
  • 所以「為什麼開了 task retry 之後 query 反而能吃更多記憶體」——這是設計，不是 bug
記憶體錯誤＝預算戰爭的陣亡通知：先看是哪條額度被踩（per-node？total？），再決定要縮查詢（少 broadcast、早過濾）還是開 spill。

26PART 4 · 記憶體與容錯 ②

Spill：記憶體不夠時「分期付款」——把中間狀態寫去磁碟，慢，但不用死

怎麼知道 spill 真的發生
EXPLAIN ANALYZE 的 operator 統計會出現 disk／spill 相關欄位，Web UI 也有 spill 計數；fragment 的 CPU 不高卻很慢＋磁碟 IO 高，就是 spill 在拖
spill vs kill 的分界記憶體滿時：該 operator 支援 spill 且 spill-enabled → 寫磁碟續命；否則 → 直接超限被 kill。所以 spill 是「用時間換活命」的開關，不是效能加速器。
EXPLAIN ANALYZE 看到 spill 發生（或 disk 出現）＝查詢在記憶體邊緣求生——治本是讓它不需要 spill（更早過濾、更小 broadcast、更多 worker），不是把 spill 調大。

27PART 4 · 記憶體與容錯 ③

記憶體相關錯誤怎麼讀：先看訊息裡的關鍵字，對回上一頁的預算規則

三個常見的記憶體錯誤（訊息模式）
Query exceeded per-node total memory limit of 10GB      ← 單 node 總額度被踩（user+revocable）
Query exceeded total memory limit of 20GB               ← 全 cluster 總額度被踩
Query exceeded per-node user memory limit of 6GB        ← 單 node user memory 被踩
（低記憶體時 system 主動殺）→ 查 Web UI／log：被 low-memory-killer 終止的 query／task

先確認：誰吃掉的？

  • 用 EXPLAIN ANALYZE 找吃記憶體最兇的 operator（join build、aggregation、排序）
  • broadcast join 的 build 表太大？group key 太多（基數高）？還是同時太多 query 在搶同一台 node？
  • 被 low-memory-killer 殺的常常不是「最肥的」，而是「卡住不動、佔著茅坑」的那個

再決定：哪條路？

  • 縮查詢：更早過濾、換 join 順序／分布、拆小查詢
  • 開 spill（26 頁）：讓支援的 operator 寫磁碟續命——治標
  • 調額度或加 worker：這是平台設定，要跟平台負責人（我們）討論，不是 session 隨手改
  • retry-policy=TASK 的查詢不吃這套上限（25 頁例外）
工程師的反射動作看到 “exceeded … memory limit” 別急著把記憶體參數調大——先問「這個查詢為什麼需要那麼多記憶體」，答案通常是計畫形狀問題（join／aggregation），不是額度問題。
記憶體錯誤是「症狀」不是「病因」：訊息告訴你哪條線被踩，EXPLAIN ANALYZE 告訴你誰在吃——兩個都要看。

28PART 4 · 記憶體與容錯 ④

Worker 掛了怎麼辦：NONE 直接死、QUERY 整條重跑、TASK 只重跑受傷的那一塊

retry-policy = NONE（467 預設）

故障容忍關閉
  • 執行中 node 缺資源或失敗 → 整條 query 失敗，手動重跑（官方原文）
  • query 跑越久，中獎機率越高——長查詢的痛點

QUERY（適合短查詢、高併發）

  • node 層級錯誤 → 自動整條重跑（最多 4 次，間隔 10s 起、每次 ×2 到上限 1m）
  • 中繼資料不落盤，成本低；大查詢重跑成本高

TASK（適合大型批次查詢）

官方：「推薦給大型批次——重跑小 task 比重跑整條有效率」
  • 只重跑失敗的那個 task（每 task 最多 4 次）；其他 task 的產出繼續用
  • 代價：stage 之間的中繼資料要 spool 到外部儲存（exchange manager：S3／HDFS 等），且預設加密（每 query 一把隨機鑰匙）
  • 短查詢高量情境反而變慢（spooling 開銷）——官方建議批次用專屬 TASK 叢集
  • 啟用後自動切換「最佳實務」預設：task.concurrency → 8、per-node 記憶體上限不適用（25 頁）
「開 fault-tolerant 就無敵」是誤解：TASK 用「中繼資料落盤＋可重算」換穩定，代價是額外 IO 與短查詢延遲——所以官方才建議批次與短查詢分叢集。

30PART 5 · Connector ①

Connector 三大介面，對應查詢的三個時刻：Metadata 被問兩次、Splits 產生一次、PageSource 一直讀

Connector 是「引擎與資料之間唯一的合約」：引擎只會 metadata／split／page 三種問法；效能差異全部來自 connector 對這三個介面的實作品質。

31PART 5 · Connector ②

Iceberg 讀取堆疊：metadata 是地圖，檔案是領土——查詢先看地圖，只去該去的地方

同一條查詢快不快，常早在「讀檔之前」就決定了：分區鍵有沒有對上 filter、投影有沒有只選要的欄、檔案大小健不健康——這三件事決定實際 IO 量。

32PART 5 · Connector ③

Split 是平行度的貨幣：太多太小＝管理費爆表；太少太大＝工人閒置

資料工程師的動作覺得「這張 Iceberg 表 scan 很慢」→ 先看檔案數與平均大小：對分區做 compaction／rewrite data files，比調任何引擎參數都有效。
Split 是平行度的貨幣，而貨幣的「面額」由資料健康度決定：檔案太大太少 → 平行不足；太多太小 → 開銷爆表——target 是檔案大小跟讀取任務匹配（通常數十 MB 到數百 MB 級）。

33PART 5 · Connector ④

寫入也走同一套引擎——但「存資料」是 Iceberg 的事：commit = 換一張新的 snapshot

只新增、不修改舊檔 ③ commit：換 snapshot coordinator 透過 connector metadata 把 manifest list 指到新版本——原子切換 ✓ 查得到 後續查詢 自動看到 新 snapshot 對資料工程師的三個含義 ① 為什麼寫入是「新增」不是「覆蓋」 小筆頻繁寫入 → 檔案越切越碎 → 第 32 頁的小檔問題 → 需要 compaction 合併 ② 為什麼 commit 前失敗不會留半套 snapshot 沒切換 = 資料沒「上架」； 孤兒檔案由 Iceberg 清理機制處理 ③ 引擎保持無狀態 transaction 語意由 Iceberg catalog 保證； 467 的 Iceberg 讀寫都支援 fault-tolerant（28 頁）
「Trino 寫資料」其實是：Trino 算好新檔案、叫 Iceberg 換一張 snapshot——這解釋了為何資料立即可見、為何舊檔不動、為何碎檔要靠 compaction。

PART 6把原理用回效能診斷

35PART 6 · 效能診斷 ①

端到端成本分五層：優化 = 找出「目前最貴的一層」，不是亂加資源

診斷口訣先讀第一行分時間（Queued／Analysis／Planning／Execution），再往下找 Execution 內 CPU 最高或 Blocked 最久的 fragment／operator——每一層都有對應的修法，而不是整包重寫。
優化的順序永遠是：定位最貴的一層 → 對照機制 → 做最小改動 → 重測。原理的價值就是讓你在動手前先知道「該動哪一層」。

36PART 6 · 效能診斷 ②

症狀 → 機制 → 動作：八個最常見的「看起來很怪」的現象

同一條 SQL 忽快忽慢
資源被其他 query 搶；exchange backpressure（22 頁）讓最慢的 task 決定全場
看 Web UI 同時在跑什麼；把大查詢排離尖峰
常見
“exceeded per-node memory limit”
單 node 的 user／total memory 額度被踩（25 頁）——多半是 broadcast 或 group by 太肥
EXPLAIN ANALYZE 找吃記憶體 operator；縮 build／開 spill
要處理
出現 spill 後龜速
記憶體不夠，operator 在磁碟邊緣求生（26 頁）
治本：更早過濾／更小 broadcast／更多平行，不是調大 spill
要處理
join 超慢且記憶體爆
broadcast 了不該 broadcast 的大 build（超過 100MB cap 卻仍被選？統計誤判）；或 partitioned 卻大量 shuffle
EXPLAIN 看 Join 的 Distribution；檢查統計值新鮮度（15 頁）
要處理
join 大表 scan 全讀
dynamic filter 沒接上：build 側沒先過濾、條件不支援、或 connector 不吃（17 頁）
EXPLAIN 找 dynamicFilters=；改寫成「先過濾維度表」的 pattern
要處理
Iceberg 表 scan 慢但檔案不多
分區鍵與 filter 不匹配 → 分區剪枝失效；projection 讀了沒用的欄（31 頁）
確認 filter 在分區鍵上；SELECT 只列需要的欄
常見
小檔案幾十萬個
split 數爆炸：metadata＋排程開銷 > 掃描本身（32 頁）
對分區 compaction（rewrite data files）
資料品質
coordinator CPU 100%

常見

37PART 6 · 效能診斷 ③

EXPLAIN ANALYZE 讀法：第一行分階段，往下找最貴的 operator——Blocked 是等待，CPU 才是計算

官方文件範例（467 sql/explain-analyze，節錄）——先看這三行
Queued: 374us, Analysis: 190ms, Planning: 179ms, Execution: 3.06s   ← 哪一階段最久？
Fragment 1 [HASH]
  CPU: 22.58ms, Scheduled: 96.72ms, Blocked: 46.21s (Input: 23.06s, Output: 0ns)
  Input: 1000 rows (37.11kB) …                                ← Blocked ≫ CPU = 在等（exchange／資源）
  └─ Aggregate[type = FINAL, keys = [clerk]]
     CPU: 8.00ms (3.51%), Scheduled: 22.00ms (5.28%), Blocked: 0ns, Output: 1000 rows …
     Input avg.: 15.63 rows, Input std.dev.: 24.36%            ← std.dev 大 = 資料傾斜
第一步：第一行分階段
Queued＝排隊等資源｜Analysis＋Planning＝coordinator 在想（12–15 頁）｜Execution＝worker 在跑（19–23 頁）。Planning 佔比大 → 查「想」的那層；Execution 大 → 往下看 fragment
第二步：fragment 與 operator 三組數字
CPU＝真的在算（含括號內佔總時間百分比）｜Scheduled＝被排到但可能等資源｜Blocked＝卡在等待（下游 buffer、exchange、慢 worker）——Blocked 高不是 operator 的錯，是它上游／下游的系統性問題
第三步：看資料形狀
每個 operator 的 Input rows／bytes 與 avg.／std.dev.：std.dev 大 = 各 task 量不均 = skew（傾斜的 key、不均的 split）；scan 的 bytes 大 = pushdown 沒吃滿（31 頁）
反射動作看到「某 operator CPU 只佔 3% 卻讓 fragment 卡 46 秒」——問題不在這個 operator，在它等什麼：往上追 exchange、往下追 scan。
EXPLAIN ANALYZE 是「原理的儀表板」：每一欄都對應一個你已經懂的機制——讀得懂它，就等於把這份教材用在了真實查詢上。

38PART 7 · 驗收準備 ①

名詞速查：21 個關鍵字，一個蘿蔔一個坑（忘了就回來看這頁）

Coordinator
「大腦」：parse／plan／最佳化／切 splits／排程；不碰資料（07）
Worker
「肌肉」：執行 task、讀 connector、互相 exchange（07）
Connector / Catalog
翻譯層；catalog＝設定檔綁一個 connector 實例（08）
Split
資料集的一小段、最小工作單位；task 照 split 領工（20、32）
Stage
計畫的一段，coordinator 腦中的模型；stage 之間是 exchange（19）
Task
stage 在 worker 上的執行分身，「work horse」（20）
Driver
task 內的最小平行單位＝一串 operator 的流水線（20）
Operator
吃 page 吐 page 的工站：scan／filter／join／aggregate…（20）
Page / Block
資料流動單位：一包同列數、逐欄（Block）的 columnar 資料（21）
Exchange
stage 間的水管：LocalExchange（同 node）／Remote（跨 node，HTTP）；有 backpressure（22）
Broadcast join
小 build 複製到每台 node，零 shuffle；上限預設 100MB（16）
Partitioned join
兩邊照 key 打散再 join；無單點記憶體上限但有 shuffle（16）
CBO / RBO
成本最佳化（靠統計）／規則最佳化（靠規則）（14–15）
Dynamic filter
執行中把 join 條件變成 scan 端 filter；預設開啟（17）
Pushdown
引擎把 filter／投影／limit 推給 connector 處理（14、31）
User memory
可歸因於 query 的記憶體（hash table、sort）；有 per-node／總量額度（25）
Revocable memory
可被回收的記憶體；回收不來就 spill（25–26）
Spill
記憶體不足時把中間狀態寫磁碟續命；預設關閉（26）
retry-policy
NONE（預設）／QUERY（整條重跑）／TASK（只重跑失敗 task，要 spool）（28）
Spooling
TASK retry 時中繼 exchange 資料落外部儲存，供重跑使用（28）
EXPLAIN ANALYZE
真實執行＋統計：第一行分階段，往下看 CPU／Blocked／input（37）
