Internal Note · Agentic Workflow

Agentic Workflow
用 agent 把工作串成可重複跑的流程

以 Oh My Pi（omp） 當具體範例，講清楚三件事：何時啟動、如何接到 agent、一輪做完之後怎麼接下一輪。同樣的結構也適用於其他 coding agent。

Agentic workflow 不是「模型一直想」。
它是：有訊號進來 → 選一個 session → 跑一輪 agent loop → 把結果寫回去，需要的話再跑下一輪。

觸發
時間到了，還是事情發生了？
接法
每次新開一支程式，還是留一個值班的？

你真正要設計的就只有這兩層。Queue、審批、多步驟狀態機，都是把這兩層包起來，不是另一種引擎。

01先看一輪：agent loop 在做什麼

不管觸發怎麼來，agent 實際執行的單位都是「一輪」。一輪長這樣：

01
收到一句指令
例如「檢查未合併 PR 和 CI」
▼
02
模型想一想
判斷要做什麼、要不要用工具
▼
03
需要就呼叫工具
讀檔、跑指令、開子 agent……
▼
04
看工具結果再想
不夠就再呼叫一次，直到這輪能收尾
▼
05
這輪結束（yield）
停下來，等下一次指令
正在示範第 1 步

同一輪，omp 有三種下法

介面寫法
CLIomp -p "做 X"　（跑完就退出）
SDKsession.prompt("做 X")
RPC{"type":"prompt","message":"做 X"}
三個容易搞錯的點
  • idle 幾乎不燒 token，只是行程還活著。
  • omp 的 /loop 是「同一句話自動再送」，比較像輪詢，不是 workflow 引擎。
  • 常駐的是 process，不是 loop 24 小時空轉。

02第一層｜觸發：時間到了，還是事情發生了

時間到了 · polling / cron

鬧鐘響了就跑 workflow 的下一步。

適合：每晚掃依賴、每 15 分鐘看 CI、週一安全檢查。

# crontab：每 15 分鐘看一次 PR 與 CI
*/15 * * * * cd /repo && omp -p \
  "檢查未合併 PR 和 CI，有問題寫進報告"

終端機還開著時，omp 也有便宜版：

  • /loop 5m 檢查 CI
  • 社群排程套件（例如 pi-schedule）
這兩個都要 omp 視窗還開著才會響，關終端機就停。真的要排程，還是 OS cron / systemd。
事情發生了 · event-driven

門鈴響了才跑。

適合：CI 紅了、有人推 code、webhook、檔案被改、使用者按按鈕。

事件來源
CI / GitHub webhook / 你的 API / 檔案變更
▼
呼叫一輪 agent
omp -p 或既有 session 的 prompt
時間驅動的取捨

優點：簡單、人不在也會跑。
缺點：沒事件也跑，有事件也要等下一個整點。

事件驅動的取捨

優點：準、不空轉。
缺點：要有一個東西一直活著收事件（你的 API，或一支常駐的 omp）。

03第二層｜接法：workflow 怎麼接到 omp

觸發和接法是正交的：cron 可以打常駐服務，webhook 也可以每次新開一支 omp。接法只有三種主要選擇，外加一種「人還坐在終端機前」。

接法 A 每次新開一支 · 短命 session

來一個工作項目，啟動 omp，做完退出。這是最薄的 workflow 步驟。

cron / webhook
▼
omp -p "任務"
▼
做完結束

適合：步驟彼此獨立、不需要記得上一輪在講什麼。
不適合：同一條線要連續改到完。

接法 B 把 omp 嵌進你的服務 · SDK

你的程式 import @oh-my-pi/pi-coding-agent，行程裡放一個 session。注意這是完整 coding agent，不是薄層的 @oh-my-pi/pi-agent。

API在 workflow 裡的意思
session.prompt(…)開新的一輪
session.followUp(…)等這輪做完再做下一步
session.steer(…)打斷正在做的，插入新指示
session.newSession()清對話，開始下一件獨立工作
webhook / 使用者 / 排程
▼
你的 API（建議 Bun）
▼
createAgentSession()
和 omp CLI 同一套引擎
▼
prompt / newSession

適合：服務本身是 TypeScript / Bun，想直接碰 session、自己加工具。
注意：agent 卡死或記憶體爆掉，你的 API 可能一起死。需要 Bun ≥ 1.3.14。

接法 C 旁邊放一個值班的 omp · RPC

RPC（Remote Procedure Call）不是新的 agent 能力，只是用 JSON 對另一支程式下指令。

你的 workflow / API（什麼語言都行）
▼ stdin 丟一行 JSON
omp --mode rpc
獨立子行程，門開著等人按鈴
▲ stdout 吐事件
你收到的結果
// 你丟進去
{"id":"1","type":"prompt","message":"看 src/ 有哪些 TS 檔"}

// 或把「下一件獨立工作」做成新 session
{"id":"2","type":"new_session"}
{"id":"3","type":"follow_up","message":"改去查 staging"}
指令在 workflow 裡的意思
prompt當新的 user 訊息，跑完整一輪
follow_up這輪做完再跑
steer打斷正在跑的
new_session開新 session
abort停當前這輪

適合：API 不是 Bun、要隔離崩潰、或以後想換語言。
同類協定還有 ACP（給編輯器 / IDE 當 host，對 agent 下 session/prompt）。

接法 D · 不算產品方案

人還坐在終端機前：omp 的 /loop、/goal、extension 裡 sendUserMessage。這是開發時把 workflow 跑起來的便宜作法，不是常駐產品方案。

04每一種方法的優缺點與限制

兩層本身先對照。上層包裝（queue、Temporal、審批）不另開一種 agent，只是何時再呼叫同一套 loop。

觸發

時間到了

鬧鐘響了就跑。實作是 OS cron / systemd，或終端機還開著時的 /loop。

優點
  • 實作最薄：一條 crontab 就能跑。
  • 人不在也會跑（用 OS 排程時）。
  • 不需要 webhook、不需要常駐收件服務。
缺點
  • 沒事件也跑，空轉燒時間與 token。
  • 有事件也要等下一個整點，反應慢。
限制
  • /loop、社群排程套件都要 omp 視窗還開著；關終端機就停。
  • 真要人不在也跑，只能靠 OS cron / systemd，不是 omp 自己。
  • cron 不管「上一輪還沒跑完」：間隔太短會重疊，要自己加鎖或拉長間隔。
  • 不適合「按下按鈕立刻改」這類秒級反應。
事情發生了

門鈴響了才跑。事件來自 CI、push、webhook、檔案變更、使用者按鈕。

優點
  • 準：有事才跑，不空轉。
  • 延遲低：事件到了就進下一輪。
缺點
  • 必須有一個東西一直活著收事件（你的 API，或一支常駐 omp）。
  • 漏事件、重送、同一事件打兩次，都要自己處理。
限制
  • 沒有事件來源（沒 webhook、沒監看）就用不了。
  • 事件風暴會連打多輪；要並行或排隊，否則一支 agent 會卡住。
  • 失敗重試、冪等（同一 webhook 不重複改碼）不是 omp 內建，要寫在你的 workflow。

接法

A 每次新開一支 · omp -p

來一個工作就啟動 omp，做完退出。行程不留。

優點
  • 最薄：cron / webhook 直接 spawn，任何語言都行。
  • 崩潰隔離：這支掛了，下一件工作是新行程。
  • 無狀態，好重跑：失敗就再 spawn 一次。
缺點
  • 沒有上一輪記憶。連續改同一條線會失憶。
  • 每次冷啟動（進 repo、讀工具），比常駐 session 慢。
限制
  • 做完行程就死，不能 followUp / steer。
  • 要留下結果，必須寫到檔案、PR、資料庫；不能靠對話紀錄。
  • 長任務可能撞上 cron 下一輪，或被 OS 殺掉。
  • 要並行 N 件，就是 N 個 process，記憶體跟著線性漲。
B SDK 嵌進服務

同一支 API 行程裡放 session。直接 prompt / followUp / steer / newSession。

優點
  • 延遲最低：沒有跨行程 JSON。
  • 能直接碰 session、自己加工具、接你的 log / auth。
  • 同一條線連續做：followUp、steer 都在物件上。
缺點
  • agent 卡死或記憶體爆掉，API 可能一起死。
  • 綁 TypeScript / Bun，換語言就要拆掉。
限制
  • 需要 Bun ≥ 1.3.14；套件是完整的 @oh-my-pi/pi-coding-agent，不是薄層 pi-agent。
  • 服務重啟，記憶體裡的 session 全沒了（要延續得自己存）。
  • 水平擴展時，同一個 session 黏在那一台；後面要加 queue 才能拆開。
  • 多使用者同時進同一 session 會互相污染，要按工作切 newSession。
C 值班 RPC · omp --mode rpc

旁邊放一支獨立 omp，stdin 丟 JSON、stdout 收事件。能力與 SDK 同一套 loop，只是換輸送管。

優點
  • API 什麼語言都行。
  • 崩潰隔離：omp 掛了，你的服務還在。
  • idle 幾乎不燒 token，只是行程活著等人按鈴。
缺點
  • 多一層 IPC：要處理斷線、重啟、一行 JSON 解析。
  • 除錯比 SDK 繞（問題在你這邊還是子行程）。
限制
  • 還是要有人保活這支子行程（systemd / 你的 supervisor）。
  • 一支 RPC 同一時間通常只跑一輪；要並行就開多支。
  • 大輸出、二進位、多行訊息要遵守「一行一個 JSON」；破格式就對不準。
  • RPC 不是更強的 agent，也不能取代 queue / 狀態機。
D TUI 開著 · /loop、/goal

人還坐在終端機前。開發時把流程跑起來用，不是產品。

優點
  • 零基礎設施，打開 omp 就能試。
  • 看得到模型在幹嘛，適合調 prompt。
缺點
  • 人走、關視窗、筆電休眠，流程就停。
  • 不能當值班服務，也難給同事當 API 用。
限制
  • 只在「這台機器、這個終端機還開著」時有效。
  • webhook 無法穩定打進來（除非 extension 且視窗仍在）。
  • 不要把 /loop 當成 cron；它只是同一句話自動再送。

上層包裝（可選，不是新引擎）

這些只決定「何時再呼叫同一套 loop」。優點是控制面變強；限制是多一個系統要維運。

包裝優點缺點 / 限制
Job queue 削峰、可重試、可加 worker 要維 Redis / SQS；不幫你管 session 記憶。每個 job 對一次 prompt 或一支 omp -p
Workflow 引擎 步驟可重跑、留下「進行到哪」 Temporal / Inngest 本身有學習與維運成本；不要幻想單一 loop 跑三天
主從 agent 拆工、主 agent 彙整 子 agent 也要配額與隔離；失敗要定義誰重試。omp 用 task 開 subagent
人在迴圈裡 危險動作先停，有人按 OK 才做 人沒按就卡住；不適合無人值班。靠 tool approval、plan 確認
Batch / 評測 一堆步驟排著跑，結果可對 花費與時間都線性；失敗要記錄哪一步。迴圈打 omp -p 或 SDK prompt
對照時只記三句：時間驅動會空轉、事件驅動要有人收信；omp -p 沒有記憶但最穩；SDK 快但會跟 API 一起死；RPC 隔離崩潰但要保活子行程；/loop 只給人盯著終端機用。

06Session 在 workflow 裡活多久

Agentic workflow 常踩的不是「會不會跑」，而是「這一步該不該帶著上一輪的記憶」。

同一條線做完

用 prompt / followUp，留在同一個 session。

每個事件互不污染

先 newSession 再 prompt，或乾脆每次 omp -p。

上下文太長：omp 可以 compact（摘要後繼續）或 handoff（開新 session 帶摘要）。這是延命，不是新的觸發方式。

07再往上包一層（仍然不是新的 loop）

控制面就是前面那些。產品差異多半在包裝：

模式多了什麼用 omp 時長怎樣
Job queue事件先排進 Redis / SQS，worker 一次領一件每個 job 對一次 prompt 或一支 omp -p
Workflow 引擎Temporal / Inngest 當狀態機規劃、改碼、開 PR 各呼叫一次 omp
主從 agent主 agent 拆工，子 agent 執行omp 的 task 開 subagent，再彙整
人在迴圈裡危險動作先停下來等人按 OKtool approval、plan 確認
Batch / 評測一堆步驟排著跑迴圈打 omp -p 或 SDK prompt

完整一條 agentic workflow 通常是：

觸發（時間 / 事件 / 人）
▼
佇列或狀態機（可選）
▼
選 session（沿用 or 新建）
▼
跑一輪 omp agent loop
▼
工具、子 agent、審批
▼
寫回結果（PR、資料庫、回覆使用者）

09常見誤解 · 專有名詞

五個常見誤解

✕「RPC 就是 loop 一直轉」

錯。常駐的是行程，沒指令就不跑模型。

✕「event-driven 一定要 import library」

錯。RPC、每次 omp -p、TUI extension 都可以收事件。

✕「做 agentic workflow 必須自己寫 agent loop」

錯。omp 的 prompt() / RPC prompt 已經會把這一輪跑完。

✕「queue / Temporal 是另一種 agent」

錯。它們只負責何時再呼叫同一套 loop。

✕「一個 session 從頭跑到專案結束」

通常不該。獨立工作要新 session，長線工作靠摘要或狀態機。

專有名詞

詞白話

一句話帶走：先決定觸發（時間 / 事件），再決定接法（新開一支 / 常駐 SDK / 常駐 RPC），最後決定session 要不要延續。其餘都是包裝。
